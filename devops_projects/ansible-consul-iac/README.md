# 🔧 Ansible и Consul: удалённое конфигурирование и Service Discovery

### 📌 Обзор проекта

Две части, каждая со своим стендом. В первой **Ansible** настраивает два узла с управляющей машины: на одном разворачивается приложение из микросервисов, на другом — Apache и PostgreSQL. Во второй появляется **Consul**: сервисы регистрируются сами, находят друг друга по именам и общаются через service mesh, не зная адресов.

Ключевая разница между частями — в том, откуда сервис узнаёт, где живёт его база. В первой адрес прописан в конфигурации. Во второй его нет вообще: приложение обращается к локальному порту, а sidecar-прокси доставляет трафик туда, где база находится сейчас.

### 🏗 Два стенда

```
   ЧАСТЬ 1 — конфигурирование через Ansible
   ┌─ manager .10 ─┐   ansible-playbook -i inventory site.yml
   │  Ansible      │──────────────┬──────────────────┐
   └───────────────┘              │ SSH              │ SSH
                                  ▼                  ▼
                        ┌─ node01 .11 ──┐   ┌─ node02 .12 ──┐
                        │ роль          │   │ роли          │
                        │ application:  │   │ apache        │
                        │ Docker +      │   │ postgres      │
                        │ микросервисы  │   │               │
                        └───────────────┘   └───────────────┘

   ЧАСТЬ 2 — Service Discovery через Consul
   ┌─ manager .19 ─┐   сборка JAR, затем ansible-playbook
   │  Ansible      │────────┬─────────────┬─────────────┐
   └───────────────┘        ▼             ▼             ▼
              ┌─ consul-server .20 ─┐  ┌─ api .21 ─┐  ┌─ db .22 ─┐
              │ server = true       │◄─┤ client    │  │ client   │
              │ UI :8500            │  │ hotel-svc │  │ postgres │
              └─────────────────────┘  └─────┬─────┘  └────┬─────┘
                                             │  mesh       │
                                             └──►sidecar───┘
                                        localhost:5432 → db:5432
```

Во второй части `hotel-service` обращается к базе по адресу `localhost:5432`. Никакого PostgreSQL на этом узле нет — порт открывает sidecar-прокси, который и доставляет трафик на `db`.

### 🚀 Ключевые решения

* **Роли вместо плоского плейбука.** Первая версия развёртывания — один файл `deploy_node01.yaml` на полторы сотни строк. Он оставлен рядом как история решения, но рабочим стал `site.yml` с ролями: переменные ушли в `defaults/`, и переопределить версию PostgreSQL или каталог развёртывания стало можно, не трогая задачи.

* **Порядок play в части 2 определяет работоспособность.** Сервер Consul поднимается раньше клиентов, база — раньше сервиса, который к ней обращается. Перестановка второго и третьего шага оставила бы клиентов без сервера: они бы стартовали, повторяли попытки и не регистрировались.

* **Пароль PostgreSQL задаётся до правки `pg_hba.conf`, а не после.** Пока действует peer-аутентификация через Unix-сокет, Ansible подключается к базе без пароля. Стоит сначала переключить метод на `md5`, и следующая же задача не сможет войти — пароля ещё нет. Порядок в роли зафиксирован явным комментарием.

* **Один конфиг клиента Consul на оба узла.** `advertise_addr` задан шаблоном go-sockaddr, который выбирает адрес из сети стенда. Фиксированное значение потребовало бы по файлу на узел, а взять первый попавшийся интерфейс нельзя — им окажется NAT от Vagrant.

* **`retry_join` вместо `join`.** Клиент повторяет попытки подключения, пока сервер не появится, и порядок запуска машин перестаёт иметь значение.

* **Сборка JAR на управляющей машине.** На целевой узел уезжает готовый артефакт, а JDK и Maven туда ставить не нужно — это разделение сборки и развёртывания в самом простом виде.

* **Адрес базы отсутствует в конфигурации сервиса.** В `hotel.json` описан upstream на `postgres` с локальным портом 5432, а роль `install_hotels_service` пишет сервису `POSTGRES_HOST=127.0.0.1`. Никакого PostgreSQL на этом узле нет — порт открывает sidecar-прокси. Адрес `192.168.56.22`, где база живёт на самом деле, в конфигурации приложения не встречается ни разу.

* **Роли сами проверяют предусловия.** Consul и Envoy не ставятся из репозиториев Ubuntu, их дистрибутивы кладутся на управляющую машину заранее. Роли ищут их через `delegate_to: localhost` и падают с внятным сообщением до того, как что-либо поменяют на целевых узлах, — а не в середине развёртывания.

| `ansible02/inventory.yml` | инвентарь в формате YAML |

| `consul01/*.hcl` | конфигурации сервера и клиента Consul |
| `consul01/*.json` | регистрации сервисов `hotel` и `postgres` |
| `main_report.md` | отчёт по обеим частям с командами и скриншотами |
| `images/` | 42 скриншота работы |

Исходный код микросервисов в репозиторий не входит — он выдан курсом. Дистрибутивы Consul и Envoy тоже: они скачиваются отдельно и загружаются на управляющую машину, команды приведены в [отчёте](./main_report.md#подготовка-бинарники-на-управляющей-машине).

> **Раскладку каталогов менять нельзя.** Роли части 2 ссылаются на конфигурации Consul путём `../../../consul01/...`, который Ansible разрешает от каталога роли. Поэтому `ansible02/` и `consul01/` обязаны оставаться соседями — и в репозитории, и при загрузке на управляющую машину.

> Пароли PostgreSQL (`postgres/postgres`) — учебные заглушки локального стенда, не образец рабочей практики. `client_addr = "0.0.0.0"` у сервера Consul открывает API и веб-интерфейс без аутентификации: для стенда из четырёх виртуальных машин это допустимо, для рабочего окружения — нет.

### 📈 Итоговый результат

Обе части отрабатывают: узлы конфигурируются с управляющей машины одной командой, сервисы регистрируются в Consul и видны в его интерфейсе, `hotel-service` находит базу через service mesh. Операции чтения и создания через API работают.

Отдельного упоминания заслуживает то, что **не** заработало. Обновление и удаление записи возвращают HTTP 500 с исключением `Provided id of the wrong type: Expected class java.lang.Integer, got class java.lang.Long`. Ошибка приходит из самого `hotel-service` — сервиса из поставки курса — и к настройке инфраструктуры отношения не имеет. Инфраструктура при этом работает: запрос доходит до сервиса, сервис доходит до базы, ответ возвращается. Разбор — в [отчёте](./main_report.md#проверка-crud-через-api).

Главный вывод — про то, где хранится знание об адресах. В первой части оно распределено по конфигурациям: сервис знает адрес базы, прокси знает адрес сервиса, и каждый переезд требует правки в нескольких местах. Во второй части этого знания нет ни у кого, кроме Consul, а сервисы обращаются к локальным портам. Цена — дополнительный слой из агента и sidecar-прокси на каждом узле; выигрыш — то, что переезд перестаёт быть событием.
