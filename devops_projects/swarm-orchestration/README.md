# 🐝 Docker Compose и Docker Swarm: приложение из 7 микросервисов

### 📌 Обзор проекта

Приложение из семи микросервисов на Spring Boot с PostgreSQL и RabbitMQ проходит три стадии: сборка образов и запуск на одной машине через **Docker Compose**, перенос кода в виртуальную машину через **Vagrant**, и наконец распределение по кластеру **Docker Swarm** из трёх узлов.

Это первое задание сквозной линии: дальше то же приложение разворачивается через Ansible, обкладывается мониторингом, переезжает в Kubernetes и параметризуется через Helm. Здесь закладывается всё, на что опираются следующие — образы в реестре, схема сети, обратный прокси и стенд из трёх машин.

### 🚀 Ключевые решения

* **`resolver` в конфигурации прокси обязателен.** Без него nginx резолвит имена сервисов один раз при старте и запоминает адреса навсегда. В Docker адрес контейнера меняется при каждом пересоздании, поэтому после перезапуска любого сервиса прокси продолжал бы стучаться по мёртвому адресу. Директива `resolver 127.0.0.11 valid=10s` указывает на встроенный DNS Docker и ограничивает время жизни записи в кеше.

* **Токен входа в кластер передаётся через общую папку, а не по SSH.** Порядок подъёма машин Vagrant не гарантирует. Менеджер кладёт токен в смонтированный на все узлы каталог, рабочие узлы ждут его появления до минуты. Проверяется не только существование файла, но и его непустота: файл создаётся перенаправлением вывода и успевает появиться пустым раньше, чем в него попадёт токен.

* **`--advertise-addr` при двух интерфейсах.** У машины Vagrant их два: NAT и приватная сеть стенда. Без явного указания Swarm выбирает адрес сам и нередко берёт NAT-овский, по которому соседние узлы до него не достучатся.

* **Проверка «Swarm уже активен» перед инициализацией.** Провижининг запускается заново при каждом `vagrant up` остановленной машины, а `docker swarm init` на уже собранном кластере завершается ошибкой — с `set -e` это уронило бы весь подъём стенда.

* **`tasks.agent` вместо `agent` у Portainer.** Обычное имя сервиса Swarm резолвит в один виртуальный адрес и балансирует между репликами — интерфейс видел бы каждый раз случайный узел. Префикс `tasks.` возвращает адреса всех экземпляров сразу, а именно это и нужно, чтобы собрать картину по кластеру целиком.

* **Конфликт VirtualBox и KVM.** Оба гипервизора требуют эксклюзивного доступа к аппаратной виртуализации процессора и одновременно не работают. На хостах, где KVM подгружается автоматически, модули приходится выгружать — иначе `vagrant up` не стартует. Команды собраны в `vagrant.sh`.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `docker-compose.yml` | приложение целиком: 7 микросервисов, БД, брокер, прокси |
| `nginx/nginx.conf` | обратный прокси, две точки входа |
| `Vagrantfile` | стенд под кластер: менеджер и два рабочих узла |
| `part2/Vagrantfile-p2` | отдельная машина для части 2 |
| `scripts/` | установка Docker, сборка кластера, вход узлов, сводка |
| `portainer.yml` | стек с веб-интерфейсом к кластеру |
| `postgres.sh`, `vagrant.sh` | подключение к БД и выгрузка модулей KVM |
| `main_report.md` | отчёт по трём частям с командами и скриншотами |
| `images/` | 31 скриншот работы |

Исходный код микросервисов в репозиторий не входит — он выдан курсом. Образы собраны из него и лежат в публичном реестре под тегом `:03`, поэтому развёртывание работает и без исходников.

> **Токен входа в кластер и приватные ключи не публикуются.** `scripts/swarm_token` создаётся менеджером при каждом подъёме стенда, каталог `.vagrant/` с ключами SSH к машинам исключён целиком. Пароли PostgreSQL и RabbitMQ (`postgres/postgres`, `guest/guest`) — учебные заглушки локального стенда, не образец рабочей практики.

### 📈 Итоговый результат

Приложение запускается тремя способами: одной командой через Compose на локальной машине, в отдельной виртуальной машине и стеком в кластере из трёх узлов с распределением сервисов между ними. Функциональные тесты проходят во всех трёх случаях, раскладка по узлам видна в Portainer.

Главное, что даёт эта работа дальше, — понимание, что переход от одной машины к кластеру почти не меняет описание приложения. Файл `docker-compose.yml` остаётся тем же; добавляется секция `deploy`, а `build:` заменяется на `image:`, потому что узлы кластера не собирают образы, а тянут готовые. Всё остальное — свойство среды, а не приложения.

Второе — что имена в такой среде важнее адресов. Сервисы находят друг друга по именам, прокси резолвит их через DNS Docker, Portainer собирает узлы через `tasks.`; адрес контейнера при этом живёт ровно до его пересоздания. Любая конфигурация, где адрес зафиксирован, ломается на первом же перезапуске.
