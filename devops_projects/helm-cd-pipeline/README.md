# 🚢 Непрерывная доставка в Kubernetes: Helm-чарт и одноразовый кластер в раннере

### 📌 Обзор проекта

Приложение из 7 микросервисов на Spring Boot с PostgreSQL и RabbitMQ доставляется в Kubernetes **одним Helm-чартом**. Конвейер GitHub Actions упаковывает чарт, поднимает **одноразовый кластер k3d прямо внутри раннера**, ставит туда собранный пакет и гоняет по живому приложению функциональные тесты Postman. Доставка по тегу публикует чарт в реестр и проверяет уже выложенный артефакт.

Смысл не в том, чтобы «задеплоить». Смысл в том, что через все стадии едет **один и тот же артефакт**: пакет, собранный стадией сборки, ставится в тестовом прогоне, он же уходит в реестр, и из реестра же он разворачивается на проверку доставки. Проверяется не рендер шаблонов и не «джоба стала зелёной», а работающее приложение, отвечающее по HTTP.

Второй сюжет — цена ложно-зелёного результата. Чарт был перенесён из предыдущего проекта в рабочем, как казалось, состоянии. При первой же установке в чистый namespace выяснилось, что `helm --wait` вообще не ждёт: установка отчитывалась `deployed` за 46 секунд, когда восемь подов из девяти ещё не были готовы. Разбор этого и ещё восьми дефектов — основное содержание [отчёта](main_report.md).

### 🏗 Как устроен конвейер

```
   push в feature_*                         push тега helm-cd-v*
         │                                            │
         ▼                                            ▼
 ┌───────────────────┐                    ┌───────────────────────┐
 │  build            │                    │  staging              │
 │                   │                    │                       │
 │ hadolint ×7       │                    │  ⏸ ожидание           │
 │ shellcheck        │                    │    подтверждения      │
 │ helm lint         │                    │    человеком          │
 │ рендер+kubeconform│                    │         │             │
 │ helm package      │                    │         ▼             │
 └────────┬──────────┘                    │ сверка тега с         │
          │ артефакт                      │   Chart.yaml          │
          │ myapp-0.4.1.tgz               │ helm push → GHCR      │
          ▼                               │ GitHub Release        │
 ┌───────────────────┐                    │ установка ИЗ реестра  │
 │  test             │                    │ newman                │
 │                   │                    └───────────────────────┘
 │ k3d cluster create│
 │ image import ×7   │       секреты: эфемерная пара │ постоянная пара
 │ ingress-nginx     │       openssl genpkey         │ из защищённого
 │ openssl genpkey   │       живёт минуты            │ окружения
 │ helm install .tgz │
 │ newman 6/6        │
 │ kubectl top       │
 └───────────────────┘
```

Ветка `feature_*` и тег — не украшение, а два разных класса событий: на ветке чарт **проверяется**, по тегу — **выпускается**. Поэтому у них разные права, разные источники секретов и разное отношение к ручному подтверждению.

Результат выпуска лежит в открытом реестре и забирается без учётных данных:

```bash
helm pull oci://ghcr.io/sher2yja/charts/myapp --version 0.4.1
```

Дайджест скачанного пакета совпадает с тем, что напечатала джоба при публикации, — `sha256:c28cddb0…d43edd`. Это и есть смысл последнего шага стадии `staging`: она ставит в свежий кластер не каталог из репозитория, а ровно тот артефакт, который получит любой другой потребитель.

### 🧩 Что разворачивает чарт

```
namespace: staging
                                    ┌──────────────┐
   Ingress (nginx)                   │  rabbitmq    │
   ├── /api/v1/auth    ──► session-svc:8081         │
   └── /api/v1/gateway ──► gateway-svc:8087         │
                              │                     │
                              ├──► hotel-svc:8082    │
                              ├──► booking-svc:8083 ─┤ очередь
                              ├──► payment-svc:8084  │
                              ├──► loyalty-svc:8085  │
                              └──► report-svc:8086 ──┘
                                        │
                              ┌─────────┴──────────┐
                              │  database (Postgres)│
                              │  PVC 2Gi, 6 баз     │
                              └─────────────────────┘

   ConfigMap environments   общие переменные, адреса сервисов, версия
   ConfigMap database-script init.sql, собирается из списка баз в values
   Secret    svc-secrets    пароли и пара ключей для подписи JWT
```

Порядок запуска держится не на удаче: у каждого образа в `CMD` стоит цепочка `wait-for-it`, а у каждого пода — `startupProbe`. `gateway-service` ждёт все шесть сервисов, `booking-service` — четыре и брокер.

### 🔑 Ключевые решения

**Артефакт стадии сборки — упакованный чарт.** Тестовый прогон скачивает `.tgz` и ставит именно его, а не каталог из репозитория. Иначе стадии проверяли бы разные вещи, и расхождение между «собрали» и «поставили» вылезло бы уже в доставке.

**`maxUnavailable: 0`, иначе `helm --wait` бессмыслен.** Helm считает Deployment готовым по условию `readyReplicas >= replicas - maxUnavailable`. При одной реплике и `maxUnavailable: 1` правая часть равна нулю — условие выполняется мгновенно, ждать нечего. Настраивать пробы при этом можно было сколько угодно: ожидание отключала стратегия обновления, а не отсутствие проб.

**`startupProbe` вместо `initialDelaySeconds`.** Разброс времени старта — от 25 секунд у `session-service` до четырёх-пяти минут у `gateway-service`, который проходит семь последовательных `wait-for-it`. Любая единая задержка либо убивала бы gateway liveness-пробой, либо на минуты замедляла перезапуск остальных.

**Шаблон Secret с `required`.** Раньше секрет заводился отдельной командой перед установкой, и забытый шаг выглядел как девять подов в `CrashLoopBackOff` и падение по таймауту, причём настоящая причина находилась только в `kubectl describe`. Теперь установка падает на шаблоне, за секунду и с текстом, где написано, что именно не передано.

**Два файла workflow, а не один.** Репозиторий общий на несколько проектов, поэтому path-фильтр обязателен. Но `paths` вместе с `tags` в одном `on.push` работает непредсказуемо: при появлении нового ref'а diff считать не от чего. Доставка вынесена в отдельный файл, где адресацию проекту берёт на себя префикс тега.

**`k3d image import` вместо загрузки образов подами.** Анонимный лимит Docker Hub — сто обращений за шесть часов на адрес, а раннеры GitHub сидят за общими адресами. Образы тянет хост (с учётными данными, если они заданы) и импортирует в containerd узла; `imagePullSecret` внутри кластера не нужен вовсе, а прогон становится детерминированным.

**`admissionWebhooks` у ingress-nginx выключены в CI и включены на стенде.** Вебхук начинает принимать соединения на пару секунд позже, чем под становится `Ready`, и установка чарта с объектом Ingress падает с `failed calling webhook`. В одноразовом кластере валидировать чужие Ingress нечем и незачем; на стенде, который живёт долго, вебхук приносит пользу и остаётся.

**Одно значение секрета — три источника.** Пара ключей в тестовом прогоне генерируется на месте и живёт минуты; в доставке приходит из секретов защищённого окружения, доступных только после подтверждения человеком; на стенде читается файлом из каталога вне репозитория. Чарт при этом один и тот же.

**`-XX:TieredStopAtLevel=1` только в CI.** Семь JVM стартуют одновременно на четырёх ядрах раннера. Отключение компилятора C2 срезает старт заметно, а пиковая производительность на шести тестовых запросах не нужна. (`-noverify` для этого не подходит — опция удалена в Java 13, а шесть образов из семи работают на 17.)

**Контрольная сумма секрета в шаблоне пода.** Без неё `helm upgrade` с новой парой ключей отрабатывает успешно и не меняет ничего: переменные из `secretKeyRef` подставляются при создании пода, а раз шаблон пода не изменился, Deployment не перекатывается. Ротация секрета молча не происходит.

**Мониторинг — подчарт с `condition`, а не отдельный релиз.** Наблюдать без приложения нечего, поэтому жизненный цикл у них общий; но состав объектов совершенно другой, и держать их вперемешку значит каждый раз разбираться, к чему относится очередной ConfigMap. По умолчанию выключен: чарт приложения обязан ставиться сам по себе.

**Конфигурации Prometheus, Loki и Alertmanager — плоские файлы, а не шаблоны Helm.** В них есть выражения в двойных фигурных скобках, но принадлежат они Prometheus, Alertmanager и LogQL. Пропустить такой файл через `tpl` — значит отдать их движку Helm, который упадёт на первом же `$labels`. Параметризация делается через `replace` по сентинелу, и побочная выгода крупнее самого правила: файлы остаются самостоятельными, и `promtool` проверяет их до всякого Helm — эта проверка встроена в стадию сборки.

**Цели Prometheus отбираются по аннотациям пода, а не по списку имён.** Адрес пода меняется при каждом обновлении, а при `replicas > 1` DNS-имя сервиса отдало бы один случайный под из нескольких, и метрики остальных потерялись бы молча. С аннотациями восьмой сервис попадёт в мониторинг, стоит их проставить, — без единой правки конфигурации Prometheus.

**uid источников данных в Grafana заданы явно.** Иначе Grafana генерирует их случайно при первом старте, а в любом выгруженном из интерфейса дашборде uid зашит — панели показывают «Datasource not found» при полностью исправных Prometheus и Loki. Это самая частая причина, по которой дашборд не переносится между установками.

### 🙈 Чего в папке нет и почему

**Исходников Java нет.** Опубликованы только Dockerfile'ы и `wait-for-it.sh` — то, что относится к сборке и доставке. Готовые образы лежат в публичном реестре `sherryja/<сервис>:<тег>`, чарт тянет их оттуда, поэтому развернуть проект можно, ничего не собирая.

Из этого следует и то, чем занята стадия `build`: собирать здесь нечего, кроме самого артефакта доставки. Она упаковывает чарт, проверяет Dockerfile'ы и скрипты линтерами, рендерит манифесты и валидирует их по схемам Kubernetes. Модульные тесты приложения живут там же, где его исходники.

> Учётные данные в коллекции Postman (`User:qwerty`) — заглушки из начальных данных базы. Стенд демонстрационный, настоящих учётных данных в нём нет.

> Пара ключей RSA в тестовом прогоне генерируется заново на каждый запуск и умирает вместе с кластером. В репозитории нет ни ключей, ни паролей — только шаблон с командами генерации.

### 📈 Итоговый результат

Замеры с одноразового кластера (одна нода, 4 vCPU):

```
создание кластера k3d           23 с
импорт семи образов             29 с
ingress-nginx                   23 с
helm upgrade --install --wait   1 мин 13 с  →  15/15 подов 1/1 Running
newman                          6 запросов, 6 проверок, 0 падений
```

Пятнадцать, а не девять: в CI мониторинг включён (`monitoring.enabled: true` в `values-ci.yaml`), и к девяти подам приложения добавляются Prometheus, Alertmanager, Loki, Grafana, Promtail и node-exporter. По умолчанию подчарт выключен, и релиз — ровно девять подов.

Потребление памяти снято `kubectl top pods` на обеих площадках, а не прикинуто. По стенду два замера — на покое и сразу после прогона функциональных тестов:

| Сервис | стенд, покой | стенд, пик | раннер |
|---|---|---|---|
| booking | 250 Ми | 277 Ми | 242 Ми |
| session | 183 Ми | 183 Ми | 206 Ми |
| loyalty | 172 Ми | 174 Ми | 189 Ми |
| hotel | 167 Ми | 167 Ми | 200 Ми |
| payment | 165 Ми | 167 Ми | 199 Ми |
| report | 156 Ми | 158 Ми | 181 Ми |
| rabbitmq | 120 Ми | 122 Ми | 138 Ми |
| gateway | 98 Ми | 98 Ми | 120 Ми |
| postgres | 72 Ми | 73 Ми | 62 Ми |
| **итого** | **1383 Ми** | **1419 Ми** | **~1,54 ГБ** |

Пик даёт только `booking` — он один выполняет транзакцию бронирования; остальные под нагрузкой не отличаются от покоя больше чем на пару мегабайт. Отсюда и `requests`: 256 Ми выбраны по нему, на покое он занимает 250 Ми, то есть request попадает почти ровно в его полку. Занижать до 192 Ми — размера кучи из `-Xmx192m` — нельзя: планировщик недосчитывал бы память примерно на четверть и поставил бы на узел больше подов, чем тот выдержит.

Главный вывод по итогу — про доверие к зелёному статусу. Пока `maxUnavailable` равнялся единице, `helm --wait` возвращал успех, не дожидаясь ни одного готового пода, и это компенсировалось скриптом, который искал в логах строку `Started ...Application in`. Скрипт работал и создавал ощущение, что всё под контролем. Убрав одну цифру в стратегии обновления, конвейер избавился не от строчки в скрипте, а от целого класса прогонов, которые сообщали об успехе раньше, чем он наступал.
