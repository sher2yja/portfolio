# 🐳 Docker: свой образ с nginx и FastCGI-приложением

### 📌 Обзор проекта

Путь от готового образа из реестра до собственного, собранного с нуля и разнесённого на два контейнера. По дороге — мини веб-сервер на C, работающий по протоколу **FastCGI**, проверка образа статическим анализатором **Dockle** и сборка связки через **Docker Compose**.

Приложение намеренно простое: оно отдаёт одну строку. Смысл работы не в нём, а в упаковке — исходник `server.c` не менялся ни разу за все шесть частей, менялся только способ его доставки и запуска.

### 🏗 Как менялась упаковка

```
   ч.1–2  готовый образ nginx из реестра
          run · inspect · exec · cp · export/import · rmi
                          │
                          ▼
   ч.3    ┌─ хост ──────────────────────────────────┐
          │  nginx :81  ──fastcgi──►  server :8080  │
          │                          (gcc + spawn)  │
          └─────────────────────────────────────────┘
                          │  та же схема, но внутри образа
                          ▼
   ч.4    ┌─ контейнер ─────────────────────────────┐
          │  nginx :81  ──fastcgi──►  server :8080  │
          │  FROM nginx:latest · root               │
          └─────────────────────────────────────────┘
                          │  Dockle: 2 ошибки, 2 предупреждения
                          ▼
   ч.5    ┌─ контейнер ─────────────────────────────┐
          │  nginx:1.24.0 · без кеша apt            │
          │  пользователь sc21d05, не root          │
          └─────────────────────────────────────────┘
                          │  разделение ответственности
                          ▼
   ч.6    ┌─ nginx-proxy ───┐      ┌─ app ──────────┐
          │ nginx:1.24.0    │─────►│ server :81     │
          │ :8080 ← :80     │ fcgi │ свой образ     │
          └─────────────────┘      └────────────────┘
                   сеть internal-network (bridge)
```

Наружу в финальной схеме опубликован только порт прокси. Приложение доступно лишь изнутри сети — в этом и смысл разделения.

### 🚀 Ключевые решения

* **Почему FastCGI, а не CGI.** Обычная программа CGI запускается заново на каждый запрос и платит за это временем старта процесса. FastCGI поднимает процесс один раз, дальше он в цикле принимает запросы: `FCGI_Accept()` блокируется до следующего обращения. nginx исполнять программы не умеет вовсе — он умеет передать запрос постороннему процессу и вернуть клиенту его ответ.

* **Порядок процессов в `ENTRYPOINT` определяет жизнь контейнера.** Приложение уходит в фон, nginx остаётся на переднем плане с `daemon off`. Контейнер живёт ровно столько, сколько работает процесс с PID 1: поставь на передний план приложение — и остановка nginx осталась бы незамеченной, а сам nginx без `daemon off` ушёл бы в фон, что для контейнера означает немедленное завершение.

* **Очистка кеша apt обязана быть в том же слое, что и установка.** Отдельной инструкцией `rm -rf /var/lib/apt/lists/*` ничего не даёт: удалённое остаётся в предыдущем слое и продолжает занимать место в образе. Слои неизменяемы, и удаление в следующем слое лишь скрывает файлы, а не убирает их.

* **`latest` ломает воспроизводимость.** Тег указывает каждый раз на разное содержимое, поэтому сборка одного и того же `dockerfile` через месяц может дать другой результат. Замена на `nginx:1.24.0` — первое, что требует Dockle.

* **Статическая проверка образа не заменяет запуск.** Самое полезное наблюдение всей работы. Образ части 5 проходит Dockle, но **контейнер из него не стартует**: после перехода на непривилегированного пользователя nginx не может записать pid-файл в `/var/run`, который принадлежит root. Dockle разбирает слои образа и о поведении при запуске ничего не знает. Разбор и решение — в [отчёте](./main_report.md#часть-5-проверка-образа-через-dockle).

* **Смена адреса при разделении на контейнеры.** Пока nginx и приложение жили вместе, хватало `fastcgi_pass 127.0.0.1:8080`. После разнесения нужны два изменения сразу: `fastcgi_pass app:81` — обращение по имени сервиса, которое резолвит встроенный DNS Docker, и флаг `-a 0.0.0.0` у `spawn-fcgi`, иначе приложение слушает только петлевой интерфейс и запрос из соседнего контейнера до него не дойдёт.

Части 1 и 2 своего кода не содержат — это операции с готовым образом через командную строку Docker; они разобраны в отчёте.

Каталог `myfirstdocker/`, видимый на скриншотах, при переносе схлопнут: файлы лежат прямо в папке части, и `docker build ./04` работает из корня проекта.

> **Часть 5 приведена в рабочее состояние.** В сданной версии образ собирался и проходил Dockle, но контейнер падал при старте. Добавлена одна строка `pid /tmp/nginx.pid;`; исходная ошибка и её причина описаны в отчёте. Часть 6 оставлена как сдана — там работа от root, и это отмечено отдельно.

### 📈 Итоговый результат

Все четыре части с кодом собраны и проверены запуском: `server.c` компилируется, образы частей 4 и 5 поднимаются и отдают страницу, связка части 6 работает через прокси. Образ части 5 запускается от пользователя `sc21d05`, а не от root.

Главный вывод — про границу применимости инструментов проверки. Dockle честно делает то, что умеет: разбирает слои образа и сверяет их с набором практик. Он не запускает контейнер и в принципе не может заметить, что выданных пользователю прав не хватает для старта. Зелёный отчёт анализатора означает «в образе нет известных признаков плохой практики», а не «это работает».

Второй вывод — про стоимость разделения. Переход от одного контейнера к двум выглядит как перенос строк из `dockerfile` в `docker-compose.yml`, но требует изменений в трёх местах сразу: адрес в конфигурации nginx, интерфейс прослушивания у приложения и публикация портов. Пропуск любого из трёх даёт связку, которая собирается, запускается и не работает.
