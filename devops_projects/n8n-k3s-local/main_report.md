# n8n в локальном кластере k3s: отчёт

## Границы работы

Это воспроизводимый локальный стенд на VM приложения и отдельной runner-VM, а не публичный сервис. Он демонстрирует путь от подготовки кластера до восстановления workflow с сохранённым доступом к PostgreSQL. GitHub Actions согласован вместо GitLab CI; build, test, автоматический staging и ручной production проверены.

## 1. Подготовка стенда

`Vagrantfile` создаёт Ubuntu 24.04 с 4 vCPU и 6 ГБ RAM для двух окружений. `ansible/site.yml` устанавливает k3s `v1.35.8+k3s1` и отключает встроенный Traefik. Повторный `vagrant provision`, запущенный из этой папки портфолио на существующей VM, завершился с `changed=0` (7 задач `ok`, 2 пропущены). Затем из этой же папки создана **новая** VM: Ansible выполнил 9 задач без ошибок, узел k3s перешёл в `Ready`. Начальная конфигурация была 2 vCPU/4 ГБ; после добавления production лимиты увеличены без замены диска VM.

Отдельно проверен путь **из свежего публичного Git-клона** коммита `5c99ee6`: новая VM получила 4 vCPU/6 ГБ, Ansible завершился с `failed=0`, `bash scripts/init-local-env.sh` создал одноразовый Secret, `bash scripts/deploy-local-helm.sh` установил ревизию 1 в пустой namespace. Все пять Pod стали готовы, `/healthz` ответил `{"status":"ok"}`. Повторный Ansible-прогон дал `changed=0`. Тестовая VM удалена, одноразовый клон перемещён в корзину, исходная VM запущена снова; staging и production после запуска ответили `{"status":"ok"}`. Это проверяет публичные инструкции на чистой машине, но не повторяет регистрацию runner без GitHub-токена.

```bash
bash scripts/init-local-env.sh
vagrant up --provider=libvirt
vagrant provision
vagrant ssh -c 'sudo k3s kubectl get nodes'
```

Скрипт инициализации создаёт `.env` с ограниченными правами и не перезаписывает существующий. Значения секретов в публикацию не входят.

## 2. Режим очередей и Kubernetes

В `experiments/` опробованы одиночный n8n и queue-mode Compose. Для k3s отдельно подготовлены обычные манифесты и Helm-чарт. Main обслуживает редактор, webhook принимает вызовы, worker выполняет задания; PostgreSQL хранит состояние, Redis обеспечивает очередь. Встроенный редактор n8n — интерфейс пользователя, отдельный frontend не нужен.

```bash
bash scripts/deploy-local-k8s.sh
bash scripts/vm-kubectl.sh -n do14 get pods
bash scripts/deploy-local-helm.sh
bash scripts/vm-kubectl.sh -n do14-helm get pods
```

Обе установки проверены на локальной VM. Дополнительно Helm развёрнут на новой VM из этой папки: main, webhook, worker, PostgreSQL и Redis стали `Running`, сервис main ответил `{"status":"ok"}` на `/healthz`. Чарт требует уже существующий Kubernetes Secret и не создаёт его из шаблона. Подробный контракт перечислен в [docs/contract.md](docs/contract.md).

Собственный `Dockerfile` собран локально с тегом `do14-n8n:portfolio-verify`. Образ передан в containerd VM через `docker save | vagrant ssh -c 'sudo k3s ctr images import -'`, без Docker Hub и другого внешнего реестра. Helm upgrade переключил все три роли на этот тег; все Deployment стали доступны, `/healthz` снова ответил `{"status":"ok"}`, а диагностическая команда образа подтвердила доступность сервиса. Для повторения опыта с локальным тегом:

```bash
docker build -t do14-n8n:local .
set -o pipefail
docker save do14-n8n:local | vagrant ssh -c 'sudo k3s ctr images import -'
bash scripts/vm-kubectl.sh -- helm upgrade do14 chart \
  --namespace do14-helm -f chart/values-staging.yaml \
  --set existingSecret=n8n-secrets \
  --set n8n.image=do14-n8n --set n8n.imageTag=local \
  --wait --timeout 10m
```

Этот опыт проверил локальную доставку собственного образа. Позднее GitHub Actions опубликовал образ в GHCR и автоматически развернул его в staging; результаты приведены ниже.

## 3. Обновление и откат

Чистая Helm-установка подняла main, webhook, worker, PostgreSQL и Redis. Два обычных обновления прошли с `--wait`. Затем был намеренно указан отсутствующий тег образа: роли n8n получили `ErrImagePull`, а PostgreSQL и Redis остались запущены. `helm rollback --wait` вернул работающее приложение. Опыт повторён после создания credential; тестовый workflow после отката снова вернул `{"credential_ok":1}`.

## 4. Мониторинг

Prometheus собирал метрики main и webhook: обе цели отображались как `up`. Проверено наличие метрик очереди, в том числе `n8n_scaling_mode_queue_jobs_waiting` и `n8n_scaling_mode_queue_jobs_active`. Отдельные PostgreSQL exporters staging и production показали `pg_up=1` и размеры баз 16 723 091 и 16 493 715 байт. Node-exporter показал 20 009 996 288 свободных байт (61,4%) на корневом диске VM. Grafana загрузила локальный дашборд с очередью, p95 временем webhook-исполнений, долей ошибок, базами и диском. После нового тестового запроса счётчик duration вырос с 12 до 13, запрос p95 вернул 9,75 с (грубая граница histogram bucket), доля ошибок — 0. Восемь правил настроены; при остановке staging PostgreSQL одновременно сработали `PostgresUnavailable`, `N8nMainUnavailable` и `N8nWebhookUnavailable`, Telegram доставил три красных сообщения. После восстановления базы Pod стали Ready, алерты снялись и пришли три зелёных сообщения. Production при этом оставался доступен. Пороги заполнения диска и роста базы искусственно не проверялись. Prometheus хранит данные в PVC `prometheus-data`; после смены стратегии Deployment на `Recreate` проверен успешный перезапуск и доступность запроса к метрикам. Долгосрочное хранение и восстановление самого PVC не испытывались.

Нагрузочный workflow с трёхсекундной задачей на worker был вызван 50 раз параллельно. Все 50 webhook-запросов вернули HTTP 200. Во время опыта main показал 15 ожидающих и 5 активных заданий; после завершения — 0 и 0. Prometheus сохранил пик `max_over_time(n8n_scaling_mode_queue_jobs_waiting[30m]) = 15`, текущее значение — `0`. Счётчик завершений после рестарта main достиг 51 (один пробный и 50 нагрузочных), ошибок — 0. Рост и рассасывание очереди подтверждены метриками, автомасштабирование не испытывалось.

Для отказного опыта нагрузочный workflow расширен параметром `delayMs` с ограничением 30 секунд. Мягкое удаление worker Pod при десяти 15-секундных задачах не прервало их: все HTTP 200. Принудительное удаление Pod при `active=1` во время одной 30-секундной задачи дало HTTP 500 через 102 секунды; execution 170 завершился `error` из-за превышения попыток обработки, счётчик failed стал 1. Сработал алерт `N8nExecutionFailures` и дошло красное Telegram-сообщение. Deployment создал новый worker, следующий запрос ответил HTTP 200, очередь опустела. Гарантированное повторное выполнение прерванной задачи этим опытом не доказано.

В production n8n опубликован workflow `DO14 Telegram alerts`. Он опрашивает Prometheus раз в минуту и хранит состояние алертов в отдельной таблице PostgreSQL. Первая реализация на workflow static data прислала два одинаковых красных сообщения; её заменили атомарным переходом состояния в БД. При повторной остановке staging main владелец получил одно красное сообщение, в двух следующих циклах повтора не было. После восстановления main и ответа `/healthz` пришло одно зелёное сообщение; SQL-строка перешла в `firing=false`. Это проверяет фактическую доставку и устранение дублей. Токен, использованный для опыта, ещё нужно отозвать и заменить в credential. Секретов в JSON и Git нет.

Дополнительно активированы `DO14 cluster summary` (утренняя сводка в Telegram) и `DO14 CI failure watch` (наблюдение за GitHub Actions). На 25.09 production-БД показывает `active=true` у всех трёх сценариев; ручной запуск сводки доставил сообщение владельцу, CI-наблюдатель имеет 14 успешных запусков по расписанию после двух ошибок отдельных запусков. Фактическое сообщение о новой упавшей CI-run после активации ещё не подтверждено, как и недельный интервал полезных уведомлений без ручного вызова.

```bash
bash scripts/vm-kubectl.sh apply -f monitoring/local.yaml
bash scripts/vm-kubectl.sh -n do14-monitoring port-forward service/grafana 3000:3000
```

## 5. Резервная копия и восстановление

`scripts/backup-local.sh` сохраняет дамп PostgreSQL, фактически применённые Helm values с SHA образа и выбранный `.env` с ключом шифрования; контрольные суммы позволяют выявить повреждение файлов. `scripts/restore-local.sh` принимает новый namespace и не перезаписывает исходный. В тесте staging дамп и ключ восстановлены в `do14-restore-credential`; workflow с PostgreSQL credential после этого выполнил `SELECT 1 AS credential_ok` и вернул `{"credential_ok":1}`. Это проверяет пригодность сохранённого доступа, а не только наличие таблиц.

```bash
bash scripts/backup-local.sh
bash scripts/restore-local.sh backups/<имя-копии> do14-restore-test
bash scripts/backup-local.sh backups/production-copy do14-production .env.production
bash scripts/restore-local.sh backups/production-copy do14-production-restore
```

Ежедневный пользовательский systemd-таймер в 03:00 сохраняет production-копию вне VM, в закрытый каталог хостового ПК. Первый ручной запуск сервиса создал дамп, ключ и Helm values; все три контрольные суммы совпали. Еженедельный таймер назначен на воскресенье 04:00: ручной запуск проверки восстановил последнюю копию во временный PostgreSQL 17.6 и нашёл 142 таблицы и 2 credentials. Таймеры догоняют пропущенный запуск после входа в систему. Дополнительно копия `20260925T154851Z` зашифрована GPG AES-256 на USB-носителе. Проверка расшифровки показала четыре файла, а после извлечения во временный закрытый каталог `sha256sum -c` подтвердил дамп, ключ и values; временные открытые файлы удалены. Это ручной снимок, не автоматическая ротация на USB и не полная репетиция восстановления после потери ПК.

Владелец согласовал еженедельный host-таймер вместо первоначально планировавшегося workflow внутри n8n: восстановление дампа должно выполняться и при отказе n8n. После настройки Telegram создана локальная копия `20260925T170609Z`; все три контрольные суммы совпали. Позднее создана новая production-копия `20260925T181958Z`, и её три файла вновь прошли SHA-256. Она зашифрована отдельным архивом на той же USB-флешке; владелец проверил расшифровку, распаковку во временный закрытый каталог и три контрольные суммы `OK`. Архив синхронизирован с накопителем. Полное развёртывание приложения именно из USB-архива после потери ПК не проверялось.

Host-playbook `ansible/host.yml` применяет мониторинг и подключает оба таймера после создания namespace и Secret. Первый проверенный прогон завершился с `changed=3`, повторный — с `changed=0`. Копия сначала создаётся во временном каталоге, проверяется по SHA-256 и только затем становится доступной как завершённая; после успешного создания остаются 14 последних проверенных копий.

## 6. Локальный runner и границы проверки

Создана отдельная Ubuntu VM `do14-runner` (2 vCPU, 2 ГБ RAM), без Vagrant shared folder. GitHub API показывает runner `online` с label `do14-deploy`. Внутри VM `kubectl auth can-i` вернул `yes` для Deployment в `do14-helm` и `do14-production`, `no` для Secrets в `kube-system` и создания Namespace.

Реальный workflow [do14-n8n](../../.github/workflows/do14-n8n.yml) на коммите `7066ec56` собрал образ из базового `docker.io/n8nio/n8n:2.40.6`, опубликовал его в GHCR и проверил чарт. Первый staging-job упал, потому что ограниченной роли не хватало чтения ReplicaSet; рабочая ревизия 10 восстановлена, затем добавлены только `get/list/watch` для ReplicaSet в обоих namespace. Повторный staging-job [завершился успешно](https://github.com/sher2yja/portfolio/actions/runs/36134534960), все пять Pod стали `Running`, три роли n8n перешли на `ghcr.io/sher2yja/do14-n8n:7066ec56f9dcf0cbeb84fa78e4494341b12cf1d3`. После деплоя `/healthz` вернул `{"status":"ok"}`, а тестовый workflow с сохранённым доступом — `{"credential_ok":1}`. Кластер скачал пакет GHCR без pull-secret; ручная смена видимости не потребовалась. Следующий [push-run `5c99ee6`](https://github.com/sher2yja/portfolio/actions/runs/36137915042) также прошёл build, test и автоматический staging; все пять Pod обновились и оба окружения ответили `{"status":"ok"}`.

Первый production-job был отменён из-за `Insufficient memory`: VM расширена с 4 до 6 ГБ RAM и с 2 до 4 vCPU. После остановки старого тестового namespace нагрузка стабилизировалась. Повторный [production workflow](https://github.com/sher2yja/portfolio/actions/runs/36136805996) установил отдельный Helm-релиз `do14` в `do14-production`; все пять Pod стали готовы, `/healthz` ответил `{"status":"ok"}`, staging остался доступен. Production использует отдельные Secret и PVC. Его дамп, ключ и реальные Helm values сохранены с контрольными суммами, восстановлены в `do14-production-restore` и дали 142 таблицы, тот же ключ и SHA образа, все пять Pod `Running` и ответ `/healthz`. Тестовый namespace после проверки масштабирован до нуля, PVC и Secret сохранены.

Коммит `6402976` прошёл [build, test и автоматический staging](https://github.com/sher2yja/portfolio/actions/runs/36165862180), затем по отдельному ручному запуску — [build, test и production](https://github.com/sher2yja/portfolio/actions/runs/36166630822). После production-деплоя main, webhook и worker стали готовы; ручной запуск `DO14 cluster summary` завершился успешно, включая узел Telegram с сохранённым credential. Красные алерты о недоступности staging main и webhook пришли в 19:18, во время staging-job (19:16–19:20); оба снялись в 19:21. Production-job начался только в 19:23, поэтому эти алерты нельзя приписать production-деплою. После восстановления Prometheus показывал все scrape-цели `up`.

В изолированном `do14-restore-credential` проверен частичный опыт с несовпадающим ключом: до изменения тестовый webhook с PostgreSQL credential вернул HTTP 200 и `{"credential_ok":1}`. Только тестовый worker временно получил другой `N8N_ENCRYPTION_KEY`; тот же запрос не завершился за 90 секунд. После возврата исходного Secret запрос вновь вернул HTTP 200 и `{"credential_ok":1}`. Прямое сообщение об ошибке расшифровки не зафиксировано, поэтому этот опыт показывает нарушение обработки при разных ключах, но ещё не доказывает точную внутреннюю причину тайм-аута. Тестовый namespace снова масштабирован до нуля, временный Secret удалён.

В том же тестовом namespace проверен одиночный отказ Redis: до остановки `POST /webhook/do14-smoke` вернул HTTP 200 и `processedBy=worker`; после масштабирования Redis до нуля тот же вызов завершился `fetch failed`; после восстановления Redis до одной готовой реплики вновь получен HTTP 200. Все тестовые компоненты затем возвращены к `0/0`. Это подтверждает зависимость доставки webhook-задачи от Redis и восстановление после его возврата, но не покрывает поведение уже выполняющихся задач при отказе под нагрузкой.

Затем в тестовый namespace импортирован и опубликован `DO14 queue load test`. Контрольная 15-секундная задача вернула HTTP 200. При десяти параллельных 30-секундных запросах Redis остановлен через пять секунд: клиентский процесс оборвался с кодом 137, тестовые роли n8n перезапустились. После возврата Redis и ролей новый запрос вновь вернул HTTP 200, но через две минуты десять прерванных execution оставались в БД: пять `crashed` и пять `running`. Это не доказательство гарантированного повтора; напротив, опыт показывает, что доступность новых задач восстанавливается, а прерванные требуют отдельной диагностики. Staging и production во время опыта оставались `Running` без новых перезапусков. Тестовый namespace вновь масштабирован до нуля.

Отдельно проверена опасность генерации ключа в Helm-шаблоне. Временная копия чарта при обновлении только тестового релиза создала Secret с новым `N8N_ENCRYPTION_KEY`, сохранив прежние пароль PostgreSQL и токен runner, без смены версии n8n. Main не запустился: `Deployment key 'signing.hmac' cannot be read with this instance encryption key`. Первый `helm upgrade --atomic --wait` завершился тайм-аутом и автоматическим откатом; повторный короткий upgrade позволил зафиксировать журнал, затем ручной rollback вернул штатную ревизию. После отката credential-workflow вновь ответил HTTP 200 и `{"credential_ok":1}`. Ошибочный Secret удалён откатом, временный чарт удалён, тестовые компоненты возвращены к `0/0`. Подробность решения — в [ADR о ключе](docs/adr/0001-encryption-key.md).

## 7. Что не проверено

- VPS, публичный DNS, TLS и внешние webhook-вызовы;
- точная причина тайм-аута при несовпадающем ключе только у worker и восстановление десяти прерванных задач после отказа Redis; повторная отправка Telegram после ротации токена;
- автоматическая регистрация новой runner-VM без ручного GitHub-токена: такая автоматизация намеренно не добавлена, чтобы не хранить токен в открытом репозитории.

Команды диагностики и подробная хронология экспериментов приведены в [docs/runbook.md](docs/runbook.md). В опубликованные файлы не включены `.env`, дампы, `.vagrant/`, приватные ключи и kubeconfig.
