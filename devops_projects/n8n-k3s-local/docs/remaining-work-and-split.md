# Проект 14 (n8n): что осталось и как делим

Основа: архив n8n-k3s-local (Саня) и обязательный чек-лист проверки. Оценки часов приблизительные.

## 1. Схема деления

Доступ к GitLab (`git.21-school.ru`) у Сани будет только пару дней, у Максима — весь проект. Поэтому делим так:

- **Первая половина — Саня.** Всё, что проверяется без GitLab: образы, чарт, тесты, скрипты сборки и деплоя, манифесты Runner'а. Дни с доступом к GitLab уходят на одну задачу — проверку Runner'а в кластере (задача С1).
- **Вторая половина — Максим.** Подключение к GitLab: кластер у себя, регистрация Runner'а, `.gitlab-ci.yml`, CI-переменные, прогоны, скриншоты, сборка отчёта.

На этом держится вся схема. Вся логика CI живёт в скриптах `src/ci/*.sh`, а `.gitlab-ci.yml` их только вызывает. Саня проверяет скрипты у себя руками. Секреты скрипты берут из переменных окружения: локально это `export`, в GitLab те же имена будут CI-переменными. Максиму остаётся написать около 40 строк YAML со стадиями и правилами запуска.

Кластер переезжает на домашний ПК Максима. Это решено. Чек-лист требует, чтобы Runner работал в том же кластере, что staging и production, поэтому финальный кластер стоит там, где GitLab доступен весь проект. Хост: Ubuntu 22.04, 32 ГБ RAM, Ryzen, dual-boot с Windows. Поднимаем тот же Vagrant (libvirt) + Ansible.

Для Сани это значит, что `README.md` пишется под чистую Ubuntu 22.04, начиная с установки хостовых пакетов: libvirt, Vagrant, плагин `vagrant-libvirt`, Ansible, kubectl, Helm, Docker. Твой хост может отличаться версиями, поэтому нужны точные команды, а не «как у меня».

## 3. Контракт между половинами

Если меняешь что-то из этого списка, предупреди второго.

Структура:

```text
.gitlab-ci.yml            ← корень репозитория (пишет Максим)
src/
  dockerfiles/{main,webhook,worker,runner}/Dockerfile
  chart/
  ci/build.sh  ci/test.sh  ci/deploy.sh
  tests/n8n.postman_collection.json  tests/smoke-workflow.json
  runner/                 ← values для чарта gitlab-runner + RBAC
  ansible/  Vagrantfile
  README.md               ← как поднять кластер с нуля
  report.md
```

Переменные окружения (локально `export`, в GitLab — CI-переменные):

| Переменная | Кто задаёт | Назначение |
| --- | --- | --- |
| `REGISTRY`, `REGISTRY_USER`, `REGISTRY_PASSWORD` | В GitLab: `CI_REGISTRY*` | Куда пушить образы |
| `IMAGE_TAG` | В GitLab: `CI_COMMIT_SHORT_SHA` | Тег всех четырёх образов |
| `N8N_ENCRYPTION_KEY`, `N8N_RUNNERS_AUTH_TOKEN`, `POSTGRES_PASSWORD` | CI-переменные, masked + protected, отдельно для staging и production | Межсервисная авторизация |
| `PULL_USER`, `PULL_TOKEN` | CI-переменная (deploy token `read_registry`) | `imagePullSecret` в кластере |
| `KUBE_NAMESPACE` | Аргумент `deploy.sh` | `do14-helm` (staging) / `do14-production` |

Интерфейс скриптов:

- `ci/build.sh`: собирает и пушит `$REGISTRY/{main,webhook,worker,runner}:$IMAGE_TAG`. Код выхода ≠ 0 при любой ошибке.
- `ci/test.sh <base_url>`: импортирует и активирует тестовый workflow, запускает Newman. Выход ≠ 0, если упал хотя бы один тест.
- `ci/deploy.sh <staging|production>`: создаёт Secret и pull-secret из env (`--dry-run=client -o yaml | kubectl apply`), затем `helm upgrade --install --atomic --wait`, затем `curl /healthz`.

Внутри скриптов никаких `vagrant ssh` и `vm-kubectl.sh`: в CI их не будет. Только `docker`, `kubectl`, `helm`, `newman`, `curl`.

Имена: namespace `do14-helm` и `do14-production`, релиз `do14`, тег Runner'а `k8s`, namespace Runner'а `gitlab-runner`.

## 5. Передача (граница половин)

Созвон на 1,5–2 часа, пока Саня на связи. Порядок:

1. Максим клонирует `src/` и по `README.md` поднимает кластер у себя. Саня подсказывает, но руками делает Максим.
2. На машине Максима, только с переменными окружения: `ci/build.sh` → `ci/test.sh` → `ci/deploy.sh staging` → `ci/deploy.sh production`. Для реестра можно временно взять локальный `registry:2`.
3. Саня проходит по каждому скрипту и манифесту: что делает и зачем. На защите это объясняет Максим (пункт 2 чек-листа).
4. Саня отдаёт `NOTES.md` по С1: как Runner заработал в его кластере.

Половина Сани закрыта, если шаг 2 прошёл без правок. Всё, что после этого сломается в GitLab, — зона Максима. Саня помогает по пересланным логам.

## 7. Риски и неизвестное

- **ПК Максима как хост.** Пока ПК загружен в Windows или выключен, кластер и Runner недоступны, и пайплайн ждёт. Для прогонов и защиты ПК должен быть включён в Ubuntu. Vagrant-box Сани (`bento/ubuntu-24.04`) и плагин `vagrant-libvirt` на хосте 22.04 не проверялись. Лучше, чтобы Максим поставил хостовые пакеты по `README.md` ещё до созвона, тогда проблемы всплывут заранее.
- **Досягаемость GitLab из кластера Максима.** Проверка С1 делается у Сани. Сеть Максима может вести себя иначе. Проверить `curl -I https://git.21-school.ru` из VM в М1, до всего остального.
- **Разница «локально работает — в CI нет».** В CI скрипты выполняются в контейнере job'а, а не на хосте. В образе job'а должны быть `kubectl`, `helm`, `newman`, `curl`. Какой образ брать, Саня фиксирует в `NOTES.md` по итогам С1.
- **Доступ к кластеру из job'а.** Runner в кластере даёт job'у ServiceAccount. `kubectl` и `helm` внутри job'а должны работать от него без kubeconfig. Проверить в С1.
- **Три «микросервиса» из одного образа.** Тонкие Dockerfile'ы закрывают формальный пункт 5. Засчитает ли проверяющий роли одного приложения как «микросервисы с бизнес-логикой», гарантировать нельзя.
- **Активация workflow в n8n 2.40.** Точную команду CLI не проверяли. Если CLI не подходит, запасной вариант — REST API n8n с API-ключом (ещё одна CI-переменная).
- **Саня недоступен после передачи.** Чем подробнее `README.md` и `NOTES.md`, тем меньше Максим зависит от него.
