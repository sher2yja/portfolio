# ⚙️ GitLab CI/CD: конвейер сборки, проверки и доставки

### 📌 Обзор проекта

Конвейер непрерывной интеграции и доставки для консольной программы на C. Четыре стадии: проверка форматирования, сборка, интеграционные тесты, доставка бинарника на удалённый сервер. Каждая стадия по завершении отправляет сообщение в Telegram — независимо от того, прошла она или упала.

Работа сделана на школьном GitLab с раннером в режиме shell-исполнителя: команды выполняются прямо на машине раннера, без контейнера. Программа, которую конвейер собирает, приходит в составе задания — предмет работы здесь не она, а то, что вокруг неё.

### 🏗 Как устроен конвейер

```
               push в develop
                     │
                     ▼
       ┌─ style ─────────────────────┐
       │ clang-format -n -Werror     │  правила берутся из поставки
       │ code-samples/*.c            │  курса и кладутся рядом с кодом
       └────────────┬────────────────┘
                    ▼
       ┌─ build ─────────────────────┐
       │ make -C code-samples all    │  бинарник DO уходит в artifacts/
       │ artifacts: expire 30 дней   │  и передаётся дальше по конвейеру
       └────────────┬────────────────┘
                    ▼
       ┌─ test ──────────────────────┐  needs: style + build
       │ 4 проверки бинарника из     │  два корректных номера
       │ artifacts/, без пересборки  │  и два ошибочных ввода
       └────────────┬────────────────┘
                    ▼
       ┌─ deploy ────────────────────┐  when: manual
       │ scp artifacts/DO → сервер   │  192.168.100.12:/usr/local/bin
       └─────────────────────────────┘

  после каждой стадии, независимо от её исхода:
       after_script → scripts/tele.sh → Telegram Bot API
```

### 🚀 Ключевые решения

* **Уведомление вызывается из `after_script`, а не из `script`.** Это не стилистическая мелочь: блок `script` при падении задачи обрывается на упавшей команде, и до отправки сообщения дело не доходит — то есть не приходило бы ровно то уведомление, ради которого всё и делается. `after_script` выполняется в любом случае, а статус завершившейся задачи виден в нём через `CI_JOB_STATUS`, которого в обычном `script` ещё не существует.

* **Тесты работают с артефактом сборки, а не пересобирают программу.** Стадия `build` выгружает бинарник как артефакт, `test` его скачивает. Иначе проверялся бы не тот файл, который потом уедет на сервер, и смысл конвейера терялся бы.

* **`needs` вместо простого порядка стадий.** Тесты объявляют зависимость от `style_code` и `build_project` напрямую, и конвейер превращается из очереди в граф: стадия стартует, как только готовы обе задачи.

* **Доставка запускается кнопкой (`when: manual`).** Зелёный конвейер — основание для выкладки, но не команда к ней. Решение о том, что изменения уходят на сервер, принимает человек.

* **Каталог артефактов пересоздаётся, конфигурация линтера удаляется после проверки.** Shell-исполнитель переиспользует рабочую копию между задачами: без `rm -rf artifacts` в сборку попал бы бинарник предыдущего запуска, а оставленный `.clang-format` всплыл бы в следующей задаче.

* **Проверка «нет аргументов» обёрнута в `|| true`.** Программа в этом случае завершается с ненулевым кодом, и без обёртки задача упала бы на самой команде, не дойдя до сравнения вывода с ожидаемым — то есть корректное поведение программы выглядело бы как провал теста.

* **Секреты вынесены в переменные CI/CD.** Токен бота и chat_id задаются в Settings → CI/CD → Variables с типом Masked. Скрипт при их отсутствии не падает, а пропускает отправку и выходит с нулём: конвейер не должен зависеть от доступности мессенджера.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `.gitlab-ci.yml` | конвейер: четыре стадии, артефакты, зависимости, уведомления |
| `scripts/tele.sh` | отправка статуса в Telegram, вызывается из `after_script` каждой стадии |
| `scripts/deploy.sh` | доставка бинарника на целевой сервер по `scp` |
| `main_report.md` | отчёт: разбор стадий, логи прогонов, найденные дефекты |
| `images/` | 5 скриншотов работы конвейера |

**Чего в папке нет и почему.** Конвейер собирает и проверяет программу, которая приходит в составе задания: `code-samples/main.c`, `code-samples/Makefile` и правила форматирования `materials/linters/.clang-format`. Эти файлы выданы курсом и в публикацию не входят, поэтому запустить конвейер как есть на этом репозитории нельзя — он опубликован как результат работы, а не как готовый к запуску шаблон.

> Адрес `192.168.100.12` и пользователь `devops` — виртуальная машина учебного стенда. Доступ по ключу настроен вне репозитория, реального сервера за этим адресом нет.

> Токен бота, попавший в сданную работу в открытом виде, отозван; на скриншоте исходника он и chat_id закрашены.

### 📈 Итоговый результат

Конвейер отрабатывает целиком: стиль проверяется, программа собирается, четыре теста проходят, доставка по кнопке кладёт бинарник на сервер, в Telegram приходят сообщения со стадией, веткой и ссылкой на прогон.

Более интересна вторая половина результата — то, что видно в логах зелёного конвейера при внимательном чтении. Сборка выдаёт предупреждение компилятора о функции без явного типа возврата, но стадия стиля этого не замечает: `clang-format` проверяет форматирование, а не корректность кода, и пройденная проверка стиля ничего не говорит о том, что скажет компилятор. В одном из прогонов уведомление и вовсе завершалось с ошибкой — задача при этом оставалась зелёной, потому что GitLab не роняет её из-за `after_script`.

Вывод, который стоил больше всего: **зелёный конвейер означает «ни одна проверка не сработала», а не «проблем нет»**. Разбор обеих находок — в отчёте.
