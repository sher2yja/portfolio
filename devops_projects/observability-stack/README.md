# 📡 Мониторинг кластера Swarm: метрики, логи и оповещения

### 📌 Обзор проекта

Приложение из 7 микросервисов, развёрнутое в кластер **Docker Swarm** из трёх машин, обвязывается полным стеком мониторинга: **Prometheus** собирает метрики, **Loki** — логи, **Grafana** сводит их на дашборд, **Alertmanager** рассылает оповещения в Telegram и на почту.

Метрики берутся с трёх уровней сразу: машины отдают их через `node_exporter`, контейнеры — через `cAdvisor`, само приложение — через собственные счётчики на **Micrometer**, встроенные в код четырёх микросервисов. Отдельно написан свой экспортёр метрик кластера — без единой строки кода HTTP-сервера.

Это часть сквозной линии заданий, где одно и то же приложение разворачивается разными способами. Здесь — не про развёртывание, а про то, как увидеть, что происходит внутри уже развёрнутого.

Приложение и мониторинг разворачиваются **разными стеками, но в общую сеть**. Иначе Prometheus не смог бы обращаться к микросервисам по их именам.

### 🚀 Ключевые решения

* **Собственный экспортёр метрик без HTTP-сервера.** Количество контейнеров и образов на узле не отдаёт ни один готовый экспортёр. Писать свой сервис не понадобилось: `node_exporter` умеет подмешивать к своим метрикам содержимое файлов из каталога textfile collector. Достаточно раз в минуту по `cron` перезаписывать текстовый файл в формате экспозиции — [`scripts/swarm-metrics.sh`](./scripts/swarm-metrics.sh) занимает 20 строк на bash.

* **Запись метрик атомарна.** Файл пишется во временный и переносится через `mv`. Переименование в пределах файловой системы атомарно, поэтому `node_exporter` никогда не прочитает файл наполовину записанным. Прямая запись такую гонку допускает — при опросе раз в 15 секунд и записи раз в минуту она рано или поздно случилась бы.

* **`_total` — суффикс счётчиков, а не «всего».** Первый вариант экспортёра назывался `swarm_containers_total` и `swarm_images_total`. `promtool check metrics` на это ругается: по соглашению Prometheus `_total` закреплён за типом counter — величиной, которая только растёт. Здесь же обе метрики — gauge, они могут и убывать. Имена исправлены.

* **Загрузка процессора вычисляется, а не читается.** Готовой метрики «процент занятости» нет ни у `node_exporter`, ни у `cAdvisor`: оба отдают накопленное процессорное время счётчиком. `rate` превращает счётчик в скорость роста, а дальше — либо умножение на 100 для контейнеров, либо вычитание доли простоя из ста для узлов.

* **Проверка доступности устроена наизнанку.** Prometheus опрашивает не проверяемый адрес, а `blackbox_exporter`, передавая ему адрес параметром. Три правила `relabel_configs` в [`prometheus/prometheus.yml`](./prometheus/prometheus.yml) как раз этим и заняты. Без последнего из них Prometheus пошёл бы на google.com напрямую и получил HTML вместо метрик.

* **Узлы опрашиваются по адресам, а не по имени сервиса.** `node_exporter` запущен в режиме `global` — по экземпляру на машину. Обращение по имени сервиса Swarm балансировалось бы между ними, и Prometheus видел бы одну цель вместо трёх, потеряв разделение метрик по узлам.

* **Два способа доставки конфигурации — и это не непоследовательность.** Часть сервисов получает конфиг через `volumes`, часть — через `configs` Swarm. Bind-mount требует, чтобы файл физически лежал на узле, куда попал контейнер: для сервисов, закреплённых за менеджером, это допустимо, а для `promtail` с `mode: global` — нет. Поэтому у него, `loki` и `alertmanager` конфигурация хранится в самом Swarm и раздаётся на узлы.

* **Логи собираются без перечисления контейнеров.** `promtail` обнаруживает их сам через сокет Docker и перечитывает список каждые 5 секунд — новый контейнер попадает в сбор без правки конфигурации и перезапуска агента.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `Vagrantfile` | стенд: 3 машины, приватная сеть, установка cron для экспортёра |
| `docker-compose.yml` | стек приложения: 7 микросервисов, PostgreSQL, RabbitMQ, прокси |
| `docker-compose.monitoring.yml` | стек мониторинга: 8 сервисов |
| `docker-compose.portainer.yml` | веб-интерфейс к кластеру, для задания не обязателен |
| `prometheus/prometheus.yml` | цели опроса, связь с Alertmanager |
| `prometheus/alert.rules.yml` | 3 правила оповещений |
| `alertmanager.yml` | маршрутизация оповещений в Telegram и на почту |
| `my_template.tmpl` | оформление сообщений |
| `blackbox.yml` | модули проверки доступности |
| `loki-config.yml`, `promtail-config.yml` | хранилище логов и агент сбора |
| `nginx.conf` | обратный прокси перед приложением |
| `grafana/Grafana.json` | дашборд на 15 метрик, готов к импорту |
| `scripts/` | 10 скриптов: установка Docker, сборка кластера, развёртывание, экспортёр |
| `main_report.md` | отчёт о прогоне: команды, вывод, скриншоты |
| `images/` | 28 скриншотов работы стенда |

Исходный код микросервисов в репозиторий не входит — он выдан курсом. Собственные вставки на Micrometer показаны фрагментами в [отчёте](./main_report.md#часть-1-сбор-метрик-и-логов). Образы приложения собраны из этих исходников и лежат в публичном реестре, поэтому развёртывание работает и без них.

> **Учётные данные заменены заглушками.** Токен Telegram-бота, идентификатор чата и пароль почтового ящика в `alertmanager.yml` — фиктивные, как их получить, описано в шапке файла. Токен входа в кластер Swarm не выкладывается: он генерируется менеджером при каждом подъёме стенда. Пароли PostgreSQL и RabbitMQ (`postgres/postgres`, `guest/guest`) — учебные заглушки локального стенда, не образец рабочей практики.

### 📈 Итоговый результат

Стек работает целиком: метрики трёх уровней собираются, логи всех контейнеров доходят до Loki, дашборд отображает 15 показателей из задания, правила срабатывают и уведомления приходят обоими каналами.

Самое полезное здесь — понимание, что экспортёр метрик не обязан быть программой. Prometheus не различает, кто на другом конце: сложный сервис, который считает что-то сам, или текстовый файл в известном формате, отданный чужим экспортёром. Задача сводится к тому, чтобы величина оказалась в нужном формате по доступному адресу, и решать её стоит самым дешёвым способом из подходящих.

Второе — что почти ни одна интересная величина не читается напрямую. Занятость процессора, отставание очереди, доступность сервиса снаружи — всё это вычисляется из более простых показателей. Мониторинг держится не столько на сборе, сколько на умении задать правильный запрос к собранному.
