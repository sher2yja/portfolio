## Программа 1. Экзамен на процессах

### Что моделируется

Экзамен принимают несколько экзаменаторов **одновременно**, каждый — в своём процессе.
Студенты стоят в одной общей очереди: освободившийся экзаменатор забирает первого
из очереди. Данные читаются из трёх текстовых файлов.

| Файл | Что содержит | Формат строки |
|---|---|---|
| `examiners.txt` | экзаменаторы | имя и пол: `Степан М` |
| `students.txt` | студенты в очереди | имя и пол: `Варвара Ж` |
| `questions.txt` | банк вопросов | текст вопроса: `Там стоит стол` |

Правила задачи намеренно вероятностные:

- студенту задают три вопроса, и **ответом служит наугад выбранное слово из самого
  вопроса**. Выбор неравновероятный: мальчики тяготеют к началу фразы, девочки — к концу,
  а распределение задано законом золотого сечения;
- экзаменатор верного ответа не знает и определяет его тем же способом, но по своему полу.
  Верных вариантов может оказаться несколько: выбрав слово, он с вероятностью `1/3`
  берёт ещё одно, и так пока не остановится или не переберёт всю фразу;
- вердикт зависит от настроения: с вероятностью `1/8` экзамен не сдан независимо
  от ответов, с вероятностью `1/4` сдан независимо от ответов, в остальных случаях
  решают сами ответы — верных должно быть больше, чем неверных;
- длительность экзамена привязана к длине имени экзаменатора: имя из `N` букв даёт
  случайное время из диапазона `[N-1, N+1]` секунд;
- через 30 секунд от начала экзаменатор уходит на обед: доводит текущего студента
  до вердикта и затем от 12 до 18 секунд никого не принимает.

Пока экзамен идёт, картинка обновляется **на месте**, а не печатается новыми строками.
После окончания промежуточные таблицы заменяются итоговыми — с лучшими студентами,
лучшими экзаменаторами, списком на отчисление, лучшими вопросами и общим выводом.

### Разделение по парадигмам

Условие требует решить задачу мультипарадигмально. Это не украшение: каждый модуль
выдержан в одной парадигме, и границы между ними совпадают с границами
ответственности.

| Файл | Парадигма | За что отвечает |
|---|---|---|
| `models.py` | объектная | правила задачи: `Question`, `Person` → `Student` / `Examiner`. Ни ввода-вывода, ни процессов |
| `report.py` | функциональная | чистые функции над снимком состояния: таблицы и итоговые строки. Ни одного обращения к разделяемым объектам |
| `main.py` | процедурная | чтение файлов, запуск процессов, цикл перерисовки |

Побочный эффект деления оказался полезнее самого требования: `report.py` работает
с обычными словарями, поэтому его функции проверяются без запуска всей многопроцессной
машинерии, а `models.py` — без запуска чего бы то ни было. Все вероятностные проверки
из раздела [«Как проверялись результаты»](#как-проверялись-результаты) стали возможны
именно поэтому.

### Схема процессов

Главный процесс ничего не вычисляет. Он только берёт снимок состояния и рисует его.
Вся запись идёт из процессов экзаменаторов и только под общим замком.

```
                       главный процесс
                  +----------------------------+
                  |  каждые 0.25 с:            |
                  |    snapshot() под Lock     |
                  |    clear + печать таблиц   |
                  +-------------+--------------+
                                | только чтение
                                v
        +========================================================+
        |             Manager: разделяемое состояние             |
        |   queue[]   current[]   status{}   finished_at{}       |
        |   duration{}   examiners{}   hits{}        + Lock      |
        +========================================================+
              ^                    ^                    ^
              | запись под Lock    |                    |
     +--------+-------+   +--------+-------+   +--------+-------+
     | Process Степан |   | Process Дарья  |   | Process Михаил |
     +----------------+   +----------------+   +----------------+
```

Рабочий цикл одного экзаменатора:

```
   take_next() ------> очередь пуста? ------> выход из процесса
        |
        v
   экзамен: 3 вопроса, sleep(длительность от длины имени)
        |
        v
   finish(): статус студента, время, статистика вопросов
        |
        v
   прошло >= 30 с и обеда ещё не было?
        |                    \
       нет                    да --> sleep(12..18 с), больше обедов не будет
        |                    /
        +<------------------+
        |
        v
   назад к take_next()
```

Цикл завершается сам: как только очередь опустела, `take_next()` возвращает `None`,
процесс выходит, и главный процесс, дождавшись всех, печатает итоги.

### Разделяемое состояние

Всё общее состояние собрано в один класс `ExamState` поверх **одного** `Manager`
и **одного** `Lock`.

| Поле | Тип | Зачем |
|---|---|---|
| `queue` | list | имена студентов, ещё не взятых на экзамен |
| `current` | list | студенты, которых опрашивают прямо сейчас |
| `status` | dict | имя → `Очередь` / `Сдал` / `Провалил` |
| `finished_at` | dict | имя → момент окончания, нужен для списка на отчисление |
| `duration` | dict | имя → длительность экзамена, нужна для лучших студентов |
| `examiners` | dict | имя → кортеж `(текущий, всего, завалил, занятость, начало)` |
| `hits` | dict | текст вопроса → сколько студентов ответили верно |

Метод `snapshot()` берёт замок и возвращает **обычные** списки и словари. Благодаря
этому главный процесс всегда рисует целостный кадр: невозможно поймать состояние,
где студента уже вынули из очереди, но ещё не записали в опрашиваемые.

### Закон золотого сечения

Условие задаёт веса рекуррентно: `a = 1/Ф`, `b = (1-a)/Ф`, `c = (1-a-b)/Ф`. То есть
каждый следующий вес — это **остаток, делённый на Ф**, а последнее слово забирает всё,
что осталось. В коде это ровно один цикл:

```
остаток = 1.0
для каждого слова, кроме последнего:
    вес = остаток / Ф
    остаток -= вес
последнее слово: вес = остаток
```

Такая запись воспроизводит формулы из условия и заодно гарантирует, что сумма весов
равна единице при любом числе слов — последний вес не вычисляется, а достаётся
остатком.

| Слов | Веса |
|---|---|
| 2 | 0.6180, 0.3820 |
| 3 | 0.6180, 0.2361, 0.1459 |
| 4 | 0.6180, 0.2361, 0.0902, 0.0557 |
| 6 | 0.6180, 0.2361, 0.0902, 0.0344, 0.0132, 0.0081 |

Разница между мальчиком и девочкой — одна операция: список весов разворачивается
(`weights[::-1]`).

```
  мальчик                                девочка
  Там    ####################  0.618     Там    ###                   0.146
  стоит  #######               0.236     стоит  #######               0.236
  стол   ####                  0.146     стол   ####################  0.618
```

Тот же метод `weights_for` используют и студент, и экзаменатор: экзаменатор ищет
верные ответы по тому же закону, только по своему полу. Именно поэтому пол
экзаменатора влияет на исход — мальчик и девочка «правильными» считают разные концы
фразы.

### Три тонких места

**1. Генераторы не переживают `Manager`.** Аргументы `manager.list(...)` и
`manager.dict(...)` пиклятся и уходят в процесс менеджера. Генераторное выражение
не пиклится, и программа падает с `TypeError: cannot pickle 'generator' object`.
Поэтому передаются готовые список и словарь:

```python
self.queue = manager.list([student.name for student in students])
self.status = manager.dict({student.name: QUEUED for student in students})
```

**2. Вложенные структуры в разделяемом словаре не обновляются.** Если бы состояние
экзаменатора было списком, `state['Степан'][1] += 1` изменил бы локальную копию
в своём процессе и до менеджера не дошёл бы — молча, без ошибки. Поэтому состояние
хранится кортежем и переприсваивается целиком:

```python
self.examiners[examiner_name] = (None, state[1] + 1, ..., None)
```

**3. Студент на экзамене всё ещё числится в очереди.** Выглядит ошибкой, но так
устроен пример в условии: студент показан одновременно текущим у экзаменатора
и со статусом `Очередь`, и он же учтён в счётчике оставшихся. Значит статус меняется
в момент вердикта, а не в момент захода к экзаменатору. Порядок внутри группы —
сначала опрашиваемые, затем ждущие: именно в этом порядке они закончат.

В [кадре ниже](#фактический-прогон) это видно прямо: «Осталось в очереди: 3 из 7»,
и все три при этом сидят у экзаменаторов — ждущих не осталось ни одного.

### Допущение про «Время работы»

Условие здесь неоднозначно, и числа в его собственном примере друг другу противоречат:
у экзаменатора с именем из шести букв показаны два студента и 7.21 с работы, хотя
шесть букв дают от 5 до 7 секунд на **одного**, то есть минимум 10 секунд на двоих.

Принято толкование, согласованное с остальными столбцами: **«Время работы» — это
накопленное время, реально потраченное на приём экзаменов**. Счётчик растёт во время
опроса, замирает на обеде и после того, как экзаменатор закончил. В коде это
накопленная занятость плюс незавершённый экзамен:

```python
return busy + (now - since if since is not None else 0.0)
```

Допущение выбрано так, чтобы столбцы сходились между собой, и проверено отдельно:
на прогоне с обедом счётчик действительно замирает на перерыв и продолжает расти после.

### Фактический прогон

Семь студентов, три экзаменатора, банк из четырёх вопросов. Живой кадр на 8.97 секунде:

```
+------------+----------+
| Студент    |  Статус  |
+------------+----------+
| Екатерина  | Очередь  |
| Александра | Очередь  |
| Алексей    | Очередь  |
| Петр       |   Сдал   |
| Сергей     |   Сдал   |
| Варвара    |   Сдал   |
| Иван       | Провалил |
+------------+----------+

+-------------+-----------------+-----------------+---------+--------------+
| Экзаменатор | Текущий студент | Всего студентов | Завалил | Время работы |
+-------------+-----------------+-----------------+---------+--------------+
| Степан      | Александра      |        1        |    0    |     8.96     |
| Дарья       | Алексей         |        2        |    1    |     8.96     |
| Михаил      | Екатерина       |        1        |    0    |     8.96     |
+-------------+-----------------+-----------------+---------+--------------+

Осталось в очереди: 3 из 7
Время с момента начала экзамена: 8.97
```

Кадр показывает сразу три вещи. Экзаменаторы работают параллельно — у каждого свой
студент. «Время работы» у всех троих одинаковое, потому что никто ещё не простаивал:
как только один студент закончил, сразу зашёл следующий. И трое опрашиваемых
по-прежнему числятся в очереди — то самое поведение из условия.

Итог того же прогона:

```
+------------+----------+
| Студент    |  Статус  |
+------------+----------+
| Петр       |   Сдал   |
| Сергей     |   Сдал   |
| Варвара    |   Сдал   |
| Иван       | Провалил |
| Екатерина  | Провалил |
| Александра | Провалил |
| Алексей    | Провалил |
+------------+----------+

+-------------+-----------------+---------+--------------+
| Экзаменатор | Всего студентов | Завалил | Время работы |
+-------------+-----------------+---------+--------------+
| Степан      |        2        |    1    |    11.33     |
| Дарья       |        3        |    2    |    13.20     |
| Михаил      |        2        |    1    |    12.05     |
+-------------+-----------------+---------+--------------+

Время с момента начала экзамена и до момента и его завершения: 13.33
Имена лучших студентов: Варвара
Имена лучших экзаменаторов: Степан, Михаил
Имена студентов, которых после экзамена отчислят: Иван
Лучшие вопросы: Программирование интересное занятие
Вывод: экзамен не удался
```

Формулировка последней строки со «сдал более 85%» на семи студентах оказывается
жёстче, чем кажется: `6/7 = 85.7%` проходит, `5/7 = 71.4%` уже нет. То есть удачным
экзамен считается, только если провалился **не более одного** студента из семи.
На соседнем прогоне сдали шестеро — и вывод был «экзамен удался». Здесь сдали трое,
и вывод обратный. Обе ветки видел живьём.

Сходимость столбцов проверяется по самому кадру: `2 + 3 + 2 = 7` студентов, столько же
строк в таблице; `1 + 2 + 1 = 4` заваленных, столько же строк со статусом `Провалил`.

## Программа 2. Асинхронное скачивание изображений

Программа спрашивает, куда сохранять, а затем принимает ссылки одну за другой.
Ключевое требование: следующую ссылку спрашивают **сразу**, не дожидаясь окончания
предыдущей загрузки. Ввод завершается пустой строкой; если к этому моменту скачано
не всё, программа сообщает об этом и дожидается остатка. Ни одна ошибка не должна
завершать работу — всё копится до итоговой таблицы.

### Почему ввод уходит в отдельный поток

Обычный `input()` блокирует цикл событий целиком. Пока пользователь думает над
следующей ссылкой, ни одна загрузка не сдвинулась бы — и вся асинхронность оказалась бы
декоративной. Поэтому ввод выполняется через `asyncio.to_thread`: ожидание клавиатуры
переезжает в отдельный поток, а цикл событий остаётся свободным.

```
   поток ввода (asyncio.to_thread)          цикл событий asyncio
   +-----------------------------+          +------------------------+
   | input("Ссылка: ")           |  create  |  download(url1) ...    |
   |   |                         | -------> |  download(url2) ...    |
   |   v                         |   task   |  download(url3) ...    |
   | пустая строка -> стоп       |          +-----------+------------+
   +--------------+--------------+                      |
                  |                                     |
                  +--------> gather(все задачи) <-------+
                                     |
                                     v
                          таблица «Ссылка / Статус»
```

Запись файла на диск уходит в поток по той же причине: `open().write()` — блокирующая
операция, и на крупном изображении она задержала бы остальные загрузки.

### Ни одна ошибка не завершает программу

Каждый путь отказа не бросает исключение наружу, а ставит статус в объекте `Download`,
поэтому итоговая таблица печатается всегда:

| Что ловится | Чем оборачивается |
|---|---|
| ошибки сети | `aiohttp.ClientError` |
| превышение времени ожидания | `asyncio.TimeoutError`, лимит 30 с на загрузку |
| ошибки записи на диск | `OSError` |
| битые и нечитаемые URL | `ValueError`, `UnicodeError` |
| ответ сервера не 200 | проверка `response.status` отдельной веткой |

Каталог для сохранения проверяется не догадкой по строке, а **попыткой в него
записать**: создаётся и тут же удаляется пробный файл. Так ловится и несуществующий
путь, и отсутствие прав — `PermissionError` здесь частный случай `OSError`.
Совпадение имён разрешается числовым суффиксом.

### Фактический прогон загрузок

Пять ссылок подряд, без пауз между вводами. Среди них намеренно битые: несуществующий
файл на живом сервере и несуществующий домен. Первая ссылка повторена дважды —
проверка суффикса при совпадении имён.

```
Загрузка ещё идёт, осталось изображений: 4. Жду...
+-------------------------------------------+--------+
| Ссылка                                    | Статус |
+-------------------------------------------+--------+
| http://127.0.0.1:8731/swamp.jpg           | Успех  |
| http://127.0.0.1:8731/lake.png            | Успех  |
| http://127.0.0.1:8731/swamp.jpg           | Успех  |
| http://127.0.0.1:8731/no-such-picture.jpg | Ошибка |
| http://nonexistent.invalid/cat.jpg        | Ошибка |
+-------------------------------------------+--------+
Успешно: 3 из 5
```

Строка «осталось изображений: 4» — это и есть доказательство асинхронности: к моменту,
когда ввод закончился, четыре из пяти загрузок ещё не завершились, то есть ссылки
принимались, не дожидаясь их. На диск легли три файла, и совпадение имён разрешилось
само:

```
lake.png       311333 байт
swamp.jpg       16962 байт
swamp_1.jpg     16962 байт
```

Отдельно проверен выбор каталога — пустая строка и каталог без прав на запись:

```
Куда сохранять изображения: Путь не может быть пустым.
Куда сохранять изображения: Не подходит: Permission denied. Введи другой путь.
Куда сохранять изображения:
```

Программа не упала ни на одном из пяти отказов и в обоих случаях с каталогом
спросила путь заново.

> Прогон сделан против локального `python3 -m http.server`, а не против внешних
> адресов: так проверка воспроизводима и не зависит от того, жива ли сегодня чужая
> картинка. Для программы разницы нет — это обычный HTTP.

## Итог

Обе программы отрабатывают, `./run.sh check` проходит, вывод обеих приведён выше
без правок.

Задача 1 показала, что в многопроцессной программе сложность не в запуске процессов —
это три строки, — а в разделяемом состоянии. Два из трёх тонких мест ломаются **молча**:
генератор в `manager.list()` роняет программу сразу и потому безобиден, а вот правка
вложенной структуры на месте просто не доходит до менеджера, и заметить это можно
только по разошедшимся числам в таблице. Оба обходятся одним приёмом: в разделяемые
структуры кладутся неизменяемые значения, которые переприсваиваются целиком.

Задача 2 показала обратное: там, где параллелизма нет вообще, всё решает то,
что именно блокирует единственный поток. Одна строка с `asyncio.to_thread` вокруг
`input()` отделяет работающую программу от программы, которая формально асинхронна,
а фактически последовательна.
