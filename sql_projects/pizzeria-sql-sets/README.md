# 🍕 SQL: множества и соединения таблиц

### 📌 Обзор проекта

Одиннадцать запросов к той же базе пиццерий, что и в [проекте с выборками](../pizzeria-sql-basics), но задача здесь другая: собрать ответ из **нескольких таблиц сразу**. Два способа сделать это противопоставлены напрямую — операторы множеств `UNION` / `INTERSECT` / `EXCEPT`, приставляющие выборки друг к другу по вертикали, и соединения `JOIN` / `NATURAL JOIN`, склеивающие их по горизонтали.

Выбор между ними здесь не стилистический. В базе два журнала событий — посещения и заказы, — и **общего внешнего ключа у них нет**: по условию задания визит и заказ одного человека в один день совпадают случайно, а не следуют друг из друга. Соединять такие таблицы по ключу нечем, и вопрос «кто в один день и заходил, и заказывал» решается только пересечением множеств. Часть заданий вдобавок запрещает `JOIN` и `DISTINCT`, заставляя получать тот же результат средствами теории множеств.

### 🏗 Схема базы

```
   person                          pizzeria
   ├─ id          PK               ├─ id       PK
   ├─ name                         ├─ name
   ├─ age              CHECK       └─ rating      CHECK 0 ≤ rating ≤ 5
   ├─ gender      female | male
   └─ address                              ▲              ▲
        ▲   ▲                              │              │
        │   │                              │              │
        │   └──────── person_visits ───────┘              │
        │             ├─ id          PK                   │
        │             ├─ person_id   FK                   │
        │             ├─ pizzeria_id FK                   │
        │             └─ visit_date       UNIQUE(person, pizzeria, date)
        │
        └──────────── person_order                     menu
                      ├─ id         PK                 ├─ id          PK
                      ├─ person_id  FK                 ├─ pizzeria_id FK ─┘
                      ├─ menu_id    FK ───────────────►├─ pizza_name
                      └─ order_date                    └─ price

   9 человек · 6 пиццерий · 18 позиций меню · 19 посещений · 20 заказов
```

Три справочника (`person`, `pizzeria`, `menu`) и два журнала событий (`person_visits`, `person_order`). Журналы ссылаются на справочники, **но не друг на друга**: у них нет ни общего внешнего ключа, ни связующей таблицы — только одноимённый столбец `person_id`, значения в котором ведут в один и тот же справочник.

Из этого вырастает половина заданий дня. Соединить журналы по `person_id` технически можно, но смысл получится неверный: `JOIN` даст все пары «заказ × визит» одного человека, а не факт «в этот день было и то, и другое». Правильный инструмент — сравнение двух наборов пар `(дата, person_id)` как множеств.

### 🚀 Что интересного в запросах

* **`INTERSECT` там, где напрашивается `JOIN`.** В `ex03` и `ex06` пересекаются два журнала. Соединение по `person_id` вернуло бы декартово произведение внутри каждого человека: три заказа Дениса за 7 января и один его визит дали бы три строки вместо одной. `INTERSECT` сравнивает строки целиком и отвечает ровно на заданный вопрос.

* **`EXCEPT ALL` и `EXCEPT` дают разный ответ, а не разное число строк.** В `ex04` слева `person_id` заказов за 7 января — `4, 4, 4, 8`, справа `person_id` визитов за тот же день — `4, 8`. Как множества обе стороны одинаковы: `{4, 8}`. Обычный `EXCEPT` сначала свернул бы дубликаты и вернул **ноль строк**; `EXCEPT ALL` вычитает поштучно (`3 − 1 = 2` четвёрки, `1 − 1 = 0` восьмёрок) и возвращает две. Разница видна только на мультимножествах.

* **`UNION ALL` вместо `UNION` в `ex01` — требование условия, а не оптимизация.** «Cheese pizza» есть в меню шести разных пиццерий, это шесть настоящих строк. Обычный `UNION` схлопнул бы их в одну и потерял данные.

* **`UNION` таблицы с самой собой заменяет запрещённый `DISTINCT`.** В `ex02` запрещены `DISTINCT`, `GROUP BY`, `HAVING` и любые `JOIN`. Уникальность достаётся из семантики самого оператора: `UNION` по определению возвращает множество.

* **`NATURAL JOIN` — главная ловушка дня.** В `ex08` он соединяет `person_order` и `person`, а столбец `id` есть в обеих таблицах и означает в них разное: номер заказа и номер человека. Голый `NATURAL JOIN` соединил бы именно по нему и выдал мусор, не сообщив об ошибке. Обе стороны завёрнуты в подзапросы так, чтобы единственным общим именем остался `person_id`.

* **`NOT IN` против `NOT EXISTS` в `ex09`.** Оба варианта дают один ответ, но `NOT IN` безопасен здесь лишь потому, что `person_visits.pizzeria_id` объявлен `NOT NULL`. Появись там `NULL` — всё условие стало бы неопределённым, и запрос молча вернул бы пустой результат. `NOT EXISTS` этой ловушке не подвержен.

* **Сортировка по вычисляемой строке в `ex07` — текстовая.** `ORDER BY person_information` упорядочивает готовую строку `Имя (age:XX)`, поэтому `Andrey (age:21)` идёт раньше `Anna (age:16)`: сравниваются символы, а не возраст.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `ex00/` … `ex10/` | по одному файлу `day01_exNN.sql` на упражнение |
| `run.sh` | прогон: интерактивное меню или все одиннадцать подряд |
| `main_report.md` | разбор каждого запроса с фактическим выводом |

Схема и тестовые данные (`model.sql`) выданы курсом и в репозиторий не входят — без них запросы выполнить не на чем. Условия заданий тоже не публикуются, их формулировки пересказаны в отчёте своими словами.

### ▶️ Запуск

```bash
createdb sqlb2_sets
psql -d sqlb2_sets -f model.sql     # файл из поставки задания, в репозитории его нет

./run.sh all                        # все одиннадцать подряд
./run.sh                            # меню: Enter — следующее упражнение, q — выход
```

Имя базы переопределяется переменной окружения: `DB_NAME=my_db ./run.sh all`. Права суперпользователя не нужны — все запросы только читают данные.

Режим `all` возвращает ненулевой код, если хотя бы одно упражнение упало: `psql` вызывается с `ON_ERROR_STOP=1`, иначе он печатает ошибку и всё равно завершается успешно, и сломанный запрос в общем прогоне теряется.

Прогон на живой базе сверялся с образцами вывода из условия автоматически — по именам столбцов и по каждой строке образца в её позиции. **Расхождений не нашлось**, включая два места, где они наиболее вероятны: `ex08` возвращает побайтово тот же результат, что `ex07` (этого требует условие), а оба варианта `ex09` совпадают между собой. Отдельно проверено соблюдение списков запрещённых конструкций — того, что возвращает верные строки недопустимым способом, в решениях нет.
