# Отчёт: множества и соединения таблиц

Одиннадцать упражнений на сборку ответа из нескольких таблиц: операторы множеств `UNION` / `INTERSECT` / `EXCEPT` и соединения `JOIN` / `NATURAL JOIN`. Каждое упражнение — один файл `day01_exNN.sql`.

Отчёт построен на фактическом выводе: все одиннадцать запросов прогнаны заново на локальном PostgreSQL, результаты вставлены как есть.

---

## Условия прогона

| Параметр | Значение |
|---|---|
| СУБД | PostgreSQL 16.15 (Ubuntu 24.04) |
| База | схема и данные из `model.sql` поставки задания |
| Запуск | `./run.sh all` — все одиннадцать подряд, от обычного пользователя |
| Объём данных | 9 человек, 6 пиццерий, 18 позиций меню, 19 посещений, 20 заказов |

---

## Схема и данные

```
   person                          pizzeria
   ├─ id          PK               ├─ id       PK
   ├─ name                         ├─ name
   ├─ age              CHECK       └─ rating      CHECK 0 ≤ rating ≤ 5
   ├─ gender      female | male
   └─ address                              ▲              ▲
        ▲   ▲                              │              │
        │   └──────── person_visits ───────┘              │
        │             ├─ person_id   FK                   │
        │             ├─ pizzeria_id FK                   │
        │             └─ visit_date       UNIQUE(person, pizzeria, date)
        │
        └──────────── person_order                     menu
                      ├─ person_id  FK                 ├─ pizzeria_id FK ─┘
                      ├─ menu_id    FK ───────────────►├─ pizza_name
                      └─ order_date                    └─ price
```

Ключевая особенность модели, на которой построена половина дня: **два журнала событий не связаны друг с другом**. `person_visits` и `person_order` ссылаются на общие справочники, но между собой у них нет ни внешнего ключа, ни связующей таблицы — только одноимённый столбец `person_id`, ведущий в `person`.

По условию задания это сделано намеренно: визит и заказ одного человека в один день — совпадение, а не причинно-следственная связь. Поэтому вопрос «кто в один день и заходил, и заказывал» нельзя решить соединением: `JOIN` по `person_id` вернул бы все пары «заказ × визит» внутри каждого человека. Сравнивать нужно наборы пар `(дата, person_id)` как множества.

---

## Теория, на которой стоят задания

### Множество и мультимножество

`UNION`, `INTERSECT` и `EXCEPT` работают с результатом запроса как с математическим множеством: дубликаты схлопываются, порядок не значим. Модификатор `ALL` отменяет схлопывание и переводит оператор в арифметику мультимножеств, где у каждой строки есть кратность:

| Оператор | Кратность строки в результате |
|---|---|
| `UNION ALL` | `m + n` |
| `INTERSECT ALL` | `min(m, n)` |
| `EXCEPT ALL` | `max(m − n, 0)` |

Без `ALL` кратность любой строки результата равна единице. Отсюда практическое следствие: `ALL` — не флаг производительности, а другой ответ на другой вопрос. В `ex04` именно это отличает две строки от нуля строк.

### Множества против соединений

Оба механизма объединяют данные, но в разных направлениях:

```
   UNION — по вертикали              JOIN — по горизонтали

   ┌────────────┐                    ┌────────────┬────────────┐
   │  выборка A │                    │  строка A  │  строка B  │
   ├────────────┤                    └────────────┴────────────┘
   │  выборка B │                    столбцов больше, строк —
   └────────────┘                    столько, сколько нашлось пар
   столбцы те же,
   строк больше
```

Отсюда и требования: операторы множеств требуют одинакового **числа столбцов и совместимых типов**, а имена итоговых столбцов берутся из первой выборки. Соединения не требуют ничего, кроме условия совпадения, — и потому молчаливо дают декартово произведение, если условие задано неверно или не задано вовсе.

### `ORDER BY` относится ко всему запросу

В конструкции с оператором множеств `ORDER BY` не принадлежит последней выборке — он сортирует объединённый результат и потому пишется один раз, в самом конце. Сортировать по столбцу, которого нет в итоговом списке, нельзя: в `ex01` из-за этого понадобился приём со служебным столбцом внутри подзапроса.

## Ограничения по упражнениям

Часть заданий запрещает конструкции, которыми задача решалась бы в один приём. Это и определяет вид запросов.

| Упражнение | Запрещено | Чем заменяется |
|---|---|---|
| `ex02` | `DISTINCT`, `GROUP BY`, `HAVING`, все виды `JOIN` | `UNION` таблицы с самой собой |
| `ex03` | все виды `JOIN` | `INTERSECT` |
| `ex04` | все виды `JOIN` | `EXCEPT ALL` |
| `ex08` | все `JOIN`, кроме `NATURAL JOIN` | подзапросы, приводящие имена столбцов |

Соблюдение этих списков проверено отдельно: запрос, возвращающий верные строки запрещённым способом, задание не проходит.

## ex00 — объединение двух справочников

Требуется собрать в один список идентификаторы и названия из `menu` и `person`, упорядочив по идентификатору, затем по имени.

```sql
SELECT id AS object_id, pizza_name AS object_name FROM menu
UNION
SELECT id AS object_id, name AS object_name FROM person
ORDER BY object_id, object_name;
```

```
 object_id |   object_name
-----------+-----------------
         1 | Anna
         1 | cheese pizza
         2 | Andrey
         2 | pepperoni pizza
         3 | Kate
         3 | sausage pizza
...
        18 | supreme pizza
(27 rows)
```

Выборки уравниваются **по позиции столбцов**, а не по именам: первый столбец одной ложится на первый столбец другой независимо от того, как они названы. Имена итоговых столбцов берутся только из первого `SELECT`, поэтому псевдонимы во втором на результат не влияют — они оставлены для читаемости.

27 строк вместо 27 = 18 + 9 здесь совпадение: `UNION` дубликатов не нашёл, потому что пара «число + строка» у пиццы и человека совпасть не может.

## ex01 — сохранить дубликаты и разделить блоки

То же объединение без столбца `object_id`, но людей нужно вывести первыми и по алфавиту, затем — пиццы, тоже по алфавиту, **сохранив повторы**.

```sql
SELECT object_name
FROM (
    SELECT name AS object_name, 1 AS block FROM person
    UNION ALL
    SELECT pizza_name AS object_name, 2 AS block FROM menu
) t
ORDER BY block, object_name;
```

```
   object_name
-----------------
 Andrey
 Anna
 Denis
 Dmitriy
 Elvira
 Irina
 Kate
 Nataly
 Peter
 cheese pizza
 cheese pizza
 cheese pizza
 cheese pizza
 cheese pizza
 cheese pizza
 mushroom pizza
...
(27 rows)
```

Два решения в одном запросе.

**`UNION ALL` вместо `UNION`** — требование условия «сохрани дубликаты», а не оптимизация. «Cheese pizza» встречается в `menu` шесть раз, у шести разных пиццерий; обычный `UNION` оставил бы одну строку и потерял пять.

**Служебный столбец `block`** задаёт порядок блоков. Сортировать по нему напрямую нельзя — в выводе должен остаться единственный столбец `object_name`. Поэтому объединение убрано в подзапрос, где `block` существует, а внешний `SELECT` его не проецирует: сортировка им пользуется, читатель результата — не видит.

## ex02 — уникальность без `DISTINCT`

Нужны уникальные названия пицц по убыванию. Запрещены `DISTINCT`, `GROUP BY`, `HAVING` и любые соединения.

```sql
SELECT pizza_name FROM menu
UNION
SELECT pizza_name FROM menu
ORDER BY pizza_name DESC;
```

```
   pizza_name
-----------------
 supreme pizza
 sausage pizza
 pepperoni pizza
 mushroom pizza
 cheese pizza
(5 rows)
```

Объединение таблицы с самой собой не добавляет ни одной новой строки, но переводит результат в семантику множества — а множество дубликатов не содержит по определению. Уникальность здесь не вычисляется отдельной командой, она вытекает из свойств оператора.

Из 18 позиций меню остаётся 5 названий: одни и те же пиццы продаются в разных пиццериях по разным ценам.

## ex03 — пересечение двух журналов

Нужны пары «дата и человек», для которых в этот день есть **и** заказ, **и** посещение. Соединения запрещены.

```sql
SELECT order_date AS action_date, person_id FROM person_order
INTERSECT
SELECT visit_date AS action_date, person_id FROM person_visits
ORDER BY action_date ASC, person_id DESC;
```

```
 action_date | person_id
-------------+-----------
 2022-01-01  |         6
 2022-01-01  |         2
 2022-01-01  |         1
 2022-01-03  |         7
 2022-01-04  |         3
 2022-01-05  |         7
 2022-01-06  |         8
 2022-01-07  |         8
 2022-01-07  |         4
 2022-01-08  |         4
 2022-01-09  |         9
 2022-01-09  |         5
 2022-01-10  |         9
(13 rows)
```

Запрет `JOIN` в этом упражнении не столько ограничение, сколько подсказка: соединять журналы **нечем**. Общего ключа у них нет, а соединение по `person_id` ответило бы на другой вопрос — оно вернуло бы каждую комбинацию заказа с визитом одного человека. У Дениса за 7 января три заказа и один визит, и такой запрос дал бы три строки вместо одной.

`INTERSECT` сравнивает строки целиком: пара `(дата, person_id)` либо есть в обоих наборах, либо нет. Кратность не важна — поэтому без `ALL`.

## ex04 — разность мультимножеств

Разность `person_id` между заказами и посещениями за 7 января, с сохранением дубликатов.

```sql
SELECT person_id FROM person_order WHERE order_date = '2022-01-07'
EXCEPT ALL
SELECT person_id FROM person_visits WHERE visit_date = '2022-01-07';
```

```
 person_id
-----------
         4
         4
(2 rows)
```

Самое показательное упражнение дня. За 7 января данные такие:

```
person_order  :  4, 4, 4, 8     Денис заказывал трижды, Натали — один раз
person_visits :  4, 8           оба в этот день где-то были
```

Как **множества** обе стороны одинаковы — `{4, 8}`, и обычный `EXCEPT` вернул бы ноль строк: разность одинаковых множеств пуста. Как **мультимножества** они различны, и `EXCEPT ALL` вычитает поштучно: `3 − 1 = 2` четвёрки, `1 − 1 = 0` восьмёрок.

Замена `EXCEPT ALL` на `EXCEPT` не «слегка изменила бы вывод» — она превратила бы содержательный ответ в пустой. При этом запрос остался бы синтаксически безупречным.

Оператор к тому же не коммутативен: поменяв выборки местами, получим ответ на другой вопрос — «кто заходил, но не заказывал», и в этих данных он пуст.

## ex05 — декартово произведение

Все возможные сочетания строк `person` и `pizzeria`.

```sql
SELECT p.*, pz.*
FROM person p
CROSS JOIN pizzeria pz
ORDER BY p.id, pz.id;
```

```
 id |  name   | age | gender |     address      | id |    name    | rating
----+---------+-----+--------+------------------+----+------------+--------
  1 | Anna    |  16 | female | Moscow           |  1 | Pizza Hut  |    4.6
  1 | Anna    |  16 | female | Moscow           |  2 | Dominos    |    4.3
  1 | Anna    |  16 | female | Moscow           |  3 | DoDo Pizza |    3.2
...
  9 | Dmitriy |  18 | male   | Samara           |  6 | DinoPizza  |    4.2
(54 rows)
```

9 × 6 = 54 строки — ровно произведение мощностей. Здесь это запрошенный результат, но то же самое получается случайно, когда в обычном соединении забыто условие: `CROSS JOIN` — это и есть `JOIN` без `ON`.

В выводе по два столбца `id` и `name` с одинаковыми именами. PostgreSQL это допускает, и запрос отрабатывает. Обращаться к таким столбцам по имени уже нельзя — и ровно на этом построена ловушка `ex08`.

## ex06 — то же пересечение, но с именами

Вопрос `ex03`, но вместо `person_id` нужно имя человека. Соединения здесь разрешены.

```sql
SELECT t.action_date, p.name AS person_name
FROM (
    SELECT order_date AS action_date, person_id FROM person_order
    INTERSECT
    SELECT visit_date AS action_date, person_id FROM person_visits
) t
JOIN person p ON p.id = t.person_id
ORDER BY t.action_date ASC, person_name DESC;
```

```
 action_date | person_name
-------------+-------------
 2022-01-01  | Irina
 2022-01-01  | Anna
 2022-01-01  | Andrey
 2022-01-03  | Peter
 2022-01-04  | Kate
 2022-01-05  | Peter
 2022-01-06  | Nataly
 2022-01-07  | Nataly
 2022-01-07  | Denis
 2022-01-08  | Denis
 2022-01-09  | Elvira
 2022-01-09  | Dmitriy
 2022-01-10  | Dmitriy
(13 rows)
```

Показательно распределение ролей. Отбор строк остаётся за множествами — `INTERSECT` внутри подзапроса решает, **какие** записи нужны. Соединение подключается только снаружи и делает единственное: подставляет имя вместо идентификатора, то есть расшифровывает справочник.

Попытка обойтись одним соединением вернула бы к проблеме `ex03`. 13 строк здесь те же, что и там, — соединение с `person` не может ни добавить строк, ни убавить, потому что идёт по первичному ключу.

## ex07 — соединение по внешнему ключу

Дата заказа и строка вида `Имя (age:возраст)`.

```sql
SELECT po.order_date, p.name || ' (age:' || p.age || ')' AS person_information
FROM person_order po
JOIN person p ON p.id = po.person_id
ORDER BY po.order_date, person_information;
```

```
 order_date | person_information
------------+--------------------
 2022-01-01 | Andrey (age:21)
 2022-01-01 | Andrey (age:21)
 2022-01-01 | Anna (age:16)
 2022-01-01 | Anna (age:16)
 2022-01-01 | Irina (age:21)
 2022-01-03 | Peter (age:24)
...
 2022-01-10 | Dmitriy (age:18)
(20 rows)
```

Здесь соединение уместно: у `person_order` есть настоящий внешний ключ на `person`. Строк ровно 20 — по числу заказов: каждый заказ находит одного человека по первичному ключу.

Дубликаты в выводе не ошибка — это разные заказы одного человека за один день, и `person_information` у них совпадает.

Сортировка идёт **по готовой строке**, а не по возрасту: `Andrey (age:21)` стоит раньше `Anna (age:16)`, потому что сравниваются символы `d` и `n`. Возраст внутри строки на порядок не влияет — он уже часть текста.

## ex08 — тот же результат через `NATURAL JOIN`

Условие требует переписать `ex07` на `NATURAL JOIN`, получив тот же результат. Другие виды соединений запрещены.

```sql
SELECT po.order_date, p.name || ' (age:' || p.age || ')' AS person_information
FROM (SELECT person_id, order_date FROM person_order) po
NATURAL JOIN (SELECT id AS person_id, name, age FROM person) p
ORDER BY po.order_date, person_information;
```

```
 order_date | person_information
------------+--------------------
 2022-01-01 | Andrey (age:21)
 2022-01-01 | Andrey (age:21)
 2022-01-01 | Anna (age:16)
 2022-01-01 | Anna (age:16)
...
(20 rows)
```

Главная ловушка дня. `NATURAL JOIN` не принимает условия соединения — он берёт **все столбцы с одинаковыми именами** в обеих таблицах и требует их равенства.

У `person_order` и `person` совпадающих имён два: `person_id` и `id`. И если `person_id` — это действительно ссылка на человека, то `id` означает в них разное: номер заказа слева и номер человека справа. Соединение по паре `(person_id, id)` потребовало бы, чтобы номер заказа равнялся номеру человека, — условие бессмысленное, но синтаксически допустимое. Запрос не выдал бы ошибки, он просто вернул бы неверные строки.

Решение — сузить набор общих имён до одного. Обе стороны завёрнуты в подзапросы: слева выбраны только `person_id` и `order_date`, справа `id` переименован в `person_id`. Теперь единственное общее имя — `person_id`, и `NATURAL JOIN` становится равносилен явному `ON p.id = po.person_id` из `ex07`.

Совпадение с `ex07` проверено сравнением файлов вывода, а не глазами: результаты идентичны побайтово.

## ex09 — `NOT IN` против `NOT EXISTS`

Пиццерии, которые никто не посещал. Условие требует два варианта.

```sql
-- через IN
SELECT * FROM pizzeria
WHERE id NOT IN (SELECT pizzeria_id FROM person_visits);

-- через EXISTS
SELECT * FROM pizzeria pz
WHERE NOT EXISTS (
    SELECT 1 FROM person_visits pv WHERE pv.pizzeria_id = pz.id
);
```

```
 id |    name    | rating
----+------------+--------
  3 | DoDo Pizza |    3.2
(1 row)

 id |    name    | rating
----+------------+--------
  3 | DoDo Pizza |    3.2
(1 row)
```

Ответ один и тот же, но равнозначны варианты не всегда.

`NOT IN` разворачивается в цепочку сравнений `id <> v1 AND id <> v2 AND …`. Появись в подзапросе `NULL`, соответствующее сравнение даст не «истину» и не «ложь», а неопределённость, и всё условие перестанет быть истинным **для любой строки** — запрос вернёт пусто, не сообщив ни о какой ошибке.

Здесь это не срабатывает только потому, что `person_visits.pizzeria_id` объявлен `NOT NULL`. То есть корректность варианта с `NOT IN` держится на ограничении схемы, а не на самом запросе, — снимут ограничение, и запрос сломается молча.

`NOT EXISTS` проверяет факт наличия строк и на `NULL` не реагирует. Поэтому в качестве значения по умолчанию надёжнее он.

## ex10 — цепочка из трёх соединений

Кто, что и в какой пиццерии заказал.

```sql
SELECT p.name AS person_name, m.pizza_name, pz.name AS pizzeria_name
FROM person_order po
JOIN person p ON p.id = po.person_id
JOIN menu m ON m.id = po.menu_id
JOIN pizzeria pz ON pz.id = m.pizzeria_id
ORDER BY person_name, pizza_name, pizzeria_name;
```

```
 person_name |   pizza_name    | pizzeria_name
-------------+-----------------+---------------
 Andrey      | cheese pizza    | Dominos
 Andrey      | mushroom pizza  | Dominos
 Anna        | cheese pizza    | Pizza Hut
 Anna        | pepperoni pizza | Pizza Hut
 Denis       | cheese pizza    | Best Pizza
 Denis       | pepperoni pizza | Best Pizza
 Denis       | pepperoni pizza | DinoPizza
 Denis       | sausage pizza   | DinoPizza
 Denis       | supreme pizza   | Best Pizza
...
 Peter       | supreme pizza   | Pizza Hut
(20 rows)
```

Пиццерия у заказа не хранится — она известна только через меню, поэтому нужен переход по трём ключам подряд: `person_order → person`, `person_order → menu`, `menu → pizzeria`.

Строк снова ровно 20, по числу заказов: каждое соединение идёт по первичному ключу принимающей таблицы, а такое соединение размножить строки не может. Это отличает цепочку соединений по ключам от соединения журналов, где число строк было бы непредсказуемым.

Две строки Дениса с `pepperoni pizza` из разных пиццерий — не дубликат: одна и та же пицца продаётся в нескольких местах, и это два разных заказа.

## Что показал прогон

Расхождений с образцами из условия **не найдено** — ни в именах столбцов, ни в значениях, ни в порядке строк.

Проверка велась не чтением. Образцы вывода из условия разбирались автоматически, и каждая явно заданная строка сверялась с фактическим выводом в её позиции; отдельно сверялись имена столбцов. Из одиннадцати упражнений образец задан у шести — у остальных условие ограничивается словесной формулировкой.

Дополнительно проверено то, что образцом не покрывается:

| Проверка | Результат |
|---|---|
| `ex08` возвращает то же, что `ex07` (требование условия) | вывод совпал побайтово |
| два варианта `ex09` дают одинаковый ответ | совпали |
| `ex05` даёт полное произведение | 54 строки = 9 × 6 |
| соблюдение списков запрещённых конструкций | нарушений нет |
| прогон целиком с `ON_ERROR_STOP=1` | 11 из 11, код возврата 0 |

Единственное место, где автоматическая сверка показала различие, — имена столбцов в `ex05`: в образце они записаны как `person.id` и `pizzeria.id`, в выводе — просто `id` и `id`. Это не дефект: условие упражнения оговаривает, что имена столбцов могут отличаться, а сами строки и их количество совпадают с образцом точно.

## Что изменено при публикации

| Изменение | Причина |
|---|---|
| `run.sh`: пути строятся от каталога скрипта | при переносе в портфолио уровень `src/` убран, прежний путь `$ROOT/src` перестал существовать |
| `run.sh`: добавлен `ON_ERROR_STOP=1` | без него `psql` печатает ошибку в запросе и всё равно завершается с нулевым кодом — упавшее упражнение в общем прогоне терялось |
| `run.sh`: добавлен режим `all` и счётчик ошибок | сданная версия была только интерактивной: чтобы увидеть весь вывод, требовалось одиннадцать раз нажать Enter |
| `run.sh`: имя базы вынесено в `DB_NAME`, добавлена проверка подключения | было зашито в код; при недоступной базе скрипт выдавал одиннадцать одинаковых ошибок подряд |
| Условия заданий пересказаны своими словами | материалы курса в публикацию не идут |

Логика запросов не менялась: все одиннадцать файлов `.sql` опубликованы в том виде, в каком сданы. Комментарии в них были написаны при решении и оставлены как есть.

## Итог

Одиннадцать упражнений отрабатывают, вывод каждого приведён выше, расхождений с условием нет.

Главное в этом дне — не набор операторов, а критерий выбора между двумя способами связать таблицы. Формально `INTERSECT` в `ex03` заменяем соединением, и запрос даже выполнится. Но ответ будет другим: соединение по `person_id` перечисляет пары «заказ и визит», а вопрос задан про факт «в этот день было и то, и другое». Правило, которое из этого следует: соединение уместно там, где есть внешний ключ и связь между записями реальна; там, где сравниваются два независимых набора, работают множества.

Второе наблюдение — про тихие ошибки. Три из одиннадцати упражнений устроены так, что неверное решение **не падает и не выдаёт предупреждения**: `EXCEPT` вместо `EXCEPT ALL` вернёт пустой результат вместо двух строк, `UNION` вместо `UNION ALL` потеряет пять строк из двадцати семи, а голый `NATURAL JOIN` в `ex08` соединит заказы с людьми по номеру заказа. Все три варианта синтаксически безупречны. Отличить их от правильных можно только сверкой фактического вывода с ожидаемым — что и делалось.
