# 🍕 SQL: представления и снимки данных

### 📌 Обзор проекта

Девять запросов к той же базе пиццерий, что и в [выборках](../pizzeria-sql-basics), [множествах](../pizzeria-sql-sets), [соединениях](../pizzeria-sql-joins) и [изменении данных](../pizzeria-sql-dml). Тема — представления: как спрятать запрос за именем и чем обычное представление отличается от материализованного.

Разница в одном: обычное представление **хранит запрос**, материализованное — **результат**. Первое выполняется заново при каждом обращении и всегда актуально. Второе выполняется один раз при создании, ложится на диск как таблица и после этого живёт своей жизнью: данные в таблицах меняются, снимок отдаёт прежний ответ, пока его не обновят командой `REFRESH`.

Проект показывает это не на словах. В `ex06` создаётся снимок, в `ex07` в таблицу добавляется строка, подходящая под его условие, — и до `REFRESH` представление продолжает возвращать старый результат, а тот же запрос напрямую к таблицам уже возвращает новый.

### 🏗 Что создаётся за день

```
   ex00  v_persons_female, v_persons_male      фильтр по полу
     └─► ex01  UNION двух представлений        общий список имён

   ex02  v_generated_dates                     календарь января
     └─► ex03  дни без визитов                 календарь EXCEPT журнал

   ex04  v_symmetric_union                     (R−S) ∪ (S−R) по двум датам
   ex05  v_price_with_discount                 цена со скидкой 10%

   ex06  mv_dmitriy_visits_and_eats            МАТЕРИАЛИЗОВАННОЕ, WITH DATA
     └─► ex07  новый визит + REFRESH           снимок догоняет таблицы
           └─► ex08  DROP всех шести объектов
```

Зависимости настоящие: `ex01` не выполнится без `ex00`, `ex03` без `ex02`, `ex07` без `ex06`. Порядок в `ex08` обратный созданию, но продиктован он привычкой, а не зависимостями: ни одно представление дня не построено поверх другого — проверено удалением первого созданного, оно проходит.

### 🚀 Что интересного

* **Снимок не следит за таблицами.** Главная демонстрация дня: между вставкой строки и `REFRESH` материализованное представление и прямой запрос к таблицам дают **разные ответы**, и оба верны — просто отвечают на разные моменты времени. Обычное представление такого расхождения не допускает по построению.

* **`WITH DATA` — не украшение.** С `WITH NO DATA` представление создалось бы пустым, и любой запрос к нему падал бы с «materialized view has not been populated» до первого `REFRESH`.

* **`DROP VIEW` не удаляет материализованное представление.** Команда прерывается: `"mv_dmitriy_visits_and_eats" is not a view`, с подсказкой использовать `DROP MATERIALIZED VIEW`. Для сервера это разные виды объектов — один хранит данные и занимает место, другой не хранит ничего.

* **`ORDER BY` внутри представления ничего не гарантирует.** Он сохраняется в определении, но внешний запрос вправе получить строки в любом порядке, если сортировка не запрошена снаружи. Поэтому `ex03` сортирует сам, хотя `v_generated_dates` уже упорядочено.

* **`round(...)` в `ex05` исправляет то, что всплыло в предыдущем проекте.** `price - price * 0.1` на столбце `numeric` без масштаба даёт `720.0` вместо `720`: арифметика `numeric` сохраняет масштаб самого точного операнда. В том проекте это осталось как есть — там формат не оговаривался, — здесь условие требует целое, и округление ставит точку в этой истории.

* **`ex06` переиспользует запрос из соседнего проекта.** Условие прямо отсылает к упражнению из дня про соединения: пиццерия, где Дмитрий был 8 января и мог поесть дешевле 800. Ответы совпадают — `Papa Johns` там и здесь.

* **Явные столбцы вместо `*` в `ex00`.** PostgreSQL разворачивает звёздочку в список колонок в момент создания представления, так что добавленный позже столбец таблицы в него всё равно не попадёт. Явный список делает это видимым по тексту.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `ex00/` … `ex08/` | по одному файлу `day04_exNN.sql` на упражнение |
| `run.sh` | подготовка базы, прогон и режим `check` — двенадцать проверок результата |
| `main_report.md` | разбор каждого запроса с фактическим выводом |

Схема и тестовые данные (`model.sql`) выданы курсом и в репозиторий не входят. Условия заданий тоже не публикуются, их формулировки пересказаны в отчёте своими словами.

### ▶️ Запуск

```bash
# model.sql — файл из поставки задания, в репозитории его нет
MODEL=/путь/к/model.sql ./run.sh all      # подготовить базу и выполнить ex00..ex08
MODEL=/путь/к/model.sql ./run.sh check    # сквозной прогон со сверкой результатов

./run.sh ex05      # одно упражнение на текущей базе
./run.sh psql      # интерактивная сессия
```

**Стартовое состояние базы здесь не произвольно.** Условие требует, чтобы изменения из [проекта про DML](../pizzeria-sql-dml) оставались на месте: две записи в журналах, добавленная позиция меню и удалённая «greek pizza». Поэтому `run.sh` собирает базу из схемы и проигрывает поверх неё `ex07`…`ex13` соседнего проекта — требуемое состояние воспроизводится из самого репозитория, а не берётся откуда-то извне. Проверено сравнением: содержимое всех пяти таблиц совпадает с базой, оставшейся после того проекта. Готовую базу можно передать и напрямую: `BASE=имя ./run.sh all`.

Если соседний проект недоступен, скрипт продолжит работу, но предупредит: без DML-части в `v_price_with_discount` окажется 20 строк вместо 22.

**Режим `check` — не прогон, а проверка.** Он поднимает временную базу, выполняет упражнения по порядку и сверяет двенадцать утверждений: сколько строк в каждом представлении, какого типа `generated_date`, что снимок до `REFRESH` содержит одну строку, а после — две, и что после `ex08` не осталось ни одного представления, но все пять таблиц целы. Временная база удаляется в любом случае, включая прерывание.

### 📈 Итоговый результат

Все девять упражнений отрабатывают, вывод каждого приведён в отчёте, `./run.sh check` проходит полностью.

Результаты сверены с образцами вывода из условия — в `ex05` совпали обе строки образца, включая округление 1100 → 990. Там, где образца нет, ответ подтверждён независимо: 21 пропущенный день сходится с тем, что в журнале заняты ровно первые десять дней января; симметрическая разность `{2, 8}` — с тем, что 2 января был один человек, а 6 января другой; результат снимка — с ответом того же запроса из проекта про соединения.
