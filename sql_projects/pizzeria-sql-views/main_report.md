# Отчёт: представления и снимки данных

Девять упражнений про представления: как спрятать запрос за именем, чем обычное представление отличается от материализованного и что происходит, когда данные под снимком меняются. Каждое упражнение — один файл `day04_exNN.sql`.

Отчёт построен на фактическом выводе: все девять запросов прогнаны заново на локальном PostgreSQL, результаты вставлены как есть. Там, где упражнение только создаёт объект и выводит `CREATE VIEW`, показано содержимое созданного представления.

---

## Стартовое состояние базы

Это единственный проект серии, который **начинается не с чистой схемы**. Условие требует, чтобы изменения предыдущего дня — того, что про `INSERT`, `UPDATE` и `DELETE`, — оставались на месте:

| Таблица | Что добавлено предыдущим проектом |
|---|---|
| `menu` | позиция `(20, 2, 'sicilian pizza', 900)`; идентификатора 19 нет — «greek pizza» была добавлена и затем удалена |
| `person_visits` | два визита 24 февраля 2022 года, идентификаторы 20 и 21 |
| `person_order` | два заказа той же датой, идентификаторы 21 и 22 |

Читателю репозитория взять такую базу неоткуда, поэтому `run.sh` её **воспроизводит**: создаёт схему из `model.sql` и проигрывает поверх неё `ex07`…`ex13` соседнего проекта. Требуемое состояние собирается из самого репозитория.

Что сборка даёт именно то состояние — проверено, а не предположено: содержимое всех пяти таблиц сравнивалось с базой, оставшейся после предыдущего проекта, построчно через контрольные суммы. Совпало.

```
 person        | 8bffc5c887425a687409419e966dcc08
 pizzeria      | a02ee098eccde819e789dad4ab4e22a4
 menu          | 32eaf7da174a7057d61f452000c32af3
 person_visits | c511ae8d6df6de6c0658ea5fe2618a04
 person_order  | 1ec18040a919c6041bb78c724ad51123
```

Разница видна в `ex05`: на правильном стартовом состоянии в `v_price_with_discount` 22 строки, на чистой схеме было бы 20. Скрипт предупреждает об этом, если соседний проект недоступен.

## Представление и материализованное представление

Оба выглядят в запросе как таблица. Отличие — в том, что именно сохранено.

```
   VIEW — хранится ЗАПРОС                MATERIALIZED VIEW — хранится РЕЗУЛЬТАТ

   SELECT ... FROM v_...                 SELECT ... FROM mv_...
        │                                     │
        ▼                                     ▼
   определение подставляется            читаются строки, лежащие на диске
   и выполняется заново                 с момента создания или REFRESH
        │                                     │
        ▼                                     ▼
   всегда актуально,                     мгновенно, но данные — на момент
   платит временем запроса               последнего обновления
```

Из этого следует всё остальное. Обычное представление не занимает места и не может устареть — но каждый запрос к нему стоит столько же, сколько исходный. Материализованное занимает место как таблица и отвечает быстро — но между ним и таблицами возникает разрыв, который закрывается только явной командой `REFRESH`.

Упражнения `ex06` и `ex07` показывают этот разрыв в действии, а не описывают его.

## ex00 — два представления по полу

Нужны два представления с теми же атрибутами, что у исходной таблицы: `v_persons_female` и `v_persons_male`.

```sql
CREATE VIEW v_persons_female AS
SELECT id,
       name,
       age,
       gender,
       address
FROM person
WHERE gender = 'female';

CREATE VIEW v_persons_male AS
SELECT id,
       name,
       age,
       gender,
       address
FROM person
WHERE gender = 'male';
```

```
CREATE VIEW
CREATE VIEW
```

Определение сохраняется, данные — нет. Каждое обращение к `v_persons_female` выполняет `SELECT ... WHERE gender = 'female'` заново, поэтому добавленная в `person` женщина появится в представлении немедленно, без каких-либо действий.

Столбцы перечислены явно, а не через `*`, и это не многословность. PostgreSQL разворачивает звёздочку в список колонок **в момент создания** представления: столбец, добавленный в таблицу позже, в него не попадёт всё равно. Явный список делает это видимым по тексту, а не сюрпризом при чтении `pg_views`.

Пять женщин и четверо мужчин — вся таблица из девяти человек, разложенная на две непересекающиеся части.

## ex01 — общий список имён

Из двух представлений нужно получить один список имён, отсортированный по алфавиту.

```sql
SELECT name
FROM v_persons_female
UNION
SELECT name
FROM v_persons_male
ORDER BY name;
```

```
  name
---------
 Andrey
 Anna
 Denis
 Dmitriy
 Elvira
 Irina
 Kate
 Nataly
 Peter
(9 rows)
```

Для запроса представление неотличимо от таблицы: его имя стоит в `FROM`, а подставляется определение. В этом и смысл упражнения — сложность запроса убрана за имя, и снаружи видно только его.

`UNION` без `ALL` соответствует формулировке «один список». На этих данных обе формы дали бы девять строк: наборы не пересекаются по построению, `gender` ограничен двумя значениями. Разница проявилась бы на тёзках разного пола — в выборке остаётся только `name`, и `UNION` схлопнул бы двух разных людей в одну строку.

## ex02 — календарь января в представлении

Нужно представление `v_generated_dates`, возвращающее все даты января 2022 года в типе `DATE`.

```sql
CREATE VIEW v_generated_dates AS
SELECT CAST(gs AS DATE) AS generated_date
FROM generate_series(CAST('2022-01-01' AS DATE),
                     CAST('2022-01-31' AS DATE),
                     CAST('1 day' AS INTERVAL)) AS gs
ORDER BY generated_date;
```

```
CREATE VIEW
```

Представление здесь используется не для сокрытия сложности, а как **источник данных, которых в базе нет**. Календарь нигде не хранится, но выглядит как таблица: в `ex03` в `FROM` стоит `v_generated_dates`, а не вызов функции с тремя аргументами и приведением типа.

`CAST(... AS DATE)` вместо `::date` — форма ANSI SQL, разрешённая условием. Приведение обязательно: `generate_series` с шагом-интервалом возвращает `timestamp`, а требуется `DATE`. Проверено запросом к представлению — `pg_typeof(generated_date)` возвращает `date`.

`ORDER BY` внутри определения сохраняется, но **внешнему запросу ничего не гарантирует**: планировщик вправе вернуть строки в любом порядке, если сортировка не запрошена снаружи. Поэтому `ex03` сортирует сам.

В представлении 31 строка — весь январь.

## ex03 — дни без визитов

Нужны дни января, в которые не было ни одного посещения. Использовать представление из `ex02`.

```sql
SELECT generated_date AS missing_date
FROM v_generated_dates
EXCEPT
SELECT visit_date
FROM person_visits
ORDER BY missing_date;
```

```

 2022-01-13

 2022-01-16
 2022-01-17

```

Пропуск в данных — отсутствующая строка, и найти его можно только вычитанием журнала из полного ряда. Ряд даёт представление, вычитание — `EXCEPT`.

Проверка по данным: в журнале заняты ровно первые десять дней января, с 1-го по 10-е. Значит, свободны 11–31 — двадцать один день, столько и вернулось.

## ex04 — симметрическая разность двух дней

Нужно представление `v_symmetric_union` с формулой (R − S) ∪ (S − R), где R — визиты 2 января, S — визиты 6 января, и сравниваются множества значений `person_id`.

```sql
CREATE VIEW v_symmetric_union AS
(SELECT person_id
 FROM person_visits
 WHERE visit_date = '2022-01-02'
 EXCEPT
 SELECT person_id
 FROM person_visits
 WHERE visit_date = '2022-01-06')
UNION
(SELECT person_id
 FROM person_visits
 WHERE visit_date = '2022-01-06'
 EXCEPT
 SELECT person_id
 FROM person_visits
 WHERE visit_date = '2022-01-02')
ORDER BY person_id;
```

```
CREATE VIEW
```

Содержимое представления:

```
 person_id
-----------
         2
         8
(2 rows)
```

Формула записана буквально: две разности в противоположных направлениях и объединение результатов. Операторы идут **без** `ALL` — сравниваются множества идентификаторов, а не количества визитов. С `ALL` ответ означал бы перевес по числу посещений, то есть другой вопрос.

Проверка по данным: 2 января в журнале один человек (`person_id = 2`), 6 января — другой (`person_id = 8`). Пересечение пусто, поэтому симметрическая разность совпала с объединением: оба идентификатора.

В представлении зашиты конкретные даты — это часть его определения. Появится новый визит 2 или 6 января, и результат изменится сам, без правки представления.

## ex05 — цена со скидкой

Нужно представление `v_price_with_discount` с именем клиента, названием пиццы, реальной ценой и ценой со скидкой 10%, округлённой до целого.

```sql
CREATE VIEW v_price_with_discount AS
SELECT p.name,
       m.pizza_name,
       m.price,
       round(m.price - m.price * 0.1) AS discount_price
FROM person_order po
         JOIN person p ON p.id = po.person_id
         JOIN menu m ON m.id = po.menu_id
ORDER BY p.name, m.pizza_name;
```

```
CREATE VIEW
```

Первые строки представления:

```
  name  |   pizza_name    | price | discount_price
--------+-----------------+-------+----------------
 Andrey | cheese pizza    |   800 |            720
 Andrey | mushroom pizza  |  1100 |            990
 Anna   | cheese pizza    |   900 |            810
 Anna   | pepperoni pizza |  1200 |           1080
 Denis  | cheese pizza    |   700 |            630
 Denis  | pepperoni pizza |   800 |            720
(6 rows)
```

Обе строки образца из условия совпали: `Andrey / cheese pizza / 800 / 720` и `Andrey / mushroom pizza / 1100 / 990`.

**`round(...)` здесь не косметика.** Столбец `price` объявлен как `numeric` без масштаба, а литерал `0.1` имеет масштаб 1: произведение получает дробную часть, и без округления 800 превратилось бы в `720.0`. В предыдущем проекте, где формат не оговаривался, это так и осталось; здесь условие требует целое, и `round` ставит точку в этой истории.

Скидка считается на лету при каждом обращении — представление данных не хранит. Изменится цена в меню, изменится и вывод, пересчитывать ничего не нужно. Ровно этим оно отличается от материализованного из `ex06`.

Всего в представлении 22 строки — по числу заказов в базе, включая два, добавленных предыдущим проектом.

## ex06 — материализованное представление

Нужно создать `mv_dmitriy_visits_and_eats` **с данными** на основе запроса, который ищет пиццерию, где Дмитрий был 8 января и мог поесть дешевле 800. Условие прямо отсылает к упражнению из проекта про соединения.

```sql
CREATE MATERIALIZED VIEW mv_dmitriy_visits_and_eats AS
SELECT DISTINCT pz.name
FROM person p
         JOIN person_visits pv ON p.id = pv.person_id
         JOIN pizzeria pz ON pz.id = pv.pizzeria_id
         JOIN menu m ON m.pizzeria_id = pz.id
WHERE p.name = 'Dmitriy'
  AND pv.visit_date = '2022-01-08'
  AND m.price < 800
ORDER BY pz.name
WITH DATA;
```

```
SELECT 1
```

Вывод `SELECT 1` вместо привычного `CREATE VIEW` — не опечатка, а суть операции: запрос **выполнен**, и одна его строка записана на диск.

Содержимое:

```
    name
------------
 Papa Johns
(1 row)
```

Тот же ответ, что даёт этот запрос в проекте про соединения, — задания разных дней сошлись.

`WITH DATA` наполняет представление сразу. С `WITH NO DATA` оно создалось бы пустым, и любой запрос к нему падал бы с «materialized view has not been populated» до первого `REFRESH`.

`DISTINCT` нужен по той же причине, что и в исходном запросе: соединение с меню размножает строку заведения по числу подходящих позиций.

## ex07 — снимок догоняет таблицы

Нужно добавить Дмитрию ещё один визит 8 января, подходящий под условие представления, но в другую пиццерию, и обновить снимок. Прямые числа для ключа, человека и пиццерии запрещены.

```sql
INSERT INTO person_visits (id, person_id, pizzeria_id, visit_date)
VALUES ((SELECT max(id) + 1 FROM person_visits),
        (SELECT id FROM person WHERE name = 'Dmitriy'),
        (SELECT id FROM pizzeria WHERE name = 'DoDo Pizza'),
        '2022-01-08');

REFRESH MATERIALIZED VIEW mv_dmitriy_visits_and_eats;
```

```
INSERT 0 1
REFRESH MATERIALIZED VIEW
```

DoDo Pizza выбрана не произвольно — заведение должно удовлетворять трём условиям сразу: продавать пиццу дешевле 800 (сырная за 780), отличаться от результата `ex06` и не столкнуться с уникальным ключом `person_visits` по тройке «человек — пиццерия — дата».

Идентификатор вычисляется как `max(id) + 1`, человек и пиццерия ищутся по имени: последовательностей в модели нет, а литеральные числа запрещены условием.

**Что происходит между двумя командами — главное наблюдение дня.** Если выполнить только вставку и не обновлять снимок:

```
--- материализованное представление (данные на момент создания):
    name
------------
 Papa Johns
(1 row)

--- тот же запрос напрямую к таблицам (актуальные данные):
    name
------------
 DoDo Pizza
 Papa Johns
(2 rows)
```

Ответы разные, и оба верны — они относятся к разным моментам времени. Обычное представление такого расхождения не допускает по построению: оно каждый раз выполняет запрос заново. Материализованное платит за скорость тем, что данные в нём ровно такие, какими были при последнем обновлении.

После `REFRESH` расхождение закрывается:

```
    name
------------
 DoDo Pizza
 Papa Johns
(2 rows)
```

## ex08 — уборка

Нужно удалить все объекты, созданные за день.

```sql
DROP MATERIALIZED VIEW mv_dmitriy_visits_and_eats;

DROP VIEW v_price_with_discount;

DROP VIEW v_symmetric_union;

DROP VIEW v_generated_dates;

DROP VIEW v_persons_male;

DROP VIEW v_persons_female;
```

```
DROP MATERIALIZED VIEW
DROP VIEW
DROP VIEW
DROP VIEW
DROP VIEW
DROP VIEW
```

**Материализованное представление требует отдельной команды.** `DROP VIEW` на нём не работает:

```
ERROR:  "mv_dmitriy_visits_and_eats" is not a view
HINT:  Use DROP MATERIALIZED VIEW to remove a materialized view.
```

Для сервера это разные виды объектов, и разница не формальная: снимок хранит данные и занимает место, обычное представление не хранит ничего.

**Порядок удаления здесь свободен.** Он обратный созданию, но зависимостями не продиктован: ни одно представление дня не построено поверх другого. Проверено — удаление первого созданного (`v_persons_female`) проходит без ошибок, хотя следом идут пять других. Обратный порядок выбран как привычка, которая останется верной, когда зависимости появятся.

После упражнения в схеме не осталось ни одного представления, и все пять таблиц целы — это проверяется утверждениями в `run.sh check`.

## Как проверялись результаты

Помимо сверки с условием, у проекта есть собственный прогон с утверждениями — `./run.sh check`. Он поднимает временную базу, выполняет упражнения по порядку и проверяет двенадцать фактов:

```
  ok    ex00: 5 женщин / 4 мужчин
  ok    ex01: 9 имён
  ok    ex01: сортировка
  ok    ex02: 31 дата
  ok    ex02: тип DATE
  ok    ex03: 21 пропущенный день
  ok    ex03: первый день
  ok    ex04: (R-S) U (S-R)
  ok    ex05: Andrey / cheese pizza
  ok    ex06: снимок до обновления
  ok    ex07: снимок после REFRESH
  ok    ex08: представлений не осталось
  ok    ex08: пять таблиц целы
```

Что проверено сверх этого:

| Что | Как |
|---|---|
| образцы вывода из условия | посимвольная сверка — `ex01`, `ex02`, `ex03`, `ex05`; в `ex05` совпали обе строки образца, включая округление 1100 → 990 |
| `ex03` (21 день) | независимо: в журнале заняты ровно первые десять дней января |
| `ex04` (`{2, 8}`) | независимо: 2 января был один человек, 6 января другой, пересечение пусто |
| `ex06` | ответ сверен с тем же запросом из проекта про соединения — `Papa Johns` там и здесь |
| `ex07` | новый визит получил `id = 22` (`max + 1`), Дмитрий и DoDo Pizza найдены по имени, с уникальным ключом не столкнулся |
| разрыв между снимком и таблицами | показан явно: вставка без `REFRESH`, затем сравнение представления с прямым запросом |
| `DROP VIEW` на матпредставлении | выполнен намеренно — получена ошибка `is not a view` |
| независимость представлений | удаление первого созданного проходит, значит порядок в `ex08` не продиктован зависимостями |
| стартовое состояние базы | сборка «схема + DML соседнего проекта» сверена с базой предыдущего проекта по контрольным суммам всех пяти таблиц |
| отчёт против реальности | скриптом: SQL-блоки сверены с файлами проекта, блоки вывода — с прогоном на живой базе |

Главное различие дня — между «хранить запрос» и «хранить результат». Обычное представление не может устареть и ничего не стоит по месту, но каждый запрос к нему выполняется заново. Материализованное отвечает мгновенно, но между ним и таблицами появляется разрыв, невидимый изнутри запроса: обращение к снимку выглядит точно так же, как обращение к таблице, и отличить устаревшие данные от свежих по виду запроса нельзя. Единственное, что закрывает этот разрыв, — явный `REFRESH`, и решение, когда его выполнять, остаётся за тем, кто проектирует систему.
