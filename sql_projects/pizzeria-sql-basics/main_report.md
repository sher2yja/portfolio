# Отчёт: выборки по базе пиццерий

Десять упражнений на выборку данных из базы, описывающей людей, пиццерии, их меню, посещения и заказы. Каждое упражнение — один файл `day00_exNN.sql`.

Отчёт построен на фактическом выводе: все десять запросов прогнаны заново на локальном PostgreSQL, результаты вставлены как есть.

---

## Условия прогона

| Параметр | Значение |
|---|---|
| СУБД | PostgreSQL 16.14 (Ubuntu 24.04) |
| База | `sqlb1_basics`, схема и данные из `model.sql` поставки задания |
| Запуск | `./queries.sh` — все десять подряд, от обычного пользователя |
| Объём данных | 9 человек, 6 пиццерий, 18 позиций меню, 19 посещений, 20 заказов |

---

## Схема и данные

```
   person                          pizzeria
   ├─ id          PK               ├─ id       PK
   ├─ name                         ├─ name
   ├─ age              CHECK       └─ rating      CHECK 0 ≤ rating ≤ 5
   ├─ gender      female | male
   └─ address                              ▲              ▲
        ▲   ▲                              │              │
        │   └──────── person_visits ───────┘              │
        │             ├─ person_id   FK                   │
        │             ├─ pizzeria_id FK                   │
        │             └─ visit_date       UNIQUE(person, pizzeria, date)
        │
        └──────────── person_order                     menu
                      ├─ person_id  FK                 ├─ pizzeria_id FK ─┘
                      ├─ menu_id    FK ───────────────►├─ pizza_name
                      └─ order_date                    └─ price
```

Ограничение `CHECK (rating >= 0 AND rating <= 5)` на таблице `pizzeria` пригодится ниже: из-за него верхняя граница в `ex02` не может ничего отсечь.

## Ограничения по упражнениям

Часть заданий запрещает конструкции, которыми задача решалась бы в одну строку. Это и определяет вид запросов.

| Упражнение | Запрещено | Чем заменяется |
|---|---|---|
| `ex05` | `IN`, все виды `JOIN` | скалярный подзапрос в `SELECT`, перебор через `OR` |
| `ex06` | `IN`, все виды `JOIN` | то же плюс `CASE` |
| `ex09` | все виды `JOIN` | подзапрос в `FROM` и два скалярных подзапроса в `SELECT` |

В остальных упражнениях ограничений нет — там достаточно одной таблицы.

## ex00 — фильтр по одному условию

Имена и возраст людей из Казани.

```sql
SELECT name, age
FROM person
WHERE address = 'Kazan';
```

```
  name  | age
--------+-----
 Kate   |  33
 Denis  |  13
 Elvira |  45
(3 rows)
```

Сортировка не требовалась, поэтому порядок строк определяется планировщиком и на него нельзя рассчитывать.

## ex01 — два условия и сортировка

Женщины из Казани, по имени.

```sql
SELECT name, age
FROM person
WHERE address = 'Kazan' AND gender = 'female'
ORDER BY name;
```

```
  name  | age
--------+-----
 Elvira |  45
 Kate   |  33
(2 rows)
```

Из трёх казанцев остаются двое: Denis отсеивается по полу.

## ex02 — один результат двумя способами

Задание требует **два разных по синтаксису** запроса, возвращающих пиццерии с рейтингом от 3.5 до 5 включительно.

```sql
-- через операторы сравнения
SELECT name, rating
FROM pizzeria
WHERE rating >= 3.5 AND rating <= 5
ORDER BY rating;

-- через BETWEEN
SELECT name, rating
FROM pizzeria
WHERE rating BETWEEN 3.5 AND 5
ORDER BY rating;
```

Оба выдают одно и то же:

```
    name    | rating
------------+--------
 DinoPizza  |    4.2
 Dominos    |    4.3
 Pizza Hut  |    4.6
 Papa Johns |    4.9
(4 rows)
```

`BETWEEN` включает обе границы — в этом он равнозначен паре `>=` и `<=`. Разница проявляется, когда границы несимметричны: условие «от 3.5 включительно, но строго меньше 5» через `BETWEEN` уже не выразить.

Отсечены `Best Pizza` (2.3) и `DoDo Pizza` (3.2) — нижней границей. Верхняя граница в этих данных не отсекает ничего и отсечь не может: рейтинг выше 5 запрещён ограничением `CHECK` на уровне таблицы.

## ex03 — диапазон дат, `OR` и приоритет операторов

Уникальные идентификаторы людей, посетивших пиццерии с 6 по 9 января 2022 года либо посетивших пиццерию с идентификатором 2. Сортировка по убыванию.

```sql
SELECT DISTINCT person_id
FROM person_visits
WHERE (visit_date BETWEEN '2022-01-06' AND '2022-01-09') OR pizzeria_id = 2
ORDER BY person_id DESC;
```

```
 person_id
-----------
         9
         8
         7
         6
         5
         4
         2
(7 rows)
```

Скобки здесь меняют результат. `AND` связывает сильнее `OR`, и `BETWEEN` — это скрытый `AND`. Без скобок условие разобралось бы как «дата ≥ 6 января **и** (дата ≤ 9 января **или** `pizzeria_id = 2`)», и посещения второй пиццерии до 6 января в выборку не попали бы.

`DISTINCT` убирает повторы: один человек мог прийти в эти дни несколько раз.

## ex04 — вычисляемое поле и экранирование кавычек

Одна строка на человека вида `Anna (age:16,gender:'female',address:'Moscow')`.

```sql
SELECT (name || ' (age:' || age || ',gender:''' || gender || ''',address:''' || address || ''')') AS person_information
FROM person
ORDER BY person_information;
```

```
                    person_information
-----------------------------------------------------------
 Andrey (age:21,gender:'male',address:'Moscow')
 Anna (age:16,gender:'female',address:'Moscow')
 Denis (age:13,gender:'male',address:'Kazan')
 Dmitriy (age:18,gender:'male',address:'Samara')
 Elvira (age:45,gender:'female',address:'Kazan')
 Irina (age:21,gender:'female',address:'Saint-Petersburg')
 Kate (age:33,gender:'female',address:'Kazan')
 Nataly (age:30,gender:'female',address:'Novosibirsk')
 Peter (age:24,gender:'male',address:'Saint-Petersburg')
(9 rows)
```

Собираемая строка сама содержит одинарные кавычки, а в SQL это символ границы литерала. Внутри литерала кавычка удваивается, поэтому последовательность `'''` читается как «закрыть литерал, вставить кавычку, открыть литерал».

Оператор `||` склеивает значения; число `age` приводится к строке неявно.

**Здесь нашлось расхождение с эталоном — см. [раздел ниже](#что-нашёл-прогон).**

## ex05 — соединение таблиц без `JOIN`

Имена людей, заказавших позиции меню 13, 14 или 18 седьмого января 2022 года. `JOIN` и `IN` запрещены.

```sql
SELECT
    (SELECT name FROM person WHERE id = person_order.person_id) AS NAME
FROM person_order
WHERE person_order.order_date = '2022-01-07'
  AND (person_order.menu_id = 13 OR person_order.menu_id = 14 OR person_order.menu_id = 18);
```

```
  name
--------
 Denis
 Nataly
(2 rows)
```

Оба запрета выполняются буквально: имя достаётся скалярным подзапросом в списке `SELECT`, перечисление меню расписано через `OR`.

Скалярный подзапрос выполняется для каждой строки внешнего запроса и обязан вернуть ровно одно значение. Здесь это гарантировано тем, что `person.id` — первичный ключ: по равенству с ним не может найтись двух строк. Если бы условие подзапроса не было уникальным, запрос падал бы с ошибкой на конкретных данных, а на других — работал.

Результат сверен независимым запросом через `JOIN` — совпадает.

## ex06 — `CASE` вместо ветвления

К предыдущему запросу добавляется столбец `check_name`: истина, если имя — `Denis`.

```sql
SELECT
    (SELECT name FROM person WHERE id = person_order.person_id) AS NAME,
    CASE
        WHEN (SELECT name FROM person WHERE id = person_order.person_id) = 'Denis'
        THEN true
        ELSE false
    END AS check_name
FROM person_order
WHERE ...
```

```
  name  | check_name
--------+------------
 Denis  | t
 Nataly | f
(2 rows)
```

Подзапрос приходится повторять: сослаться на псевдоним `NAME` из того же списка `SELECT` нельзя — на момент вычисления `CASE` он ещё не существует. Именно этот повтор и делает наглядной цену отказа от `JOIN`: при соединении таблиц имя было бы обычным столбцом и вычислялось один раз.

`t` и `f` — то, как `psql` отображает тип `boolean`.

## ex07 — интервалы значений

Идентификатор, имя и возрастной интервал по трём правилам.

```sql
SELECT id, name,
    CASE
    WHEN (age >= 10 and age <= 20) THEN 'interval #1'
    WHEN (age > 20 and age < 24) THEN 'interval #2'
    ELSE 'interval #3'
END AS interval_info
FROM person
ORDER BY interval_info ASC;
```

```
 id |  name   | interval_info
----+---------+---------------
  1 | Anna    | interval #1
  4 | Denis   | interval #1
  9 | Dmitriy | interval #1
  6 | Irina   | interval #2
  2 | Andrey  | interval #2
  8 | Nataly  | interval #3
  5 | Elvira  | interval #3
  7 | Peter   | interval #3
  3 | Kate    | interval #3
(9 rows)
```

Условия `CASE` проверяются сверху вниз, срабатывает первое подошедшее — поэтому диапазоны не нужно делать взаимоисключающими явно. Сортировка идёт по вычисленной строке, а не по возрасту: внутри одного интервала порядок произвольный.

Возраст 24 у Peter попадает в третий интервал: второй ограничен строгим `< 24`.

**Здесь нашлось второе расхождение с эталоном — см. [раздел ниже](#что-нашёл-прогон).**

## ex08 — арифметика в условии

Все столбцы `person_order`, где идентификатор чётный.

```sql
SELECT *
FROM person_order
WHERE id % 2 = 0
ORDER BY id;
```

```
 id | person_id | menu_id | order_date
----+-----------+---------+------------
  2 |         1 |       2 | 2022-01-01
  4 |         2 |       9 | 2022-01-01
  6 |         4 |      16 | 2022-01-07
  8 |         4 |      18 | 2022-01-07
 10 |         4 |       7 | 2022-01-08
 12 |         5 |       7 | 2022-01-09
 14 |         7 |       3 | 2022-01-03
 16 |         7 |       4 | 2022-01-05
 18 |         8 |      14 | 2022-01-07
```

## ex09 — подзапрос в `FROM`

Имена людей и названия пиццерий по посещениям с 7 по 9 января, с обязательным подзапросом в части `FROM`. `JOIN` запрещён.

```sql
SELECT
    (SELECT name FROM person WHERE id = pv.person_id) AS person_name,
    (SELECT name FROM pizzeria WHERE id = pv.pizzeria_id) AS pizzeria_name
FROM (
    SELECT person_id, pizzeria_id
    FROM person_visits
    WHERE visit_date BETWEEN '2022-01-07' AND '2022-01-09'
    ) AS pv
ORDER BY person_name ASC, pizzeria_name DESC;
```

```
 person_name | pizzeria_name
-------------+---------------
 Denis       | DinoPizza
 Denis       | Best Pizza
 Dmitriy     | Papa Johns
 Dmitriy     | Best Pizza
 Elvira      | Dominos
 Elvira      | DinoPizza
 Irina       | Dominos
 Nataly      | Papa Johns
(8 rows)
```

Самое сложное упражнение набора: три таблицы связаны без единого `JOIN`. Подзапрос в `FROM` отбирает нужные посещения, два скалярных подзапроса в `SELECT` подставляют имена.

Псевдоним `pv` обязателен — подзапрос в `FROM` без имени PostgreSQL не принимает, и сослаться на его столбцы из внешнего запроса было бы нечем.

Сортировка разнонаправленная: по имени человека по возрастанию, по названию пиццерии по убыванию. Видно на парах строк — у Denis сначала `DinoPizza`, затем `Best Pizza`.

Результат сверен независимым запросом с двумя `JOIN` — совпадает построчно.

## Что нашёл прогон

Все десять запросов выполнялись без единой ошибки и до прогона выглядели готовыми. Сверка вывода с образцами из условия обнаружила два расхождения — оба в форматировании результата, то есть ровно в том, что проверяет ревьюер.

### ex04: не хватало пробела

| | |
|---|---|
| Образец в условии | `Anna (age:16,gender:'female',address:'Moscow')` |
| Выдавала сданная версия | `Anna(age:16,gender:'female',address:'Moscow')` |

В формуле склейки было `name || '(age:'` вместо `name || ' (age:'`. Запрос синтаксически безупречен, ошибок не выдаёт, разница — один символ в каждой из девяти строк.

### ex07: кавычки из текста задания попали в значение

| | |
|---|---|
| Псевдокод в условии (русская версия) | `вернуть «interval #1»` |
| Тот же псевдокод в английской версии | `return 'interval #1'` |
| Выдавала сданная версия | `«interval #1»` |

Кавычки-ёлочки в русском тексте задания — оформление, обозначающее строку, а не часть значения. Английская версия того же условия записывает эти строки в обычных одинарных кавычках, что снимает двусмысленность. В сданной версии ёлочки оказались внутри строкового литерала и попали в вывод.

### Почему это не ловится чтением

Оба дефекта невидимы при проверке кода: синтаксис верен, таблицы и столбцы существуют, типы сходятся, `psql` не выдаёт ни ошибки, ни предупреждения. Расхождение проявляется только при сравнении фактического вывода с образцом из условия — символ в символ.

Ни один из этих запросов не сломался бы и в продуктивной системе. Он просто отдавал бы данные в формате, отличном от согласованного, — а это тот класс дефектов, который обнаруживается позже всех и обычно уже потребителем данных.

## Что изменено при публикации

| Изменение | Причина |
|---|---|
| `ex04`: добавлен пробел перед `(age:` | вывод не совпадал с образцом из условия |
| `ex07`: убраны кавычки-ёлочки из возвращаемых строк | то же |
| `queries.sh`: убран `sudo -u postgres` | набор `SELECT`-ов не требует прав суперпользователя базы; публичный скрипт не должен просить root |
| `queries.sh`: имя базы вынесено в переменную `DB_NAME` | было зашито в код |
| `queries.sh`: пути строятся от каталога скрипта | прогон работает из любого каталога, а не только из корня проекта |
| `queries.sh`: добавлены `ON_ERROR_STOP=1`, проверка подключения и счётчик ошибок | без `ON_ERROR_STOP` psql печатает ошибку и завершается успешно — сломанный запрос в общем прогоне оставался незамеченным |
| Добавлены пояснения к `ex03`, `ex05`, `ex09` | запросы выглядят неоправданно громоздкими, если не знать про запрет `JOIN` и `IN` |

Логика запросов не менялась нигде, кроме двух исправленных расхождений: вывод остальных восьми упражнений до и после правок совпадает построчно.

## Итог

Десять упражнений отрабатывают, вывод каждого приведён выше. Каждый результат дополнительно сверен независимой проверкой: `ex02`, `ex05`, `ex06` и `ex09` — запросами через `JOIN`, запрещённый в самих упражнениях; `ex04` — сверкой всех девяти строк с образцом по регулярному выражению; остальные — агрегатами и контрольными подсчётами. Расхождений нет.

Главное же вынесено не из самих выборок, а из запретов. `JOIN` и `IN` — конструкции, которые обычно пишут не задумываясь; заданиями `ex05`, `ex06` и `ex09` они отняты, и связывать таблицы приходится вручную. Становится видно, что `JOIN` соединяет данные за один проход планировщика, тогда как скалярный подзапрос выполняется заново для каждой строки результата — и что в `ex06` из-за отсутствия соединения один и тот же подзапрос приходится писать дважды.

Второй вывод — про проверку. Запрос, который выполняется без ошибок, ещё не является правильным: два из десяти отдавали данные в формате, отличном от требуемого, и заметить это можно было только прогоном с последующей сверкой вывода.
