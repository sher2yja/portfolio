# 🍕 SQL: выборки по базе пиццерий

### 📌 Обзор проекта

Десять запросов к реляционной базе из пяти связанных таблиц: люди, пиццерии, меню, посещения и заказы. Фильтрация по датам и диапазонам, вычисляемые столбцы, ветвление через `CASE`, подзапросы в `SELECT` и в `FROM`.

Интерес здесь не в самих выборках, а в ограничениях. Часть заданий **запрещает `JOIN` и `IN`** — те самые конструкции, которыми такие задачи решаются в один приём. Связывать таблицы приходится подзапросами вручную, и становится видно, что именно `JOIN` делает за разработчика.

### 🏗 Схема базы

```
   person                          pizzeria
   ├─ id          PK               ├─ id       PK
   ├─ name                         ├─ name
   ├─ age              CHECK       └─ rating      CHECK 0 ≤ rating ≤ 5
   ├─ gender      female | male
   └─ address                              ▲              ▲
        ▲   ▲                              │              │
        │   │                              │              │
        │   └──────── person_visits ───────┘              │
        │             ├─ id          PK                   │
        │             ├─ person_id   FK                   │
        │             ├─ pizzeria_id FK                   │
        │             └─ visit_date       UNIQUE(person, pizzeria, date)
        │
        └──────────── person_order                     menu
                      ├─ id         PK                 ├─ id          PK
                      ├─ person_id  FK                 ├─ pizzeria_id FK ─┘
                      ├─ menu_id    FK ───────────────►├─ pizza_name
                      └─ order_date                    └─ price

   9 человек · 6 пиццерий · 18 позиций меню · 19 посещений · 20 заказов
```

Две таблицы связей: `person_visits` фиксирует, кто куда заходил, `person_order` — кто что заказывал. Пиццерия у заказа известна не напрямую, а через меню: `person_order → menu → pizzeria`. Именно из-за этой цепочки задания с заказами оказываются сложнее заданий с посещениями.

### 🚀 Что интересного в запросах

* **Запрет `JOIN` — не каприз, а суть упражнения.** В `ex05`, `ex06` и `ex09` соединение таблиц собирается из подзапросов: имя человека достаётся скалярным подзапросом в списке `SELECT`, отбор строк — подзапросом в `FROM`. Такой запрос выполняется для каждой строки внешнего результата, тогда как `JOIN` планировщик соединяет за один проход. Ограничение показывает разницу нагляднее любого объяснения.

* **Запрет `IN` заставляет расписывать перебор через `OR`.** `menu_id = 13 OR menu_id = 14 OR menu_id = 18` вместо `menu_id IN (13, 14, 18)`. Результат тот же, но видно, во что `IN` разворачивается.

* **Скобки в `ex03` меняют результат.** Условие «посетил с 6 по 9 января **или** посетил пиццерию 2» без скобок разберётся иначе: `AND` связывает сильнее `OR`, и посещения второй пиццерии до 6 января потерялись бы.

* **Два разных запроса на одну задачу в `ex02`.** Сравнение `rating >= 3.5 AND rating <= 5` и `BETWEEN 3.5 AND 5` — задание требует именно двух вариантов. `BETWEEN` короче и включает обе границы; явные сравнения гибче, когда границы несимметричны.

* **`CASE` вместо ветвления.** В `ex06` и `ex07` условная логика живёт внутри запроса: условия проверяются сверху вниз, срабатывает первое подошедшее.

* **Экранирование кавычек в `ex04`.** Вычисляемая строка сама содержит одинарные кавычки, поэтому внутри литерала они удваиваются: последовательность `'''` — это закрывающая кавычка, экранированная кавычка и открывающая.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `ex00/` … `ex09/` | по одному файлу `day00_exNN.sql` на упражнение |
| `queries.sh` | последовательный прогон всех десяти на одной базе |
| `main_report.md` | разбор каждого запроса с фактическим выводом |

Схема и тестовые данные (`model.sql`) выданы курсом и в репозиторий не входят — без них запросы выполнить не на чем. Условия заданий тоже не публикуются, их формулировки пересказаны в отчёте своими словами.

---

### ▶️ Запуск

```bash
createdb sqlb1_basics
psql -d sqlb1_basics -f model.sql     # файл из поставки задания, в репозитории его нет
./queries.sh                          # все десять упражнений подряд
```

Имя базы переопределяется переменной окружения: `DB_NAME=my_db ./queries.sh`. Права суперпользователя не нужны — запросы читают данные и ничего не меняют.
