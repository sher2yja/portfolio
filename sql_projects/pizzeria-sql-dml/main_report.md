# Отчёт: изменение данных

Четырнадцать упражнений, из которых семь читают данные, а семь их меняют. Каждое упражнение — один файл `day03_exNN.sql`.

Отчёт построен на фактическом выводе: все четырнадцать запросов прогнаны заново на локальном PostgreSQL, результаты вставлены как есть. Для `INSERT`, `UPDATE` и `DELETE` одного вывода мало — `INSERT 0 2` не сообщает, что именно вставлено, — поэтому у каждого такого упражнения показано состояние базы после него.

---

## Условия прогона

| Параметр | Значение |
|---|---|
| СУБД | PostgreSQL 16.15 (Ubuntu 24.04) |
| База | схема и данные из `model.sql` поставки задания |
| Запуск | `./run.sh all` — база пересоздаётся, затем все четырнадцать подряд |
| Объём данных | 9 человек, 6 пиццерий, 18 позиций меню, 19 посещений, 20 заказов |

---

## Чем DML отличается от запроса

Первые тринадцать упражнений двух предыдущих дней возвращали ответ и не оставляли следа. Здесь семь последних оставляют след, и из этого следует всё остальное.

### Повторный запуск — не проверка

```
   SELECT                          INSERT / UPDATE / DELETE
   ┌──────────────┐                ┌──────────────┐
   │  база        │──► ответ       │  база (v1)   │──► база (v2)
   │  не меняется │                └──────────────┘
   └──────────────┘                прогнать дважды — получить v3,
   прогнать дважды —               а не проверить v2
   тот же ответ
```

Второй запуск вставки падает на дубле первичного ключа, второй `UPDATE` уценивает уже уценённое, второй `DELETE` не находит чего удалять. Ни один из трёх исходов не говорит о том, верен ли запрос.

### Цепочка ex07–ex13 кумулятивна

```
   model.sql ──► ex07 ──► ex08 ──► ex09 ──► ex10 ──► ex11 ──► ex12 ──► ex13
   18 позиций    +greek   +sicilian  +2      +2      цена     +9       −9 заказов
   меню          пицца    пицца    визита  заказа   −10%    заказов   −greek
```

Каждый шаг написан в расчёте на предыдущие: `ex10` заказывает пиццу, добавленную в `ex08`, `ex11` уценяет добавленную в `ex07`, `ex13` удаляет заказы из `ex12`. Проверить `ex11` в отрыве от цепочки невозможно — его просто не на чем выполнить.

Поэтому `run.sh` перед запуском упражнения `N` пересоздаёт базу из `model.sql` и проигрывает `ex07`…`ex(N-1)`. Это не удобство, а условие корректности проверки.

### Ключи назначаются вручную

В модели нет ни `serial`, ни `identity`, ни `default nextval(...)`. Значение первичного ключа задаёт тот, кто вставляет строку, и задания это эксплуатируют: сначала разрешают написать число прямо (`ex07`), а начиная со следующего — запрещают, вынуждая вычислять ключ подзапросом.

## Ограничения по упражнениям

| Упражнение | Запрещено | Чем заменяется |
|---|---|---|
| `ex01` | любые виды `JOIN` | подзапрос с `NOT IN` |
| `ex03` | операторы множеств без `ALL` | `EXCEPT ALL`, `UNION ALL` — арифметика мультимножеств |
| `ex04` | операторы множеств с `ALL` | `EXCEPT`, `UNION` — множества без дубликатов |
| `ex08`–`ex10`, `ex12` | прямые числа для первичных ключей и ссылки на пиццерию | `max(id) + 1`, `row_number()`, подзапрос по названию |
| `ex12` | оконные функции, отдельные `INSERT` | `generate_series(...)` в шаблоне `INSERT ... SELECT` |

Соблюдение проверено отдельно, поиском по текстам решений: запрос, дающий верный результат запрещённым способом, задание не проходит.

## ex00 — цены для Кейт

Нужны названия пицц, цены, заведения и даты посещений — для Кейт и только в диапазоне от 800 до 1000.

```sql
SELECT m.pizza_name,
       m.price,
       pz.name AS pizzeria_name,
       pv.visit_date
FROM person_visits pv
         JOIN person p ON p.id = pv.person_id
         JOIN pizzeria pz ON pz.id = pv.pizzeria_id
         JOIN menu m ON m.pizzeria_id = pz.id
WHERE p.name = 'Kate'
  AND m.price BETWEEN 800 AND 1000
ORDER BY m.pizza_name, m.price, pz.name;
```

```
   pizza_name    | price | pizzeria_name | visit_date
-----------------+-------+---------------+------------
 cheese pizza    |   950 | DinoPizza     | 2022-01-04
 pepperoni pizza |   800 | Best Pizza    | 2022-01-03
 pepperoni pizza |   800 | DinoPizza     | 2022-01-04
 sausage pizza   |  1000 | DinoPizza     | 2022-01-04
 supreme pizza   |   850 | Best Pizza    | 2022-01-03
(5 rows)
```

Меню подключается к пиццерии, а не к заказу: спрашивают, что Кейт **могла** взять там, где была, а не что она взяла. Журнал заказов в запросе не участвует.

Кейт заходила в два заведения: Best Pizza 3 января и DinoPizza 4 января. В их меню девять позиций, в диапазон попадают пять — обе границы включительно, поэтому пицца ровно за 800 и ровно за 1000 в ответе есть, а сырная за 700 из Best Pizza — нет.

## ex01 — забытые позиции меню

Нужны идентификаторы позиций, которые никто ни разу не заказывал. Любые соединения запрещены.

```sql
SELECT id AS menu_id
FROM menu
WHERE id NOT IN (SELECT menu_id FROM person_order)
ORDER BY menu_id;
```

```
 menu_id
---------
       5
      10
      11
      12
      15
(5 rows)
```

Разность множеств, выраженная подзапросом. `NOT IN` сравнивает каждый идентификатор меню со всем списком заказанных.

**Запрос безопасен ровно потому, что `person_order.menu_id` объявлен `NOT NULL`.** Появись в подзапросе хоть один `NULL`, условие `id NOT IN (...)` стало бы неопределённым сразу для всех строк — не ложным, а именно неопределённым, — и запрос молча вернул бы пустой результат. `NOT EXISTS` этой ловушке не подвержен; условие разрешает оба варианта, и здесь ограничение таблицы делает более короткий безопасным.

Из 18 позиций меню не заказывали пять.

## ex02 — те же позиции с названиями

То же множество, но с названием пиццы, ценой и заведением. Ограничение на соединения снято.

```sql
SELECT m.pizza_name,
       m.price,
       pz.name AS pizzeria_name
FROM menu m
         JOIN pizzeria pz ON pz.id = m.pizzeria_id
WHERE m.id NOT IN (SELECT menu_id FROM person_order)
ORDER BY m.pizza_name, m.price;
```

```
  pizza_name   | price | pizzeria_name
---------------+-------+---------------
 cheese pizza  |   700 | Papa Johns
 cheese pizza  |   780 | DoDo Pizza
 cheese pizza  |   950 | DinoPizza
 sausage pizza |   950 | Papa Johns
 supreme pizza |   850 | DoDo Pizza
(5 rows)
```

Условие не изменилось ни на символ — добавилось только соединение с `pizzeria`, чтобы назвать заведение. Пара упражнений показывает разницу между запретом и невозможностью: тот же ответ достижим обоими способами, запрет в `ex01` заставляет выбрать тот, что без `JOIN`.

Три из пяти забытых позиций — сырная пицца в трёх разных заведениях.

## ex03 — перевес визитов по полу

Нужны пиццерии, которые чаще посещали женщины или чаще мужчины. Условие требует сохранять дубликаты — то есть использовать `ALL`.

```sql
(SELECT pz.name AS pizzeria_name
 FROM person_visits pv
          JOIN person p ON p.id = pv.person_id
          JOIN pizzeria pz ON pz.id = pv.pizzeria_id
 WHERE p.gender = 'female'
 EXCEPT ALL
 SELECT pz.name
 FROM person_visits pv
          JOIN person p ON p.id = pv.person_id
          JOIN pizzeria pz ON pz.id = pv.pizzeria_id
 WHERE p.gender = 'male')
UNION ALL
(SELECT pz.name
 FROM person_visits pv
          JOIN person p ON p.id = pv.person_id
          JOIN pizzeria pz ON pz.id = pv.pizzeria_id
 WHERE p.gender = 'male'
 EXCEPT ALL
 SELECT pz.name
 FROM person_visits pv
          JOIN person p ON p.id = pv.person_id
          JOIN pizzeria pz ON pz.id = pv.pizzeria_id
 WHERE p.gender = 'female')
ORDER BY pizzeria_name;
```

```
 pizzeria_name
---------------
 Best Pizza
 Dominos
 Papa Johns
(3 rows)
```

`ALL` здесь не оптимизация и не «то же самое, но с повторами» — на нём держится весь смысл. Каждая строка выборки это один визит, и кратность названия равна числу визитов. `EXCEPT ALL` вычитает кратности поштучно, поэтому разность показывает **перевес**, а не факт «ходили только сюда».

Проверка по данным — визиты в разбивке по полам:

| Пиццерия | женщины | мужчины | перевес |
|---|---|---|---|
| Best Pizza | 1 | 2 | мужчины, +1 |
| DinoPizza | 2 | 2 | нет |
| Dominos | 3 | 2 | женщины, +1 |
| Papa Johns | 2 | 1 | женщины, +1 |
| Pizza Hut | 2 | 2 | нет |

Три ненулевых перевеса — три строки ответа. Заведения с равным счётом обе разности гасят.

## ex04 — заказы только женщин и только мужчин

Нужно объединение двух множеств: пиццерии, где заказывали исключительно женщины, и те, где исключительно мужчины. Дубликаты, наоборот, запрещены.

```sql
(SELECT pz.name AS pizzeria_name
 FROM person_order po
          JOIN person p ON p.id = po.person_id
          JOIN menu m ON m.id = po.menu_id
          JOIN pizzeria pz ON pz.id = m.pizzeria_id
 WHERE p.gender = 'female'
 EXCEPT
 SELECT pz.name
 FROM person_order po
          JOIN person p ON p.id = po.person_id
          JOIN menu m ON m.id = po.menu_id
          JOIN pizzeria pz ON pz.id = m.pizzeria_id
 WHERE p.gender = 'male')
UNION
(SELECT pz.name
 FROM person_order po
          JOIN person p ON p.id = po.person_id
          JOIN menu m ON m.id = po.menu_id
          JOIN pizzeria pz ON pz.id = m.pizzeria_id
 WHERE p.gender = 'male'
 EXCEPT
 SELECT pz.name
 FROM person_order po
          JOIN person p ON p.id = po.person_id
          JOIN menu m ON m.id = po.menu_id
          JOIN pizzeria pz ON pz.id = m.pizzeria_id
 WHERE p.gender = 'female')
ORDER BY pizzeria_name;
```

```
 pizzeria_name
---------------
 Papa Johns
(1 row)
```

Каркас тот же, что в `ex03`, отличие в одном слове — и ответ другой по существу. Без `ALL` обе стороны сворачиваются в множества названий, и разность означает «этот пол заказывал, другой не заказывал вовсе». Это и есть «только» из условия.

Заказы по полам:

| Пиццерия | женщины | мужчины |
|---|---|---|
| Best Pizza | 1 | 4 |
| DinoPizza | 2 | 3 |
| Dominos | 1 | 3 |
| Papa Johns | 2 | 0 |
| Pizza Hut | 2 | 2 |

Papa Johns — единственное заведение, где заказы делал ровно один пол. Чисто мужских нет, поэтому вторая половина объединения пуста, и ответ состоит из одной строки.

Пара `ex03`/`ex04` — самое ценное место дня: два почти одинаковых текста, дающих разные ответы, и различие видно только если помнить, что `ALL` переключает семантику с множеств на мультимножества.

## ex05 — заходил, но не заказывал

Нужны пиццерии, которые Андрей посещал, но заказов оттуда не делал.

```sql
SELECT pz.name AS pizzeria_name
FROM person_visits pv
         JOIN person p ON p.id = pv.person_id
         JOIN pizzeria pz ON pz.id = pv.pizzeria_id
WHERE p.name = 'Andrey'
EXCEPT
SELECT pz.name
FROM person_order po
         JOIN person p ON p.id = po.person_id
         JOIN menu m ON m.id = po.menu_id
         JOIN pizzeria pz ON pz.id = m.pizzeria_id
WHERE p.name = 'Andrey'
ORDER BY pizzeria_name;
```

```
 pizzeria_name
---------------
 Pizza Hut
(1 row)
```

Упражнение существует ради главной особенности модели: **журналы визитов и заказов не связаны между собой**. Нет ни общего внешнего ключа, ни связующей таблицы, и «был, но не заказал» — не строка в таблице, а разность двух множеств.

Обратите внимание на асимметрию путей. Слева достаточно двух соединений: визит ссылается на пиццерию напрямую. Справа их три — заказ ссылается на позицию меню, и только она ведёт к заведению.

Андрей заходил в Dominos и Pizza Hut, а заказывал дважды, оба раза из Dominos. Разность оставляет Pizza Hut.

## ex06 — одинаковые цены в разных пиццериях

Нужны совпадающие названия пицц с одинаковой ценой, но из разных заведений. Имена колонок заданы условием.

```sql
SELECT m1.pizza_name,
       pz1.name AS pizzeria_name_1,
       pz2.name AS pizzeria_name_2,
       m1.price
FROM menu m1
         JOIN menu m2 ON m1.pizza_name = m2.pizza_name
    AND m1.price = m2.price
    AND m1.pizzeria_id > m2.pizzeria_id
         JOIN pizzeria pz1 ON pz1.id = m1.pizzeria_id
         JOIN pizzeria pz2 ON pz2.id = m2.pizzeria_id
ORDER BY m1.pizza_name;
```

```
   pizza_name    | pizzeria_name_1 | pizzeria_name_2 | price
-----------------+-----------------+-----------------+-------
 cheese pizza    | Best Pizza      | Papa Johns      |   700
 pepperoni pizza | DinoPizza       | Best Pizza      |   800
 supreme pizza   | Best Pizza      | DoDo Pizza      |   850
(3 rows)
```

Самосоединение по паре «название + цена». Третье условие, `m1.pizzeria_id > m2.pizzeria_id`, делает две вещи сразу: отсекает строку, соединённую сама с собой — у неё название и цена, разумеется, совпадают, — и оставляет от каждой пары заведений одну строку вместо зеркальных двух. Со строгим неравенством результат содержит три строки, с `<>` — шесть.

Контрольная группировка по паре «название + цена» даёт ровно три пары, встречающиеся более чем в одном заведении, — столько же, сколько строк в ответе.

## ex07 — новая пицца в меню

Нужно добавить «greek pizza» с `id = 19` по цене 800 в Dominos (`pizzeria_id = 2`). Оба числа названы в условии дословно.

```sql
INSERT INTO menu (id, pizzeria_id, pizza_name, price)
VALUES (19, 2, 'greek pizza', 800);
```

```
INSERT 0 1
```

`INSERT 0 1` — это не «вставлено 0 или 1». Первое число `oid` вставленной строки, давно всегда нулевой, второе — число строк. То есть вставлена одна.

Что появилось в таблице:

```
 id | pizzeria_id |  pizza_name   | price
----+-------------+---------------+-------
 19 |           2 | greek pizza   |   800
 18 |           5 | supreme pizza |   850
```

Единственное упражнение дня, где литеральные идентификаторы разрешены, — дальше они запрещены, и та же по смыслу вставка выглядит совсем иначе. Ключ приходится указывать руками, потому что последовательности к таблице не привязаны: `id` объявлен просто `bigint primary key`.

## ex08 — та же вставка без литеральных id

Добавить «sicilian pizza» за 900 в Dominos, но идентификатор вычислить как «максимальный существующий + 1», а ссылку на заведение получить подзапросом.

```sql
INSERT INTO menu (id, pizzeria_id, pizza_name, price)
SELECT (SELECT max(id) + 1 FROM menu),
       (SELECT id FROM pizzeria WHERE name = 'Dominos'),
       'sicilian pizza',
       900;
```

```
INSERT 0 1
```

```
 id | pizzeria |   pizza_name   | price
----+----------+----------------+-------
 20 | Dominos  | sicilian pizza |   900
 19 | Dominos  | greek pizza    |   800
```

Форма `INSERT ... SELECT` вместо `VALUES` выбрана не ради стиля: подзапросы допустимы и в `VALUES`, но `SELECT` собирает всю строку одним выражением и без переписывания масштабируется на вставку многих строк — что и понадобится в `ex09`.

**`max(id) + 1` честен ровно в тех условиях, в которых выполняется задание.** В базе с параллельной записью это гонка: два сеанса прочитают один и тот же максимум и получат конфликт по первичному ключу. Правильный инструмент — последовательность, но в этой модели её нет, и задание требует обойтись тем, что есть. Полезно понимать, что упражнение показывает приём, а не рекомендацию.

Идентификатор Dominos в результате тот же самый (2), что был написан числом в `ex07`, — разница не в значении, а в том, что запрос больше не сломается, если справочник пересоберут с другими ключами.

## ex09 — новые визиты

Зафиксировать посещение Dominos Денисом и Ириной 24 февраля 2022 года. Прямые числа для ключей и ссылки на пиццерию по-прежнему запрещены.

```sql
INSERT INTO person_visits (id, person_id, pizzeria_id, visit_date)
SELECT (SELECT max(id) FROM person_visits) + row_number() OVER (ORDER BY p.id),
       p.id,
       (SELECT id FROM pizzeria WHERE name = 'Dominos'),
       '2022-02-24'
FROM person p
WHERE p.name IN ('Denis', 'Irina');
```

```
INSERT 0 2
```

```
 id | name  | pizzeria | visit_date
----+-------+----------+------------
 21 | Irina | Dominos  | 2022-02-24
 20 | Denis | Dominos  | 2022-02-24
```

Строк вставляется две, а ключ у каждой должен быть свой — `max(id) + 1` для обеих дал бы одно значение и падение на первичном ключе. Нумерацию берёт на себя `row_number()`: он нумерует строки выборки, и максимум таблицы плюс номер даёт 20 и 21.

Оконные функции здесь разрешены — запрещены они только в `ex12`, и там то же самое приходится делать иначе.

Людей отбирает `WHERE p.name IN (...)`, а не список идентификаторов: имена в условии названы, числа — нет.

## ex10 — новые заказы

Зарегистрировать заказы тех же двоих на «sicilian pizza» той же датой.

```sql
INSERT INTO person_order (id, person_id, menu_id, order_date)
SELECT (SELECT max(id) FROM person_order) + row_number() OVER (ORDER BY p.id),
       p.id,
       (SELECT id FROM menu WHERE pizza_name = 'sicilian pizza'),
       '2022-02-24'
FROM person p
WHERE p.name IN ('Denis', 'Irina');
```

```
INSERT 0 2
```

```
 id | name  |   pizza_name   | order_date
----+-------+----------------+------------
 22 | Irina | sicilian pizza | 2022-02-24
 21 | Denis | sicilian pizza | 2022-02-24
```

Схема та же, что в `ex09`, но ссылка ведёт не на заведение, а на позицию меню — заказ связан именно с ней, и это ровно та особенность модели, вокруг которой строились предыдущие дни.

Позиция ищется по названию, потому что её идентификатор заранее неизвестен: он появился в `ex08` как `max(id) + 1` и в тексте задания не назван. Здесь видно, зачем предыдущее упражнение запрещало литералы — цепочка держится на том, что каждый следующий шаг находит нужное значение сам.

## ex11 — скидка 10%

Уменьшить цену «greek pizza» на 10% от текущего значения.

```sql
UPDATE menu
SET price = price - (price * 0.1)
WHERE pizza_name = 'greek pizza';
```

```
UPDATE 1
```

Цена до и после:

```
 id | pizza_name  | price          id | pizza_name  | price
----+-------------+-------        ----+-------------+-------
 19 | greek pizza |   800          19 | greek pizza | 720.0
```

**Запрос не идемпотентен, и это видно прямо в его тексте.** `price` в правой части — значение до изменения, поэтому второй запуск даст скидку от уже уценённого: 800 → 720 → 648. Для DML это нормально и ожидаемо, но означает, что перепрогонять цепочку по кусочкам нельзя — база к этому моменту должна быть ровно в том состоянии, которое оставил `ex10`.

**Цена стала `720.0`, а не `720`.** Столбец объявлен как `numeric` без указания масштаба, а литерал `0.1` имеет масштаб 1; умножение даёт `80.0`, вычитание сохраняет масштаб самого точного операнда — получается `720.0`. Значение верное и в сравнениях ведёт себя как 720, отличается только запись, и рядом с целыми ценами остальных позиций она бросается в глаза. Условие формата не оговаривает; привести к целому можно было бы округлением, но это уже правка сверх задания.

## ex12 — заказ каждому клиенту

Зарегистрировать заказ «greek pizza» для всех девяти клиентов 25 февраля. Запрещены оконные функции и отдельные `INSERT`, требуется шаблон `INSERT ... SELECT` с `generate_series(...)`.

```sql
INSERT INTO person_order (id, person_id, menu_id, order_date)
SELECT (SELECT max(id) FROM person_order) + gs.num,
       p.id,
       (SELECT id FROM menu WHERE pizza_name = 'greek pizza'),
       '2022-02-25'
FROM generate_series(1, (SELECT count(*) FROM person)) AS gs(num)
         JOIN person p ON p.id = gs.num;
```

```
INSERT 0 9
```

```
 id |  name   | pizza_name  | order_date
----+---------+-------------+------------
 23 | Anna    | greek pizza | 2022-02-25
 24 | Andrey  | greek pizza | 2022-02-25
 25 | Kate    | greek pizza | 2022-02-25
 26 | Denis   | greek pizza | 2022-02-25
 27 | Elvira  | greek pizza | 2022-02-25
 28 | Irina   | greek pizza | 2022-02-25
 29 | Peter   | greek pizza | 2022-02-25
 30 | Nataly  | greek pizza | 2022-02-25
 31 | Dmitriy | greek pizza | 2022-02-25
(9 rows)
```

Запреты этого упражнения отбирают оба привычных способа: девять отдельных вставок и `row_number()` из `ex09`. Остаётся взять номер строки у самого генератора ряда — `generate_series(1, 9)` выдаёт 1…9, и `max(id) + gs.num` назначает девять непересекающихся ключей. Верхняя граница ряда тоже вычисляется, а не пишется числом: `(SELECT count(*) FROM person)`.

**У решения есть скрытое допущение.** Соединение идёт по равенству `p.id = gs.num`, то есть номер строки ряда используется как идентификатор человека. Это верно, пока идентификаторы идут подряд от единицы, — в этой базе так и есть, проверено: `min = 1, max = 9, count = 9`. Появись в `person` пропуск, часть клиентов молча осталась бы без заказа: ошибки не будет, строк просто вставится меньше. Устойчивее было бы нумеровать саму выборку людей, но именно это здесь и запрещено.

## ex13 — откат акции

Двумя запросами удалить заказы из `ex12` по дате, а затем убрать «greek pizza» из меню.

```sql
DELETE
FROM person_order
WHERE order_date = '2022-02-25';

DELETE
FROM menu
WHERE pizza_name = 'greek pizza';
```

```
DELETE 9
DELETE 1
```

Состояние базы после всей цепочки:

```
 заказов_25_фев | greek_в_меню | всего_в_меню | всего_заказов
----------------+--------------+--------------+---------------
              0 |            0 |           19 |            22
```

**Порядок двух удалений задаёт не стиль, а внешний ключ.** `person_order.menu_id` ссылается на `menu.id` без `ON DELETE`, поэтому попытка убрать позицию меню, на которую ещё ссылаются заказы, прерывается. Проверено запуском в обратном порядке:

```
ERROR:  update or delete on table "menu" violates foreign key constraint "fk_order_menu_id"
DETAIL:  Key (id)=(19) is still referenced from table "person_order".
```

**Удаление по дате безопасно только потому, что дата чужих строк не задевает.** Условие требует удалять именно по `order_date`, и это работает, поскольку в исходных данных заказов на 25 февраля нет — под условие попадают ровно девять строк из `ex12`. Проверено до запуска: `select count(*) ... where order_date = '2022-02-25'` на чистой базе возвращает ноль. Будь там хоть один настоящий заказ, он бы тоже исчез, и запрос об этом не сообщил бы.

От цепочки в базе остаётся след: 19 позиций меню вместо исходных 18 (осталась «sicilian pizza»), 21 визит вместо 19 и 22 заказа вместо 20. Так и задумано — `ex13` откатывает только акцию с греческой пиццей.

## Итог

Все четырнадцать упражнений отрабатывают, вывод каждого приведён выше и получен на живой базе. Расхождений с образцами из условия нет.

Главное, что показывает этот день, — разница между вопросом и действием. Запрос можно прогнать сколько угодно раз и сравнить ответ с ожидаемым; изменение данных проверяется иначе, потому что второй запуск проверяет уже другую базу. Отсюда всё остальное: пересоздание базы как часть проверки, порядок операций, продиктованный внешними ключами, и внимание к тому, чего в выводе не видно, — `INSERT 0 9` одинаково выглядит и когда вставлено то, что нужно, и когда не то.
