# 🍕 SQL: изменение данных

### 📌 Обзор проекта

Четырнадцать запросов к той же базе пиццерий, что и в [выборках](../pizzeria-sql-basics), [множествах](../pizzeria-sql-sets) и [соединениях](../pizzeria-sql-joins). Проект делится пополам, и вторая половина принципиально отличается от всего, что было раньше.

Первые семь упражнений — чтение: разность множеств без `JOIN`, сравнение мультимножеств, поиск одинаковых цен самосоединением. Последние семь — `INSERT`, `UPDATE`, `DELETE`, и они **меняют данные и накапливаются**: каждое написано в расчёте на то, что все предыдущие уже применены. Запрос перестаёт быть вопросом к базе и становится действием над ней, у которого есть побочный эффект и порядок.

Отсюда главное практическое отличие: проверить решение повторным запуском больше нельзя. Вторая вставка упадёт на дубле первичного ключа, второй `UPDATE` уценит уже уценённое, а `DELETE` во второй раз не найдёт чего удалять. Единственный честный способ проверки — пересоздать базу и проиграть цепочку с начала, и ровно это делает `run.sh`.

### 🏗 Схема базы

```
   person                          pizzeria
   ├─ id          PK               ├─ id       PK
   ├─ name                         ├─ name
   ├─ age              CHECK       └─ rating      CHECK 0 ≤ rating ≤ 5
   ├─ gender      female | male
   └─ address     город                    ▲              ▲
        ▲   ▲                              │              │
        │   │                              │              │
        │   └──────── person_visits ───────┘              │
        │             ├─ id          PK                   │
        │             ├─ person_id   FK                   │
        │             ├─ pizzeria_id FK                   │
        │             └─ visit_date       UNIQUE(person, pizzeria, date)
        │
        └──────────── person_order                     menu
                      ├─ id         PK                 ├─ id          PK
                      ├─ person_id  FK                 ├─ pizzeria_id FK ─┘
                      ├─ menu_id    FK ───────────────►├─ pizza_name
                      └─ order_date                    └─ price

   9 человек · 6 пиццерий · 18 позиций меню · 19 посещений · 20 заказов
```

Для DML в этой схеме важны три вещи, которых не было видно, пока данные только читали:

* **Последовательностей нет.** Ни `serial`, ни `identity`, ни `default nextval(...)` — значение первичного ключа назначает тот, кто вставляет строку. Отсюда `max(id) + 1` в решениях.
* **Внешние ключи без `ON DELETE`.** Удалить строку, на которую кто-то ссылается, нельзя — база прервёт операцию. Это определяет порядок двух удалений в `ex13`.
* **У `person_visits` есть уникальный ключ** по тройке «человек — пиццерия — дата». Повторный прогон вставки визитов падает не на первичном ключе, а на нём.

---

### 🚀 Что интересного в запросах

* **`ALL` — это не «то же самое, но с дубликатами».** `ex03` и `ex04` построены на одном каркасе: разность в обе стороны, потом объединение. В `ex03` операторы идут с `ALL`, в `ex04` — без, и это два разных вопроса. С `ALL` кратность строки означает число визитов, и разность даёт **перевес одного пола над другим**. Без `ALL` стороны сворачиваются в множества названий, и разность отвечает «заказывал только этот пол». Ответы не совпадают ни по смыслу, ни по строкам.

* **`NOT IN` безопасен ровно потому, что столбец `NOT NULL`.** В `ex01` любые `JOIN` запрещены, и разность выражается подзапросом. Появись в `person_order.menu_id` хоть один `NULL` — сравнение стало бы неопределённым для всех строк сразу, и запрос молча вернул бы пусто. Ограничение таблицы здесь часть корректности запроса.

* **«Был, но не заказывал» — разность, а не соединение.** `ex05` существует ради особенности модели: журналы визитов и заказов независимы, между ними нет ключа. Соединять их нечем, и ответ получается вычитанием одного множества пиццерий из другого.

* **`max(id) + 1` честен только там, где нет конкуренции.** В `ex08`–`ex12` прямые числа для ключей запрещены, и ключ вычисляется подзапросом. В учебной базе это верно, в базе с параллельной записью — гонка: два сеанса прочитают один и тот же максимум. Настоящее решение той же задачи — последовательность, которой в этой модели нет.

* **`generate_series` вместо девяти `INSERT` и вместо `ROW_NUMBER`.** В `ex12` запрещены и одиночные вставки, и оконные функции, так что номер строки приходится брать у самого генератора ряда. Приём работает, но держится на том, что идентификаторы людей идут подряд от единицы: соединение `p.id = gs.num` при пропуске в `person` молча оставило бы кого-то без заказа — без ошибки, просто строк вышло бы меньше.

* **Порядок двух `DELETE` задаёт не стиль, а внешний ключ.** В `ex13` сначала удаляются заказы, потом сама пицца из меню. В обратном порядке PostgreSQL прерывает удаление: `violates foreign key constraint "fk_order_menu_id"`. Проверено запуском.

* **`UPDATE` не идемпотентен, и это видно на цене.** `price = price - price * 0.1` считает от текущего значения строки, поэтому второй запуск даёт скидку от уже уценённого. Заодно `numeric`-арифметика поднимает масштаб результата до масштаба множителя, и 800 становится `720.0`, а не `720`: значение верное, отличается только запись.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `ex00/` … `ex13/` | по одному файлу `day03_exNN.sql` на упражнение |
| `run.sh` | прогон с пересозданием базы и доигрыванием цепочки DML |
| `main_report.md` | разбор каждого запроса с фактическим выводом и состоянием базы до и после |

Схема и тестовые данные (`model.sql`) выданы курсом и в репозиторий не входят — без них запросы выполнить не на чем. Условия заданий тоже не публикуются, их формулировки пересказаны в отчёте своими словами.

### ▶️ Запуск

```bash
# model.sql — файл из поставки задания, в репозитории его нет
MODEL=/путь/к/model.sql ./run.sh all    # база пересоздаётся, затем ex00..ex13 подряд

./run.sh 11        # пересоздать базу, доиграть ex07..ex10, запустить ex11
./run.sh -k 11     # запустить ex11 на текущей базе, ничего не пересоздавая
./run.sh reset     # только пересоздать базу
```

Положенный рядом со скриптом `model.sql` подхватывается сам, имя базы переопределяется переменной `DB` (по умолчанию `sqlb4_dml`). Права суперпользователя не нужны, но нужны права на `createdb`.

**Скрипт удаляет и создаёт базу заново — это его работа, а не перестраховка.** Упражнения `ex07`–`ex13` кумулятивны, и запуск любого из них на базе от прошлого прогона даёт неверный результат: дубль первичного ключа, повторная уценка, удаление того, чего уже нет. Поэтому по умолчанию перед запуском упражнения `N` скрипт пересоздаёт базу и проигрывает `ex07`…`ex(N-1)`. Флаг `-k` это отключает — им удобно смотреть, что именно ломается на грязной базе.

`psql` вызывается с `ON_ERROR_STOP=1`: без него ошибка в запросе печатается, но код возврата остаётся нулевым, и сломанное упражнение в общем прогоне теряется.

### 📈 Итоговый результат

Все четырнадцать упражнений отрабатывают, вывод каждого приведён в отчёте.

Читающая половина сверена с образцами вывода из условия построчно, включая `ex04` и `ex05`, где образец состоит из единственной строки, — расхождений нет. Ответы дополнительно подтверждены независимо: `ex01` — тем же вопросом через запрещённый в задании `LEFT JOIN`, `ex03` и `ex04` — подсчётом визитов и заказов по полам агрегатами, `ex06` — группировкой по паре «название + цена».

У изменяющей половины образцов вывода нет — `INSERT 0 2` не говорит ничего о том, что именно вставлено. Поэтому каждый шаг цепочки проверен состоянием базы до и после: содержимое добавленных строк, счётчики таблиц (меню 18 → 20 → 19, визиты 19 → 21, заказы 20 → 31 → 22) и отдельно то, что `ex13` удаляет только свои девять заказов — в исходных данных заказов на эту дату нет.
