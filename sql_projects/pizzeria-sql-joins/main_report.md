# Отчёт: соединения таблиц вглубь

Одиннадцать упражнений про соединения: какой тип соединения отвечает на заданный вопрос, что происходит со строками без пары и чем анти-джойн заменяет запрещённые `NOT IN` и `NOT EXISTS`. Каждое упражнение — один файл `day02_exNN.sql`.

Отчёт построен на фактическом выводе: все одиннадцать запросов прогнаны заново на локальном PostgreSQL, результаты вставлены как есть.

---

## Условия прогона

| Параметр | Значение |
|---|---|
| СУБД | PostgreSQL 16.15 (Ubuntu 24.04) |
| База | схема и данные из `model.sql` поставки задания |
| Запуск | `./run.sh all` — все одиннадцать подряд, от обычного пользователя |
| Объём данных | 9 человек, 6 пиццерий, 18 позиций меню, 19 посещений, 20 заказов |

---

## Схема и данные

```
   person                          pizzeria
   ├─ id          PK               ├─ id       PK
   ├─ name                         ├─ name
   ├─ age                          └─ rating
   ├─ gender      female | male
   └─ address     город                    ▲              ▲
        ▲   ▲                              │              │
        │   └──────── person_visits ───────┘              │
        │             ├─ person_id   FK                   │
        │             ├─ pizzeria_id FK                   │
        │             └─ visit_date                       │
        │                                                 │
        └──────────── person_order                     menu
                      ├─ person_id  FK                 ├─ pizzeria_id FK ─┘
                      ├─ menu_id    FK ───────────────►├─ pizza_name
                      └─ order_date                    └─ price
```

Данных мало намеренно: результат любого запроса помещается на экран и проверяется глазами, а не выборочно.

Две особенности модели определяют половину заданий.

**Заказ не ссылается на пиццерию.** `person_order.menu_id` ведёт в конкретную позицию меню, и уже `menu.pizzeria_id` — в заведение. Поэтому путь «от заказа к названию пиццерии» всегда идёт через `menu`, а короткий путь по названию пиццы неверен: `pizza_name` не уникален, одна и та же пицца лежит в шести меню по разным ценам.

**Журналы не связаны между собой.** У `person_visits` и `person_order` нет ни общего внешнего ключа, ни связующей таблицы — только одноимённый столбец `person_id`, ведущий в один и тот же справочник. По условию задания это сделано намеренно: человек может сидеть в одном заведении и заказывать по телефону в другом. Соединение журналов по человеку и дате — доступная, но бессмысленная операция; ни одно задание дня её не требует.

---

## Теория, на которой стоят задания

### Соединение — это фильтр над произведением

Любое соединение начинается с декартова произведения двух таблиц, из которого условие `ON` оставляет подходящие пары. Псевдокод из условия задания:

```
FOR r in R LOOP
    FOR s in S LOOP
        if r.id = s.r_id then add(r, s)
    END;
END;
```

Отсюда два практических следствия. Забытое условие соединения не даёт ошибки — оно даёт произведение целиком. А соединение «один ко многим» размножает левую строку по числу найденных пар, и если правая сторона в результат не попадает, размножение выглядит как необъяснимые дубликаты. В `ex07`, `ex08` и `ex09` `DISTINCT` стоит именно поэтому.

### Что делает каждый тип

```
   таблица A        таблица B          INNER  — только пары
   ┌───┬───┐        ┌───┬───┐          LEFT   — все A, к B добавляется NULL
   │ 1 │ x │        │ 1 │ p │          RIGHT  — все B, к A добавляется NULL
   │ 2 │ y │        │ 3 │ q │          FULL   — все A и все B
   └───┴───┘        └───┴───┘

   INNER JOIN ON A.id = B.id        LEFT JOIN                 FULL JOIN
   ┌───┬───┬───┬───┐                ┌───┬───┬──────┬──────┐   ┌──────┬──────┬──────┬──────┐
   │ 1 │ x │ 1 │ p │                │ 1 │ x │  1   │  p   │   │  1   │  x   │  1   │  p   │
   └───┴───┴───┴───┘                │ 2 │ y │ NULL │ NULL │   │  2   │  y   │ NULL │ NULL │
                                    └───┴───┴──────┴──────┘   │ NULL │ NULL │  3   │  q   │
                                                              └──────┴──────┴──────┴──────┘
```

Строка без пары — не побочный эффект, а ответ на вопрос. Именно она означает «пиццерию никто не посещал» и «человек никуда не ходил».

### Анти-джойн

Комбинация «внешнее соединение плюс проверка на `NULL`» выражает разность множеств:

```
   LEFT JOIN                    WHERE B.id IS NULL
   все строки A                 остались только те,
   + найденные пары B           у кого пары не нашлось
```

Проверять надо столбец, который **не может** быть `NULL` в самих данных, — первичный ключ. Тогда `NULL` в нём однозначно означает «пары нет». Проверка по обычному столбцу смешала бы два разных случая: «строки не нашлось» и «нашлась, но значение пустое».

### `ON` против `WHERE`

Для внешних соединений это не вопрос стиля.

| Где условие | Что делает |
|---|---|
| в `ON` | отбирает строки правой таблицы **до** соединения; строки левой сохраняются в любом случае |
| в `WHERE` | фильтрует **результат**; строки с `NULL` в правой части не проходят проверку и исчезают |

Перенос условия из `ON` в `WHERE` превращает `LEFT JOIN` в `INNER JOIN` — молча, без ошибки. В `ex01` и `ex03` это вернуло бы пустой результат вместо восьми дат.

## Ограничения по упражнениям

| Упражнения | Запрещено | Чем заменяется |
|---|---|---|
| `ex00`–`ex03` | `IN`, `NOT IN`, `EXISTS`, `NOT EXISTS`, `UNION`, `EXCEPT`, `INTERSECT` | анти-джойн (`LEFT JOIN` + `IS NULL`), `FULL JOIN` |
| `ex01`, `ex03` | то же, но разрешён `generate_series(...)` | генератор дат как левая таблица соединения |
| `ex04`–`ex10` | ограничений нет | — |

Смысл ограничения — не в усложнении: четвёрка запретов заставляет выразить разность и объединение множеств средствами соединений, то есть увидеть за `JOIN` операцию реляционной алгебры, а не способ «дотянуться до соседней таблицы».

Соблюдение списка проверено отдельно, поиском по текстам решений: запрос, возвращающий верные строки запрещённым способом, задание не проходит.

## ex00 — пиццерии, где никто не был

Нужен список заведений с рейтингом, но только тех, что не встречаются в журнале посещений. Запрещены `NOT IN`, `NOT EXISTS` и операторы множеств — то есть всё, чем такой вопрос пишется напрямую.

```sql
SELECT pz.name,
       pz.rating
FROM pizzeria pz
         LEFT JOIN person_visits pv ON pz.id = pv.pizzeria_id
WHERE pv.id IS NULL
ORDER BY pz.name;
```

```
    name    | rating
------------+--------
 DoDo Pizza |    3.2
(1 row)
```

`LEFT JOIN` сохраняет все шесть пиццерий: у пяти находятся визиты, у шестой пары нет, и её правая половина заполняется `NULL`. `WHERE pv.id IS NULL` оставляет только такую строку.

Проверка идёт по `pv.id` — первичному ключу журнала. Он объявлен `NOT NULL`, поэтому `NULL` в нём возможен ровно по одной причине: строки не нашлось. Взять для проверки `pv.visit_date` было бы ошибкой другого рода — она в этой таблице тоже `NOT NULL`, но такой запрос перестал бы работать, как только в данных появился бы столбец с допустимыми пропусками.

Из шести заведений в журнале не встречается одно — DoDo Pizza.

## ex01 — пропущенные даты

Требуется вернуть дни с 1 по 10 января 2022 года, в которые не ходил **ни человек 1, ни человек 2**. Разрешён `generate_series(...)`, запреты те же.

```sql
SELECT gs.missing_date::date AS missing_date
FROM generate_series('2022-01-01'::date, '2022-01-10'::date, '1 day'::interval) AS gs(missing_date)
         LEFT JOIN person_visits pv
                   ON pv.visit_date = gs.missing_date::date
                       AND (pv.person_id = 1 OR pv.person_id = 2)
WHERE pv.id IS NULL
ORDER BY missing_date;
```

```
 missing_date
--------------
 2022-01-03
 2022-01-04
 2022-01-05
 2022-01-06
 2022-01-07
 2022-01-08
 2022-01-09
 2022-01-10
(8 rows)
```

Пропуск в данных — это отсутствующая строка, и достать её запросом по таблице нельзя: искать нечего. Поэтому сначала строится полный ряд из десяти дат, и уже из него вычитается то, что в журнале есть.

**Условие на человека стоит в `ON` намеренно.** В `WHERE` оно отбросило бы строки, у которых пары не нашлось: `person_id` там `NULL`, а `NULL = 1` не истинно и не ложно — результат неопределён, и строка не проходит фильтр. Анти-джойн выродился бы в обычное внутреннее соединение и вернул бы ноль строк вместо восьми. Ошибка тихая: запрос остаётся синтаксически верным.

**Приведение `::date` обязательно.** `generate_series` с шагом-интервалом возвращает `timestamp`, а `visit_date` имеет тип `date`. Без приведения сравнение пошло бы по значению с временем — совпадения находились бы, но полагаться на это нельзя.

Проверка ответа по данным: у людей 1 и 2 в этом окне два визита — 1 января (оба) и 2 января (только человек 2). Значит, свободны восемь дней с 3 по 10 января.

## ex02 — обе стороны целиком

Нужен полный список людей — посещавших и не посещавших пиццерии с 1 по 3 января — и одновременно полный список пиццерий, посещённых и не посещённых за тот же период. Пропуски в именах выводятся как `-`, сортировка по всем трём колонкам.

```sql
SELECT COALESCE(p.name, '-')  AS person_name,
       pv.visit_date,
       COALESCE(pz.name, '-') AS pizzeria_name
FROM person p
         FULL JOIN (SELECT *
                    FROM person_visits
                    WHERE visit_date BETWEEN '2022-01-01' AND '2022-01-03') pv
                   ON p.id = pv.person_id
         FULL JOIN pizzeria pz ON pz.id = pv.pizzeria_id
ORDER BY person_name, visit_date, pizzeria_name;
```

```
 person_name | visit_date | pizzeria_name
-------------+------------+---------------
 -           |            | DinoPizza
 -           |            | DoDo Pizza
 Andrey      | 2022-01-01 | Dominos
 Andrey      | 2022-01-02 | Pizza Hut
 Anna        | 2022-01-01 | Pizza Hut
 Denis       |            | -
 Dmitriy     |            | -
 Elvira      |            | -
 Irina       | 2022-01-01 | Papa Johns
 Kate        | 2022-01-03 | Best Pizza
 Nataly      |            | -
 Peter       | 2022-01-03 | Pizza Hut
(12 rows)
```

Двенадцать строк складываются из трёх частей: шесть реальных визитов за эти три дня, четыре человека, не ходивших никуда, и две пиццерии, куда никто не пришёл. Сохранить и людей без визитов, и пиццерии без посетителей может только `FULL JOIN` — `LEFT` сберёг бы одну сторону, `RIGHT` другую.

**Отбор по датам убран в подзапрос, и это главное решение задания.** Если написать его в `WHERE` внешнего запроса, отсеются строки людей без визитов: `visit_date` у них `NULL`, а `NULL` не попадает ни в один диапазон `BETWEEN`. Запрос вернул бы только фактические визиты — то есть ровно тот результат, ради отказа от которого и брался `FULL JOIN`. Ошибку не видно ни в тексте запроса, ни в сообщениях: он просто отдаёт меньше строк.

`COALESCE` подставляет `-` там, где имени нет. В `visit_date` замены нет — по образцу из условия пустая дата остаётся пустой.

Сортировка идёт по псевдонимам, а не по исходным столбцам: `-` должен встать в общий порядок наравне с именами, а не рядом с `NULL`.

## ex03 — то же самое через CTE

Задание требует переписать `ex01`, вынеся генератор дат в CTE, и получить точно такой же результат.

```sql
WITH date_generator AS (SELECT generate_series('2022-01-01'::date,
                                               '2022-01-10'::date,
                                               '1 day'::interval)::date AS missing_date)
SELECT dg.missing_date
FROM date_generator dg
         LEFT JOIN person_visits pv
                   ON pv.visit_date = dg.missing_date
                       AND (pv.person_id = 1 OR pv.person_id = 2)
WHERE pv.id IS NULL
ORDER BY dg.missing_date;
```

```
 missing_date
--------------
 2022-01-03
 2022-01-04
 2022-01-05
 2022-01-06
 2022-01-07
 2022-01-08
 2022-01-09
 2022-01-10
(8 rows)
```

Логика не изменилась: тот же анти-джойн, тот же план выполнения, те же восемь дат. Изменилось чтение запроса — генератор получил имя, приведение `::date` сделано один раз внутри CTE, и в теле запроса вместо вызова функции с тремя аргументами стоит `date_generator dg`.

Совпадение результатов проверено не глазами: разность двух выборок оператором `EXCEPT` пуста в обе стороны при одинаковом числе строк.

## ex04 — цены на грибную и пепперони

Нужны все варианты, где продаются эти две пиццы, с названием заведения и ценой. Имена колонок заданы условием.

```sql
SELECT m.pizza_name,
       pz.name AS pizzeria_name,
       m.price
FROM menu m
         INNER JOIN pizzeria pz ON m.pizzeria_id = pz.id
WHERE m.pizza_name = 'mushroom pizza'
   OR m.pizza_name = 'pepperoni pizza'
ORDER BY m.pizza_name, pizzeria_name;
```

```
   pizza_name    | pizzeria_name | price
-----------------+---------------+-------
 mushroom pizza  | Dominos       |  1100
 mushroom pizza  | Papa Johns    |   950
 pepperoni pizza | Best Pizza    |   800
 pepperoni pizza | DinoPizza     |   800
 pepperoni pizza | Papa Johns    |  1000
 pepperoni pizza | Pizza Hut     |  1200
(6 rows)
```

Простейший случай: соединение по внешнему ключу «многие к одному». Позиция меню принадлежит ровно одному заведению, поэтому `INNER JOIN` ничего не размножает, и `DISTINCT` не нужен.

Строк шесть, а не две: `pizza_name` в меню не уникален. Грибная пицца есть в двух заведениях, пепперони — в четырёх, и разброс цен на неё полуторакратный, от 800 до 1200.

Сортировка по `pizzeria_name` — по псевдониму: у обеих таблиц столбец называется `name`, и без псевдонима пришлось бы писать `pz.name`.

## ex05 — женщины старше 25

Имена всех женщин старше 25 лет, по алфавиту.

```sql
SELECT p.name
FROM person p
WHERE p.gender = 'female'
  AND p.age > 25
ORDER BY p.name;
```

```
  name
--------
 Elvira
 Kate
 Nataly
(3 rows)
```

Единственное упражнение дня без соединения: оба условия проверяются по одной таблице. Добавлять сюда `JOIN` ради темы дня значило бы усложнять запрос без нужды.

Сравнение строгое — «старше 25» не включает ровно 25-летних. Из пяти женщин в базе проходят три: Nataly (30), Kate (33), Elvira (45); Anna (16) и Irina (21) моложе.

## ex06 — что заказывали Денис и Анна

Нужны названия пицц и заведений, где эти заказы сделаны, отсортированные по обеим колонкам.

```sql
SELECT m.pizza_name,
       pz.name AS pizzeria_name
FROM person_order po
         INNER JOIN person p ON po.person_id = p.id
         INNER JOIN menu m ON po.menu_id = m.id
         INNER JOIN pizzeria pz ON m.pizzeria_id = pz.id
WHERE p.name = 'Denis'
   OR p.name = 'Anna'
ORDER BY m.pizza_name, pizzeria_name;
```

```
   pizza_name    | pizzeria_name
-----------------+---------------
 cheese pizza    | Best Pizza
 cheese pizza    | Pizza Hut
 pepperoni pizza | Best Pizza
 pepperoni pizza | DinoPizza
 pepperoni pizza | Pizza Hut
 sausage pizza   | DinoPizza
 supreme pizza   | Best Pizza
(7 rows)
```

Цепочка из трёх соединений, и каждое звено обязательно. `person` нужен, чтобы отобрать по имени; `menu` — чтобы узнать, что именно заказано; `pizzeria` — чтобы назвать заведение.

**Заведение определяется по `menu_id` заказа, а не по названию пиццы.** Соблазн срезать угол — соединить `person_order` с `menu` по `pizza_name` — даёт неверный ответ: сырная пицца есть в шести меню, и такой запрос вернул бы все шесть заведений вместо того одного, где заказ действительно сделан.

`DISTINCT` здесь не поставлен, и на этих данных он ничего бы не изменил: у Дениса и Анны семь заказов, и все семь пар «пицца — заведение» различны. Появись у одного из них два одинаковых заказа в разные дни, строка задвоилась бы — но условие спрашивает про заказы, и повтор был бы честным их отражением.

## ex07 — где Дмитрий мог поесть дешевле 800

Требуется найти заведение, которое Дмитрий посетил 8 января 2022 года и в котором **мог** заказать пиццу дешевле 800.

```sql
SELECT DISTINCT pz.name
FROM person p
         INNER JOIN person_visits pv ON p.id = pv.person_id
         INNER JOIN pizzeria pz ON pv.pizzeria_id = pz.id
         INNER JOIN menu m ON m.pizzeria_id = pz.id
WHERE p.name = 'Dmitriy'
  AND pv.visit_date = '2022-01-08'
  AND m.price < 800
ORDER BY pz.name;
```

```
    name
------------
 Papa Johns
(1 row)
```

Ключевое слово условия — «мог». Вопрос о возможности, а не о факте заказа, поэтому журнал заказов в запросе не участвует вовсе: путь идёт `person → person_visits → pizzeria → menu`.

**Соединять два журнала по человеку и дате — ловушка модели.** Такой запрос выглядит естественно и отвечает на другой вопрос: «где Дмитрий и был, и заказывал в один день». По условию задания эти события независимы, и ни одно упражнение дня их не связывает.

`DISTINCT` защищает от размножения строк последним соединением: в меню заведения может оказаться несколько позиций дешевле 800, и заведение вернулось бы столько раз, сколько их нашлось. На этих данных дубликат не возникает — в Papa Johns дешевле 800 ровно одна позиция, сырная за 700, — но правильность запроса не должна зависеть от конкретного наполнения меню.

## ex08 — мужчины Москвы и Самары

Нужны имена мужчин из Москвы или Самары, заказывавших пепперони, грибную пиццу или обе сразу. Сортировка — в обратном алфавитном порядке.

```sql
SELECT DISTINCT p.name
FROM person p
         INNER JOIN person_order po ON p.id = po.person_id
         INNER JOIN menu m ON po.menu_id = m.id
WHERE p.gender = 'male'
  AND (p.address = 'Moscow' OR p.address = 'Samara')
  AND (m.pizza_name = 'pepperoni pizza' OR m.pizza_name = 'mushroom pizza')
ORDER BY p.name DESC;
```

```
  name
---------
 Dmitriy
 Andrey
(2 rows)
```

Условия лежат в двух таблицах, но проверяются на одной строке результата: пол и город — из `person`, название пиццы — из `menu`. Скобки существенны, `AND` связывает сильнее `OR`, и без них «мужчина из Москвы» и «кто угодно из Самары» стали бы двумя независимыми ветками.

«Или оба вида сразу» отдельной обработки не требует: перечисление через `OR` покрывает и этот случай, а `DISTINCT` сводит несколько подходящих заказов одного человека к одной строке. На этих данных у каждого из двоих подходящий заказ ровно один, так что дубликат снова не проявился бы — но запрос от этого не зависит.

Проверка ответа по данным: мужчин в Москве и Самаре трое — Андрей, Дмитрий и Денис из Казани не в счёт; Андрей заказывал грибную, Дмитрий — пепперони, а третий подходящих заказов не делал.

## ex09 — и пепперони, и сырная

Нужны женщины, заказывавшие **обе** пиццы — в любое время и в любых заведениях.

```sql
SELECT DISTINCT p.name
FROM person p
         INNER JOIN person_order po_pep ON p.id = po_pep.person_id
         INNER JOIN menu m_pep ON po_pep.menu_id = m_pep.id
             AND m_pep.pizza_name = 'pepperoni pizza'
         INNER JOIN person_order po_che ON p.id = po_che.person_id
         INNER JOIN menu m_che ON po_che.menu_id = m_che.id
             AND m_che.pizza_name = 'cheese pizza'
WHERE p.gender = 'female'
ORDER BY p.name;
```

```
  name
--------
 Anna
 Nataly
(2 rows)
```

Одним условием это не выражается. Строка заказа содержит ровно одну пиццу, поэтому `pizza_name = 'pepperoni pizza' AND pizza_name = 'cheese pizza'` ложно всегда, а замена `AND` на `OR` отвечает на другой вопрос — «хотя бы одну из двух».

Поэтому журнал заказов подключается **дважды под разными псевдонимами**: первая цепочка ищет пепперони, вторая — сыр, и обе привязаны к одному и тому же человеку. Строка появляется в результате, только если нашлись обе — то есть требование «и то, и другое» выражено самим фактом успешного соединения.

Условие на название пиццы стоит в `ON`, а не в `WHERE`: так каждая пара «заказ — позиция меню» отбирается в момент соединения, и оба ограничения не мешают друг другу. В `WHERE` пришлось бы писать `m_pep.pizza_name = ... AND m_che.pizza_name = ...` — работает так же, но связь условия со своей цепочкой перестаёт быть видна.

Два соединения дают внутри человека произведение его заказов: две пепперони и один сыр обернулись бы двумя одинаковыми строками. `DISTINCT` это снимает. На этих данных у Анны и Натальи по одному заказу каждого вида, произведение равно единице — и снова видно, что прогон не доказывает правильность: обе версии, с `DISTINCT` и без, здесь дают один результат.

Из пяти женщин обе пиццы заказывали двое. У Эльвиры — пепперони и колбасная, сырной нет; у Ирины только грибная, у Кейт только сырная.

## ex10 — соседи по городу

Нужны пары людей, живущих по одному адресу, с сортировкой по трём колонкам и заданными именами колонок.

```sql
SELECT p1.name    AS person_name1,
       p2.name    AS person_name2,
       p1.address AS common_address
FROM person p1
         INNER JOIN person p2
                    ON p1.address = p2.address
                        AND p1.id > p2.id
ORDER BY person_name1, person_name2, common_address;
```

```
 person_name1 | person_name2 |  common_address
--------------+--------------+------------------
 Andrey       | Anna         | Moscow
 Denis        | Kate         | Kazan
 Elvira       | Denis        | Kazan
 Elvira       | Kate         | Kazan
 Peter        | Irina        | Saint-Petersburg
(5 rows)
```

Самосоединение: таблица соединяется сама с собой, строка сравнивается с другими строками той же таблицы. Псевдонимы `p1` и `p2` здесь не украшение — без них ссылки на столбцы неоднозначны и запрос не выполнится.

**Строгое неравенство `p1.id > p2.id` делает две вещи сразу.** Отсекает пару человека с самим собой — адрес у него, разумеется, совпадает — и оставляет от каждой пары одну строку вместо зеркальных двух: «Андрей и Анна» без «Анна и Андрей». Замена на `<>` дала бы десять строк вместо пяти, каждую дважды.

Сравнение идёт по `id`, а не по имени: `id` уникален, а тёзки при сравнении имён оказались бы равны и выпали бы из результата вместе с парой самого себя.

Из девяти человек соседи есть у шестерых: трое в Казани дают три пары, по двое в Москве и Петербурге — по одной. Наталья из Новосибирска и Дмитрий из Самары живут поодиночке и в результат не попадают.

## Как проверялись результаты

Прогон без ошибок ничего не доказывает: запрос с неверной логикой синтаксически корректен, и `psql` о нём не сообщит. Поэтому каждое упражнение проверено дважды — сверкой с образцом из условия и независимым запросом.

| Что проверялось | Как |
|---|---|
| имена колонок и порядок строк | посимвольная сверка с образцом вывода из условия — `ex01`–`ex06`, `ex08`–`ex10` |
| `ex00` (образца в условии нет) | тот же вопрос, заданный через запрещённый в задании `NOT EXISTS`, — ответ совпал |
| `ex01`, `ex03` | даты визитов людей 1 и 2 подняты отдельным запросом: заняты 1 и 2 января, свободны восемь дней |
| `ex03` ≡ `ex01` | `EXCEPT` между выборками пуст в обе стороны при равном числе строк |
| `ex02` | 6 визитов + 4 человека без визитов + 2 непосещённые пиццерии = 12 строк |
| `ex07` (образца нет) | визиты Дмитрия за 8 января и меню этого заведения выведены по отдельности: одно посещение, минимальная цена 700 |
| `ex08`, `ex09` | состав ответа подтверждён агрегатами: заказы мужчин Москвы и Самары, заказы женщин по видам пицц |
| `ex10` | список адресов с числом жильцов: 3 + 2 + 2 + 1 + 1 = 5 возможных пар |
| запрещённые конструкции в `ex00`–`ex03` | поиск по текстам решений с отсевом ложных совпадений (`INNER`, `INTERVAL`) |

Отдельно проверено то, что легко принять за правильность: в `ex06`, `ex07`, `ex08` и `ex09` дубликаты строк на этих данных не возникают, и запросы без `DISTINCT` вернули бы то же самое. Это свойство наполнения базы, а не запроса, — поэтому `DISTINCT` оставлен там, где соединение способно размножить строку.

## Итог

Одиннадцать упражнений отрабатывают, вывод каждого приведён выше и получен на живой базе. Расхождений с образцами из условия нет.

Главное, что показывает этот день: тип соединения — это не деталь синтаксиса, а формулировка вопроса. `INNER JOIN` спрашивает «что совпало», `LEFT JOIN` с проверкой на `NULL` — «чего не хватает», `FULL JOIN` — «покажи всё с обеих сторон». А ошибка в выборе не вызывает сообщения об ошибке: запрос выполняется и отдаёт правдоподобный результат, отличающийся от верного на те строки, которых в нём молча не стало.
