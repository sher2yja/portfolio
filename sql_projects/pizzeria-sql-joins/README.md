# 🍕 SQL: соединения таблиц вглубь

### 📌 Обзор проекта

Одиннадцать запросов к той же базе пиццерий, что и в [выборках](../pizzeria-sql-basics) и [множествах](../pizzeria-sql-sets). Тема здесь — соединения: не «как достать данные из двух таблиц», а **какой тип соединения отвечает на заданный вопрос** и что происходит со строками, у которых пары не нашлось.

Половина заданий именно про такие строки. Первые четыре запрещают `IN`, `NOT IN`, `EXISTS`, `NOT EXISTS` и все операторы множеств — то есть ровно те конструкции, которыми «найти отсутствующее» пишется в одну строку. Разность множеств приходится выражать соединением: `LEFT JOIN` оставляет строку без пары, заполняя правую сторону `NULL`, и проверка `IS NULL` отбирает именно её. Приём называется анти-джойном и в этих заданиях остаётся единственным доступным.

Вторая половина — обычный ANSI SQL без ограничений, где важно другое: правильно проложить путь по внешним ключам. Модель к этому располагает: заказ ссылается не на пиццерию, а на позицию меню, а два журнала событий не связаны между собой вовсе.

### 🏗 Схема базы

```
   person                          pizzeria
   ├─ id          PK               ├─ id       PK
   ├─ name                         ├─ name
   ├─ age              CHECK       └─ rating      CHECK 0 ≤ rating ≤ 5
   ├─ gender      female | male
   └─ address     город                    ▲              ▲
        ▲   ▲                              │              │
        │   │                              │              │
        │   └──────── person_visits ───────┘              │
        │             ├─ id          PK                   │
        │             ├─ person_id   FK                   │
        │             ├─ pizzeria_id FK                   │
        │             └─ visit_date       UNIQUE(person, pizzeria, date)
        │
        └──────────── person_order                     menu
                      ├─ id         PK                 ├─ id          PK
                      ├─ person_id  FK                 ├─ pizzeria_id FK ─┘
                      ├─ menu_id    FK ───────────────►├─ pizza_name
                      └─ order_date                    └─ price

   9 человек · 6 пиццерий · 18 позиций меню · 19 посещений · 20 заказов
```

Три справочника (`person`, `pizzeria`, `menu`) и два журнала событий (`person_visits`, `person_order`). Из схемы вытекают два обстоятельства, на которых строятся половина заданий дня:

* **Заказ не знает о пиццерии напрямую.** `person_order.menu_id` ведёт в позицию меню, и только `menu.pizzeria_id` — в заведение. Путь до названия заведения по заказу всегда трёхзвенный.
* **Журналы не связаны друг с другом.** Визит и заказ одного человека в один день по условию совпадают случайно. Соединять их по `person_id` технически можно, но смысл получится неверный.

### 🚀 Что интересного в запросах

* **Анти-джойн вместо `NOT IN`.** В `ex00` нужны пиццерии, которых нет в журнале визитов, а `NOT IN` и `NOT EXISTS` запрещены. `LEFT JOIN` сохраняет строку без пары и заполняет правую сторону `NULL`; `WHERE pv.id IS NULL` оставляет только такие строки. Проверять при этом надо первичный ключ — он объявлен `NOT NULL`, и `NULL` в нём означает ровно «пары не нашлось», а не пустое значение в данных.

* **Условие в `ON` и то же условие в `WHERE` дают разный результат.** В `ex01` и `ex03` отбор по человеку (`person_id = 1 OR person_id = 2`) стоит в `ON`. Перенести его в `WHERE` — значит отбросить все строки без пары, где `person_id` равен `NULL`: анти-джойн выродится в обычное внутреннее соединение и вернёт пусто. Для `LEFT JOIN` это общее правило: условие в `ON` фильтрует правую таблицу до соединения, условие в `WHERE` — результат после.

* **Искать пропуск можно только в готовом ряду.** Отсутствующая дата — это отсутствующая строка, и запросом по таблице её не достать. `generate_series` строит полный ряд дат, а анти-джойн вычитает из него то, что в журнале есть.

* **`FULL JOIN` и фильтр, который его обнуляет.** В `ex02` нужны и люди без визитов, и пиццерии без посетителей — обе стороны целиком. Отбор по датам убран в подзапрос намеренно: в `WHERE` внешнего запроса он выбросил бы строки людей без визитов, потому что `visit_date` у них `NULL`, а `NULL` не попадает ни в один диапазон. Результат остался бы синтаксически верным и молча неполным.

* **CTE не ускоряет, а называет.** `ex03` — переписанный `ex01`: тот же анти-джойн, тот же план выполнения. Разница в том, что генератор дат получает имя и перестаёт быть вызовом функции с тремя аргументами и приведением типа посреди `FROM`.

* **`pizza_name` не уникален — и это ловушка.** Одна и та же пицца продаётся в шести заведениях по разным ценам. В `ex06` название пиццерии берётся по `menu_id` заказа; сопоставление по имени пиццы вернуло бы все заведения, где она есть, вместо того одного, где её заказали.

* **`ex07` не касается журнала заказов.** Вопрос «где Дмитрий мог заказать дешевле 800» — про возможность, а не про факт, и решается путём `person_visits → pizzeria → menu`. Соединение двух журналов по человеку и дате дало бы ответ на другой вопрос и внешне столь же правдоподобный.

* **«И то, и другое» — это два соединения, а не два условия.** В `ex09` строка заказа содержит ровно одну пиццу, поэтому `pizza_name = 'pepperoni' AND pizza_name = 'cheese'` не истинно никогда. Таблица заказов подключается дважды под разными псевдонимами: одна цепочка ищет пепперони, вторая — сыр.

* **Самосоединение с `p1.id > p2.id`.** В `ex10` строгое неравенство делает две вещи сразу: отсекает пару человека с самим собой и оставляет от каждой пары одну строку вместо зеркальных двух. Сравнение идёт по `id`, а не по имени — тёзки сравнялись бы и выпали из результата.

### 📂 Что в папке

| Путь | Назначение |
|---|---|
| `ex00/` … `ex10/` | по одному файлу `day02_exNN.sql` на упражнение |
| `run.sh` | прогон: интерактивное меню или все одиннадцать подряд |
| `main_report.md` | разбор каждого запроса с фактическим выводом |

Схема и тестовые данные (`model.sql`) выданы курсом и в репозиторий не входят — без них запросы выполнить не на чем. Условия заданий тоже не публикуются, их формулировки пересказаны в отчёте своими словами.

### ▶️ Запуск

```bash
createdb sqlb3_joins
psql -d sqlb3_joins -f model.sql    # файл из поставки задания, в репозитории его нет

./run.sh all                        # все одиннадцать подряд
./run.sh                            # меню: Enter — следующее упражнение, q — выход
```

Имя базы переопределяется переменной окружения: `DB_NAME=my_db ./run.sh all`. Права суперпользователя не нужны — все запросы только читают данные.

Режим `all` возвращает ненулевой код, если хотя бы одно упражнение упало: `psql` вызывается с `ON_ERROR_STOP=1`, иначе он печатает ошибку и всё равно завершается успешно, и сломанный запрос в общем прогоне теряется.

### 📈 Итоговый результат

Все одиннадцать упражнений отрабатывают, вывод каждого приведён в отчёте.

Прогон на живой базе сверялся с образцами вывода из условия — по именам столбцов и по каждой строке образца в её позиции, включая замену `NULL` на `-` в `ex02` и обратный порядок сортировки в `ex08`. Расхождений не нашлось. Там, где образца в условии нет (`ex00`, `ex07`), ответ проверен независимым запросом: тем же вопросом, заданным через запрещённый в задании `NOT EXISTS`, и разбором данных по шагам. Отдельно подтверждено, что `ex03` возвращает ровно тот же набор строк, что `ex01`, — этого требует условие, — и что списки запрещённых конструкций соблюдены.
